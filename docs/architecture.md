# Architecture and runtime internals

Agent-facing reference for how the powbox image, identity, volumes, and bundled services fit together.
This is the detail that does not need to sit in every task's context — [AGENTS.md](../AGENTS.md) keeps only the always-on directives and routes here.
Container startup (the entrypoint chain, hooks, ordering, permission healing, shadow mounts) lives in a sibling chapter: [entrypoint-and-runtime.md](entrypoint-and-runtime.md).
For the deeper design specs, follow the cross-links at each section.

## Rules the file map does not state

See the README [Layout](../README.md#layout) for the repo file map. Rules that map does not state:

- There is one unified agent image `powbox-agent:latest` (`docker/agent/Dockerfile`) built on `powbox-agent-base:latest`. It installs both agent binaries — Codex directly on the base, then the stable shared-linter layers, then Claude — so a Claude version bump (the common case) busts only the Claude layer plus the cheap asset/entrypoint layers above it; a Codex bump rebuilds the linter and Claude layers on top too (accepted). Keeping Codex directly on the base also preserves the provenance resolver's base-ID-plus-version cache model. The old per-agent images (`powbox-claude`, `powbox-codex`) and Dockerfiles are gone. See [unified-agent-image.md](unified-agent-image.md) for the full spec and migration order.
- Each agent's image-baked seed assets live under a per-agent directory `/home/node/.agent-container/<agent>` (e.g. `docker/claude/agent-container/` → `/home/node/.agent-container/claude/`), read by that agent's hook via the `AGENT_SEED_DIR` variable so the two agents' templates, skills, statusline, and build epoch never collide.
- Image-baked skills are seeded into each agent's user-level skills directory at startup (`$CLAUDE_CONFIG_DIR/skills/` for Claude, `~/.agents/skills/` for Codex), no-clobber at the skill-directory level; a per-repo `.claude/skills/` (or `.agents/skills/`) still takes precedence at invoke time. The copy logic and the `.powbox-seeded` ownership marker live in one baked helper `docker/shared/seed-skills.sh` (`/usr/local/bin/seed-skills.sh`), sourced by both entrypoint hooks (`seed_skills … noclobber`) and the updater, so the sites cannot drift. The marker means "powbox owns this copy": a marked skill may be refreshed/pruned, an unmarked folder is treated as user-authored and never touched.
- Skill custody: `Roubtec/agent-skills` is the single source of truth for every skill (task 015 split the custody; the forfeit then moved the last powbox-specific skills — `enable-worktrees`, `session-learnings` — and the `wf-*` workflows there too). The bake+seed path above carries the **Codex palette only**, fetched in full from `Roubtec/agent-skills` at build time (`codex/dev-skills/skills/` → `/home/node/.agent-container/codex/skills/`; there are no in-tree skill sources left). Nothing is baked/seeded for Claude — its skills and the `wf-*` dynamic workflows all arrive through the `dev-skills@roubtec` marketplace plugin (namespaced `/dev-skills:<name>` and `/dev-skills:wf-<name>`; see the Claude plugin-channel bullet in [entrypoint-and-runtime.md](entrypoint-and-runtime.md) and README "Agent Skills"). So `update-skills.*` manages the bake+seed channel, and on a `claude-config` volume seeded before these custody changes it classifies every previously-seeded Claude item (the 8 shared skills, the 2 forfeited skills, and the seeded `wf-*.js` workflows with their sidecar markers) as prunable orphans — `update-skills-incontainer.sh`'s orphan sweep deliberately runs even for a kind whose baked source dir no longer exists in the image, so `--prune` retires them.
- Because of the no-clobber, a rebuilt image's updated skill text does not replace the stale volume copies; `commands/update-skills.*` (function `agent-update-skills`) force-refreshes the baked skills onto both config volumes via a throwaway container, running the shared in-container worker `docker/shared/update-skills-incontainer.sh` (a classify/apply engine over the same `seed-skills.sh`). It seeds absent skills, refreshes marked ones, reports unmarked name-collisions as conflicts (overwritten only with `--adopt-all`), and reports marked skills no longer baked as obsolete (deleted only with `--prune`); `--dry-run` previews. On a TTY it prompts before adopting/pruning, and `agent-update` offers to run it after a successful rebuild. The `.powbox-seeded` marker records the image build epoch and the powbox commit baked via the `POWBOX_COMMIT` build-arg (`scripts/build-image.{sh,ps1}` → `docker-bake.hcl` → Dockerfile, next to `build-epoch`), plus the item's **upstream** source as `source=<owner>/<repo>#<repo-relative-path>` (e.g. `source=Roubtec/agent-skills#codex/dev-skills/skills/<name>`) so an agent that finds a defect in a seeded skill learns where to fix it from one `cat` instead of a multi-command hunt. Marker readers parse by key, never by line number or count, so the two-line markers older images wrote still classify, refresh, and prune correctly — see [skills-refresh-and-provenance.md](skills-refresh-and-provenance.md) → D8. User-authored skills (no marker) are left untouched.
- The Claude-only dynamic workflows (`wf-address-tasks`, `wf-address-review`; no Codex sibling — Codex has no workflow runtime) live in `Roubtec/agent-skills` under `plugins/dev-skills/workflows/` and are delivered by the `dev-skills@roubtec` plugin (invoked `/dev-skills:wf-<name>`), not baked or seeded by powbox. Powbox previously seeded them into `$CLAUDE_CONFIG_DIR/workflows/` with a hidden sibling sidecar marker `.<name>.js.powbox-seeded` (a workflow is a single `.js` file with no "inside", so the marker cannot live in-folder); `seed-skills.sh` keeps its workflow primitives and `update-skills-incontainer.sh` keeps its claude workflow target exactly so those legacy seeded copies — including a stranded sidecar whose `.js` was hand-deleted — are still classified as `workflow` orphans and retired by `--prune`. The workflows deliberately avoid the runtime's built-in `isolation: "worktree"` (it cannot honor the `.worktrees/$CONTAINER_NAME/<slug>` convention and starts each agent from the default branch) — `wf-address-tasks` manages explicit convention worktrees through the baked `wt-*` helpers, `wf-address-review` shares the one checkout — and the prose skills remain in place alongside them; see README "Claude Dynamic Workflows" for the worktree contract.
- The mechanical worktree lifecycle is encoded once, as three scripts (`docker/shared/wt-bootstrap`, `wt-enter`, `wt-remove` → `/usr/local/bin/`) shared by both agents' worktree-running skills and the plugin-delivered `wf-*` Claude workflows: the workflows own control flow (waves, round caps, gating) as real code, agents own judgment, and the scripts own the git/worktree plumbing (root-safety checks, container-scoped orphan pruning, rerun-safe worktree resolve, guarded removal). Skill prose and workflow prompts must call these helpers rather than restate the plumbing — that split is what keeps the three layers from drifting. Like the entrypoint and per-agent hooks, these helpers are baked by the **agent** image, not the base, because they evolve in lockstep with the agent-layer assets that consume them — so editing one is picked up by the ordinary `agent-update` / `build.sh agent` rebuild (which reuses an existing base unless `--pull`) without forcing a base rebuild. The same agent layer bakes the other single-purpose helpers the skills and workflows call, for the same lockstep reason: `docker/shared/gitcat` (a cross-branch file reader with stable line numbers, for reading across a stacked-PR chain from one checkout) and `docker/shared/peer-review-run` (the bidirectional, provider-neutral peer-review runner — see below). Add a new such in-tree helper here, not in the base, whenever it is consumed by an agent-layer skill or workflow. A second, growing set of baked helpers is NOT kept in-tree at all: those vendored in `Roubtec/agent-skills` (`plugins/dev-skills/bin/`) as their single source of truth — the same files the `dev-skills` plugin ships to non-powbox users — which the agent layer bakes to `/usr/local/bin/` straight from the same agent-skills staging clone that feeds the Codex skill palette, so powbox carries exactly one copy of each tracking that clone rather than a hand-synced sibling. The rule for the set, rather than for any one member: it is the right home for a helper whose consumers include non-powbox users, the bake exists because the Codex palette is seeded from `.agent-skills-src/codex/…` which carries no `bin/` (Claude alone would already resolve the plugin's own copy on `PATH`, and that copy can only be staler, never divergent), and adding one costs a `.dockerignore` re-include, a line in the Dockerfile `COPY`, a presence guard in **both** build drivers, and — if it has an upstream contract suite — an imported `scripts/test-*.sh` routed to Tier 1. Editing the helper itself belongs upstream. The current members are `gh-review-threads` (a safe PR review-thread fetcher — manual pagination, never `gh api graphql --paginate`, with a repo-qualified, boundary-safe PR-scope assertion that fails closed on a contaminated response — used by both agents' `address-review` skills and the `wf-address-review` workflow) and the disposable-clone pair `dc-enter`/`dc-remove` (a clone of the invoking repository that a subagent can wreck while verifying a claim, where a worktree would not do because it shares `.git`; both halves are baked, since `dc-remove` is how a slug is freed and shipping the creator alone would send agents back to `rm -rf`). Powbox deliberately sets **neither** `DC_ROOT` nor `DC_AGENT`, because both helpers' defaults already land where powbox would point them: with `TMPDIR` unset in the container, clones go under `/tmp`, which is disk-backed overlay rather than a size-capped tmpfs — container-local and outside `/workspace`, exactly the placement `DC_ROOT` would express — and the scope component falls through to `CONTAINER_NAME`, which powbox sets, so clones are already keyed per container and per invoking worktree. The one case that scope does not separate is a `codex exec` peer invoked from inside a Claude container: it inherits the same `CONTAINER_NAME`, so the two share a slug namespace. That is an ergonomics wrinkle, not a safety one — `dc-enter` refuses an already-taken slug rather than reusing it, precisely so a concurrent sibling's verification is never pulled out from under it — and the fix, if it is ever worth making, is to export `DC_AGENT` from the same per-agent value that keys `/home/node/.agent-container/<agent>/` in the agent hooks. Note that `AGENT_SKILLS_COMMIT` **records** which snapshot was fetched; it does not select one. Both build drivers fetch a moving ref (`AGENT_SKILLS_REF="main"`) and derive the variable from the resulting checkout, so it is provenance stamped on the image. Editing its `docker-bake.hcl` default therefore changes nothing about which snapshot is baked; it would only mis-stamp the recorded SHA for someone invoking `docker buildx bake` directly — which is why the "did the snapshot actually contain this helper" question is answered by the per-file presence guards in `scripts/build-image.{sh,ps1}` instead. The `.dockerignore` re-includes exactly these helper paths, and nothing else, from the otherwise-excluded staging tree.
- `docker/shared/wf-check` and `docker/shared/wf-status` are read-only workflow-debugging helpers baked in that same agent layer. `wf-check` mirrors the installed Workflow loader's observable script contract: its private Acorn 8.15.0 dependency matches the parser bundled in Claude Code 2.1.221 and pinned acorn-walk 8.3.4 reproduces the runtime's AST compiler pass, the first statement is one exported `const meta` object, recursive metadata values are literals (including non-interpolated templates and negative numbers), `name`/`description` are non-empty strings while other literal metadata such as `phases` is accepted without interpretation, and the remaining source is compiled as a strict parameterless async body whose hooks are runtime globals — which accepts top-level `await`/`return`, permits local bindings that shadow hook names, maps syntax failures back to the original source lines, reserves `__wRg$` identifier names for generated wrappers, and rejects unsupported `await using` declarations. `wf-status` does not pretend the append-only journal contains more than it does: current journals record only keyed `started`/`result` entries, while phase events, labels, error states, and the workflow's final return are in the sibling `workflows/<runId>.json` snapshot; agent sidecars currently carry only `agentType`/`spawnDepth`. It combines all three surfaces, uses transcript prompts only as a clearly best-effort label fallback, and reports absent/truncated killed-run artifacts as warnings with unknown/pending values rather than changing the harness or journal schema.
- `docker/shared/peer-review-run` (baked to `/usr/local/bin/peer-review-run`) is the bidirectional, provider-neutral peer-review runner: a Claude-led workflow reviews with Codex and a Codex-led workflow reviews with Claude through ONE command interface and ONE result contract, replacing the hand-written process supervision, prompt quoting, artifact management, polling, output parsing, and cleanup that peer-review loops used to carry inline. It owns creating a fresh owner-only (`0700`, fail-closed — the run is rejected if the artifact-root filesystem cannot enforce the mode) attempt directory OUTSIDE the reviewed worktree per attempt (never reused across a retry), nested under one per-invocation, unpredictably-named `0700` session dir (never a direct child of the artifact-root) so the path a provider is handed neighbours only THIS invocation's attempts, never a concurrent or retry sibling's. The by-default isolation guarantee is made as strong as filesystem permissions allow by handing the provider only the MINIMAL paths it needs — it is `--cd`'d into the worktree under review (artifacts stay OUT of that tree) and given only the one specific output-file path inside its OWN attempt dir, never the artifact-root/session/sibling on argv, stdin, `--cd`, or `--output-last-message`. Residual, stated honestly (NOT complete isolation): the providers' read-only sandboxes are permission/read-only, not a private mount namespace, and run as the SAME UID as the artifacts, so a determined provider that manually climbs `..` out of its handed attempt dir to the artifact-root CAN read a sibling it was never handed — `0700` cannot stop a same-UID reader. The guarantee is precisely that the helper does not HAND a sibling/parent path and a normal review does not encounter one; complete traversal-proof isolation would need a filesystem sandbox (bubblewrap / private mount namespace) and is out of scope for this helper. The hermetic test (case 11c) asserts BOTH the handed-path guarantee and, honestly, the traversable residual. It also owns literal prompt handling (the prompt file's contents are fed on the provider's stdin, never placed on argv or through a shell), read-only provider execution, process-group supervision with a timeout, a retry-once policy that is a **transient allowlist** — it retries ONLY a failure positively identified as transient (network/connection errors, explicit timeouts, 5xx/overloaded/"try again" signals); an unclassified/unknown non-zero exit is NOT retried, and auth/usage/quota signals short-circuit to `unavailable` — result parsing, and process reaping on every success/failure/timeout path (TERM the validated process group — its PGID confirmed to equal the leader PID, never an unvalidated negative PID and never `pkill -f` — then a bounded grace, then escalate to KILL for survivors — supplemented on EVERY path, not only the rare unvalidated-PGID fallback, by a start-time-verified descendant PID set SNAPSHOTTED while the leader is still alive (accumulated each poll tick and before the wait/reap) so a stray grandchild is recorded BEFORE the leader exits and reparents it to init, which a tree-walk rooted at the already-dead leader would miss: the per-PID sweep runs after the group kill so a descendant that LEFT the validated group (e.g. a provider tool calling `setsid` into a new session/process group) is still reaped, and on the fallback it is the only reach; the set is seeded with the leader's launch-time start time, a live re-walk runs only while the leader still matches that baseline, and the walk itself verifies lineage PER LEVEL — each candidate child's parent link and start time come from one atomic `/proc` snapshot, the parent is re-verified against its own chained baseline AFTER that snapshot, and a level whose parent no longer matches is discarded unrecorded — so neither a recycled leader PID nor a recycled INTERMEDIATE PID mid-walk can ever have an unrelated process's children captured or signalled — and if any descendant somehow survives SIGKILL the result's `reason` says so honestly rather than reporting a clean reap (a reap failure during an interrupted run's EXIT-trap teardown, where no result JSON is emitted, is reported as a stderr warn event instead); collecting the ZOMBIE entry of a descendant killed after its leader died is the reaping ancestor's job, which the powbox runtime provides — every agent container launches with `init: true` in `compose.shared.yml`, so PID 1 is docker-init and reparented children are promptly collected). Invoke as `peer-review-run --provider <claude|codex> --worktree <ABS_DIR> --prompt-file <FILE> --artifact-root <ABS_DIR> [--base <REF>] [--timeout <SECONDS>] [--model <ID>] [--effort <LEVEL>]`. The last two are the **review-strength knobs**, and they DEFAULT rather than inherit: `--effort` is `high` for both providers, and `--model` is `opus` for claude while codex, whose `gpt-5.6-luna`/`-sol`/`-terra` families expose no rolling alias (and a dated ID hard-coded here would rot into a wrong pin that outlives the model), instead has its CONFIGURED model preserved: with no `--model`, the helper reads the ROOT top-level `model` from `${CODEX_HOME:-~/.codex}/config.toml` — the file the container's `/model` workflow writes — and re-applies it as one `-m` argument, so the adapter's own `--ignore-user-config` no longer silently drops the tier someone selected. Nothing else from that file crosses the isolation boundary, and the passthrough is deliberately conservative: a root `profile` or ANY explicit root `model_provider` makes the bare name profile- or provider-dependent, so the helper forwards nothing, warns, and reports `model:null` rather than reviewing with something the caller did not pick (no provider identity is hard-coded as safe, and `[profiles.*]`/`[model_providers.*]` are never forwarded). A missing config, or one carrying no root `model`, is the SILENT unconfigured case — no `-m`, `model:null`, and no warning, exactly as before this passthrough existed. An unreadable/unparseable/empty/non-string/flag-shaped/non-printable value (a model carrying a newline cannot survive the command substitution the reader's result is read through, so it is rejected rather than passed altered), a config path that is not a regular file (a FIFO, a `/dev/zero` symlink) or one past the read cap, and an interpreter without `tomllib` all take the honest-degradation path — no `-m`, `model:null`, a stderr warning — never a failed review; an explicit `--model` wins and bypasses the lookup entirely. The lookup is resolved in the strength-knob block BEFORE any artifact/session filesystem side effect, and the file is parsed as TOML by an isolated `python3 -I` program that opens non-blockingly and classifies by `fstat` on that same descriptor (`-I` is load-bearing rather than hygiene: a plain `python3 -c` puts the invocation's working directory on `sys.path`, and this helper is routinely run from the checkout under review). `--effort` stays independent throughout — a configured `model_reasoning_effort` never overrides the requested level. Inheriting was the wrong default because `~/.claude/settings.json` and `~/.codex/config.toml` are shared mutable state every container writes through `/model`, so review strength silently became a function of whichever model someone last picked in some other container — and for codex it was worse than that: this adapter's own `--ignore-user-config` DISCARDS that config, so before these defaults a codex peer reviewed at `reasoning effort: none`. Both knobs are per-invocation and never write back to the shared configuration. `--effort` accepts `low|medium|high|xhigh|max` (`max` is claude-only, rejected up front for codex because `codex exec` would accept the bogus level in its session header and only die on a 400 mid-review); `none` and `minimal` are deliberately unaccepted — the former is exactly the silent weakness these defaults end, and the latter is API-rejected on current models. The provider adapters are not one command string: the Claude adapter runs `claude -p --safe-mode --no-session-persistence --output-format json` and — because Claude has NO filesystem sandbox, so its read-only guarantee is purely permission/tool-surface based — restricts the very built-in tool SET to the native read-only tools with `--tools Read,Grep,Glob` (matching allow list, plus a defense-in-depth deny list naming `Bash` and every write tool) and NO `--dangerously-skip-permissions`. This deliberately drops the earlier allowlisted Bash read-*commands*: an allowlisted `Bash(cat:*)`/`Bash(git …:*)` still permits shell REDIRECTION (`cat secret > file` WRITES, because the permission match is on the command prefix, not the redirection) — the same write vector as the old `sed -i` hole — so no Bash tool exists at all and there is no command to redirect. Residual, documented honestly: Read/Grep/Glob can still READ any path Claude's user can read (that is the point of a review) but none can WRITE; and with no shell the Claude reviewer cannot run `git diff` itself, so a diff-oriented prompt should embed the diff or reference the base while the file tree stays reviewable over `--add-dir`. `--safe-mode` disables CLAUDE.md/skills/plugins/hooks/MCP and other customizations for the untrusted run and `--no-session-persistence` keeps the prompt/result off disk. Auth precedence honors powbox's documented OAuth-primary/key-fallback model for the headless peer (README "Cross-Agent Delegation"): because `claude -p` otherwise prefers an inherited env credential — `ANTHROPIC_API_KEY`, `ANTHROPIC_AUTH_TOKEN`, or a `CLAUDE_CODE_OAUTH_TOKEN` setup token, all three of which Claude Code checks AHEAD of the stored login with no fall-through in one invocation — over the logged-in session, a stray/stale one could shadow a working login (making the peer `unavailable`, or misbilling to the pricier API account), so the runner drives the precedence itself — it attempts the LOGIN first (when a `${CLAUDE_CONFIG_DIR:-$HOME/.claude}/.credentials.json` is present it clears ALL THREE of those env credentials with an `env -u` prefix so the subscription session is used — clearing only the two `ANTHROPIC_*` vars would let a stale setup token still shadow the login), and only if that attempt comes back `unavailable` (an expired session or a session limit — an auth failure yielding no verdict) while an env credential IS available does it retry ONCE in key mode so the documented fallback still authenticates the peer; either credential may be expired, and if neither authenticates the peer stays `unavailable`. This auth-fallback retry is distinct from and mutually exclusive with the transient-failure retry, so total attempts stay capped at two. Non-credential settings like `ANTHROPIC_BASE_URL` are never touched, and the Codex side needs no analog since powbox treats `CODEX_API_KEY` as a first-class auth path. Its JSON envelope is honored — a non-`result` `type` or an `is_error:true` object is treated as no usable verdict (so a pass token inside an error/malformed envelope never becomes `passed`) — and it is represented honestly as buffered (`liveProgress:false`, one up-front note, no simulated heartbeats). The Codex adapter runs `codex exec --sandbox read-only --cd <worktree> --ephemeral` with the version-independent config overrides `-c mcp_servers={}` (so no MCP/server state leaks into the untrusted review and no session files persist), `-c approval_policy=never` (a headless review must never stall waiting for an approval an inherited `on-request`/`untrusted` policy would demand; an unrecognized key is ignored on older CLIs without `--strict-config`), and `-c project_doc_max_bytes=0` (the reviewed worktree's `AGENTS.md` is NOT loaded as reviewer instructions — `--ignore-user-config`/`--ignore-rules` leave project docs enabled, so without this the code under review could steer its own reviewer through a PR-modified `AGENTS.md`), plus the config/hook-isolation flags — the Codex analog of Claude's `--safe-mode`, so the code under review cannot steer its own reviewer: `--ignore-user-config` (skips `$CODEX_HOME/config.toml` and with it the persisted project-trust table, so the reviewed worktree's trusted-project config/hooks do not activate; auth still works), `--ignore-rules` (no user/project execpolicy `.rules`), `--disable hooks` (hooks feature off for the invocation), and `--ask-for-approval never` (the explicit flag spelling of the approvals-off policy, on the CLIs whose `codex exec` accepts it — current ones, e.g. 0.144.6, do not list it there and rely on the `-c` override); each of these — like `--json` live progress (streamed to stderr, `liveProgress:true`, when advertised) — is probed against one cached help capture and omitted on an older CLI that lacks it, degrading to the mcp-only isolation rather than failing on an unknown flag; the probe is provider-neutral (only the selected provider is ever probed, so it stays one subprocess either way) and the Claude adapter uses it for `--effort`, which is recent enough that a lagging image can lack it — there the flag is dropped and the result reports `effort:null`, because silently omitting it while still claiming `high` would leave the caller believing in a pin that never landed; claude's `--model` is unprobed, having been part of headless mode for as long as headless mode has existed; the help probe itself runs under the same process-group supervision and reaping as an attempt (bounded — as a WHOLE — by `min(--timeout, 10s)`: that budget is the hard poll backstop, with the inner `timeout` sending TERM at half the budget and SIGKILL at three-quarters, so for any realistic `--timeout` a hung `codex exec --help` is reaped within the deadline (not deadline-plus-grace) before any attempt starts — the only residuals being the ~0.1s poll-loop floor for a degenerate sub-0.1s budget and, for a probe descendant that both escapes the group via `setsid` and ignores TERM, `reap_tree`'s bounded escalation window (the same stubborn-escapee residual the reaper carries everywhere), output captured through a file so a stdout-inheriting stray can never hang a pipe read), so a background child the `--help` path leaves behind is swept by the post-probe group reap instead of outliving the run — the no-live-peer-process guarantee covers the probe, not only the attempts. The **result contract** (its FINAL, and only, stdout is one JSON object, schema `powbox.peer-review-run/v1`): `{ schema, provider, outcome, verdict, elapsedSeconds, exitStatus, attempts, retried, liveProgress, model, effort, artifactDir, reviewFile, reason }`, where `elapsedSeconds` is the total wall time across ALL attempts (a retried run reports the sum, never the final attempt alone), `model` and `effort` report the strength the peer ACTUALLY ran at — null where the knob was not applied (a codex model that was neither given nor safely resolvable from configuration, an `--effort`-less CLI, or an `unavailable` run that never reached a provider) — so a caller can VERIFY review strength rather than trust that its flags landed, `reviewFile` is the **provider-neutral review payload**: for `passed`/`issues`, the absolute path of `<artifactDir>/review.txt` holding the peer's COMPLETE final review message as plain text with provider JSON envelopes already decoded (null for every other outcome), so a caller relays the prose from one documented path instead of opening `provider.stdout`, constructing codex's final-message filename, or parsing a provider-native format — the guarantee is "plain text, byte-identical to the parsed message" and no more (that message reaches the writer through a command substitution, which drops NUL bytes and strips trailing newlines, and nothing validates UTF-8), the provider-native artifacts stay in `artifactDir` unchanged so this is an additional consumption surface rather than a replacement for diagnostic evidence, and the file is created `O_CREAT|O_EXCL` at 0600 with its bytes read back and compared on that same descriptor before the result is emitted — fail-closed on content, warn-and-continue on the mode (whose privacy rests on the enclosing 0700 attempt dir anyway), and honestly bounded: `O_EXCL` protects the final path component only, and a same-UID descendant can still swap the emitted path after the helper exits, so the promise is against a STANDING obstacle rather than an actively racing writer; and all of these are additive within schema `v1` because consumers read keys by name and no promised field changed and `outcome` is one of `passed | issues | unavailable | timeout | forfeited | failed` and `verdict` is `pass | issues | none` (normalized from a documented `VERDICT: …` token the reviewer emits — the runner parses the verdict, it does not judge review content; detection is anchored to a `VERDICT:` line with ISSUES taking precedence and scans the whole verdict value, so neither a body that merely quotes an example pass token (inline, fenced — including a longer/nested or list-/blockquote-wrapped fence — blockquoted, inline-code, or any nesting of those — the PASS side lexes and strips fenced blocks by CommonMark's fence rules (char+length match, code-span-vs-opener, blockquote-container depth on close), drops CommonMark indented code lines (>= 4 columns of leading indent — four spaces or a tab from column 0-3, so an indented `    VERDICT: PASS` example cannot false-pass), and refuses a pass whose leading decoration carries a quote marker (`>`/backtick) at any depth; the only residuals — all exotic, never produced by a compliant peer, and irreducible without a full Markdown block+inline parse — are a bare unquoted example line, a genuine verdict lost after mixed list+blockquote container nesting (a forfeit, the safe direction), and a line enclosed by a multiline inline-code span) nor a mixed line like `VERDICT: APPROVED, CHANGES REQUIRED` — including one whose pass token is itself a negated alias, `VERDICT: NO ISSUES, CHANGES REQUIRED` — can false-pass, while negated pass language such as `no issues found` still passes). The runner NEVER reports success from an absent or empty output; a missing binary, unavailable login, or usage exhaustion is `unavailable`, a deadline is `timeout`, a clean exit whose final message is empty/verdict-less/malformed is `forfeited` (distinct from an execution-failure `failed`), and every such outcome is **non-blocking** — the helper exits 0 for any produced outcome EXCEPT one whose `reviewFile` could not be created or verified, which exits 70 and emits NO result (a completed, already-paid-for review is discarded rather than reported with prose the helper could not prove), and non-zero otherwise only for its own usage/operational errors. **Runtime precondition:** besides `jq` the helper now requires `python3`, which creates, writes, modes and verifies that `reviewFile`; it is preflighted before any provider is launched and its absence exits 70, because discovering it after a completed review would throw away work nobody can get back. Python 3 is baked into the agent image this helper ships in, so this is a documented precondition rather than a live degradation path — but adopters running the helper elsewhere need it. Its `tomllib` module is optional: an interpreter without it (it arrived in 3.11) degrades codex configured-model passthrough with a warning, exactly like an unparseable config. A peer result **supplements but does not replace** the fresh-reviewer subagent gate, and no peer opinion is required for publication. **agent-skills adoption boundary:** the shared `Roubtec/agent-skills` review skills should consume this stable invocation/result contract instead of carrying provider-specific launch guidance; the generic process mechanics live in powbox (this helper), and the external skill files are NOT copied into this repo — the contract in this bullet, plus the helper header, is the downstream adoption boundary. Two powbox-owned prerequisites for that repo's task 015 land here rather than there, and both are now satisfied: its Claude-led renderings kept a raw isolated `codex exec` launch only because the helper could not preserve a configured Codex model without embedding a dated model ID (the configured-model passthrough above removes that reason, and no adopter has to name a model ID), and every rendering needed a stable way to retrieve the peer's full review prose before it could drop its provider-specific extraction (`reviewFile` is that way, and no adopter has to know a provider-native filename or format). Hermetic coverage with fake `claude`/`codex` binaries is `scripts/test-peer-review-run.sh`: Tier 0 runs the repo source, while smoke Stage 0f targets the baked helper. A live both-direction smoke needs a rebuilt image (real providers, a disposable worktree) and cannot run in-container.
- Image provenance: each image records the powbox commit that built it. A piecemeal build can carry up to three distinct commits — base (its own parent), codex, and claude/top — so they are tracked separately. Host-side: labels `powbox.commit.{base,codex,claude}` (+ `powbox.{codex,claude}.version` and `powbox.base.image.id`), surfaced by the `agent-image-info` shell function and in `agent-update` output. In-container: files `/home/node/.powbox/{base,codex,claude}.commit` (base inherited from the base image), printed by the baked `powbox-provenance` command. The codex commit is computed in `scripts/build-image.{sh,ps1}` (HEAD when the Codex layer rebuilds, else the prior image's value carried forward) and stamped only in the top metadata layer — never inside the Codex install layer, which would bust its cache. Reuse is judged against that layer's cache key — its parent base image (`powbox.base.image.id`) and `CODEX_VERSION` (`powbox.codex.version`) — so a separate base rebuild correctly re-stamps codex at HEAD; see [skills-refresh-and-provenance.md](skills-refresh-and-provenance.md) for the residual pre-build-prediction limitation. `-dirty` marks an uncommitted worktree. Introspection only; no logic depends on these values.
- Entrypoint scripts all live in `docker/shared/`, but only `entrypoint-core.sh` is baked by the base image. The unified entrypoint `entrypoint-agent.sh` and both per-agent hooks (`entrypoint-{claude,codex}-hook.sh`) are baked by the agent image, so editing the entrypoint or a hook only requires rebuilding the agent image — not the base. The old per-agent entrypoint shims (`entrypoint-{claude,codex}.sh`) are gone, replaced by `entrypoint-agent.sh` plus its in-script agent registry.
- After cutover the obsolete `powbox-claude` / `powbox-codex` images can be removed with `docker image rm powbox-claude powbox-codex` — non-destructive to the `claude-config` / `codex-config` volumes.

## Project Identity

There are two launch modes; the launchers (`scripts/launch-agent.{sh,ps1}`) branch the identity block on `--isolated` and dir-mounted is the default.

- **Dir-mounted (default, unchanged):** per-project identity uses `basename + SHA256(full path)` (truncated to 12 chars) so container names and `node_modules` volumes do not collide across similarly named projects. The host working dir is bind-mounted; this path-based identity is the contract and must not be altered.
- **Self-hosted (`--isolated`):** the container clones the repo into a private per-instance volume instead of bind-mounting the host (see README "Self-Hosted Mode"). Identity is `<repo-slug>[-<name-slug>] + SHA256(label-or-timestamp)[:12]` — the same 12-char hash shape — where the discriminator is `--name <label>` (deterministic → reusable: same clone + session history across launches) or, unnamed, a high-resolution timestamp (fresh every launch). The optional `<name-slug>` is a sanitised, capped rendering of `--name` woven into the name for human/`cc-list` legibility only; the **raw** `--name` (folded into the hash, and stored verbatim in the `powbox.instance-name` label) owns identity, so two names that slugify alike stay distinct. `--ref` is excluded from the hash (volatile). The repo is a required input (positional or `--repo`); when omitted inside a git repo it is inferred from `git remote get-url origin`. Self-hosted containers also carry `powbox.repo` / `powbox.ref` labels for the lists. All self-hosted logic is gated behind `--isolated` so the dir-mounted path is byte-for-byte unchanged.

## Volumes and Stores

See README "Workspace Shadow Mounts" and "Runtime" for volume behavior. The non-obvious constraint: pnpm can only **hardlink** from its store when the store and the target `node_modules` share **one mount** (not merely one device — `link(2)` returns `EXDEV` across mount points even on the same filesystem). So the per-container pnpm store lives *inside* the `.worktrees` volume (`agent-wt-<agent>-<project>`) alongside every `.worktrees/<task>/node_modules`, and `package-import-method=auto` lets pnpm hardlink there and transparently fall back to copying for the root `node_modules` (a separate mount). The launcher passes `PNPM_STORE_DIR` and `entrypoint-core.sh` points pnpm at it per project.

Both are gated, and on *different* gates: the `.worktrees` volume is mounted for dir-mounted JS/powbox, `go.mod`, or boundedly detected .NET projects, while `PNPM_STORE_DIR` is set only on the narrower JS/powbox gate — so a Go- or .NET-only repo gets the volume with no pnpm store in it, and a non-dev folder gets neither, and no `.worktrees` mountpoint at all: every way to declare that shadow (a committed `.powbox.yml`, or a `.powbox.local.yml` with a top-level `shadow:` key) also trips the JS/powbox gate, so `detect-shadows.sh` emits nothing for a genuinely non-dev folder — the tmpfs fallback documented elsewhere is about a repo that *declares* `.worktrees` yet is launched without the volume. The .NET predicate is intentionally finite and case-insensitive: `*.sln`/`*.slnx`/`*.csproj`/`*.fsproj`/`*.vbproj` at the root or exactly one directory below it, including dot-prefixed direct children; inaccessible or vanishing children and symlink/reparse-point files or directories are skipped. This covers common `src/App.sln` and `src/App.csproj` layouts without recursively walking large repositories or following a link outside the checkout. A layout whose only solution/project markers are deeper is not auto-detected; adding a root solution file preserves the .NET-only no-`node_modules` shape, while opting in with `.powbox.yml` instead deliberately trips the broader JS/powbox gate and therefore mounts `agent-nm-*` too. Under `--isolated` the launcher sets `PNPM_STORE_DIR` regardless of project type, and the store is a plain subdir of the single `agent-ws-*` workspace volume rather than of a separate one — the one-mount property that makes hardlinking work holds in every case.

Context mounts are host-side launch concerns, not container startup behavior. The launchers derive a context mount set from CLI `--ctx` / `-Ctx` or effective `ctx:` config in `.powbox.yml` / `.powbox.local.yml`, mount each source under `/ctx/<name>` through a generated compose overlay attached only to the final agent run, and record the canonical derived set as the `powbox.ctx-hash` container label so stopped containers recreate when the set changes. With no CLI ctx and no effective `ctx:` key, the launcher deliberately skips that comparison and preserves any existing context mounts.

The same `.worktrees` volume also persists the Go caches (`.gomodcache`, `.gocache`, and the per-worktree `.golangci-cache/…`) via launcher-exported `GOMODCACHE`/`GOCACHE` env and the golangci-lint wrapper, the NuGet global packages folder (`.nuget`, launcher-exported `NUGET_PACKAGES`), and the opt-in ccache compiler cache (`.ccache`, launcher-exported `CCACHE_DIR`) — see "Bundled Go toolchain" and "Bundled .NET SDK" below for locations, the split volume gate, and the sharing-vs-isolation reasoning.

It also carries the **durable per-worktree git metadata** at `.worktrees/.gitworktrees`, which `shadow-mounts.sh` **bind-mounts over `.git/worktrees`** (instead of tmpfs) whenever `.worktrees` is the persistent volume. Co-locating the metadata inside the one per-container volume — rather than a separate durable resource that could drift from the working-tree storage — gives it exactly the volume's lifecycle: a linked worktree and its uncommitted changes survive a container recycle (`git status` still works), and pruning the `agent-wt-*` volume removes the metadata with it. The bind stays container-local (it hides the host's own `.git/worktrees` and keeps container registrations off the host), and without the volume (fallback launch) `.git/worktrees` reverts to tmpfs. This is the co-located, lighter form of the `A-coherent` alternative that [worktree-node-modules-hardlinks.md](worktree-node-modules-hardlinks.md) originally deferred: it adds **no** new volume and no `git worktree prune` discipline — orphan reaping instead preserves (never deletes) any non-empty dir whose metadata was lost. In self-hosted mode the metadata is already a plain subdir of the one workspace volume, so no bind is needed (`shadow-mounts.sh` is skipped there).

In **self-hosted (`--isolated`)** mode this three-mount layout collapses to **one**: a single per-instance `agent-ws-<container>` volume mounted at `/workspace/<slug>` holds the clone plus `node_modules`, `.worktrees`, and the pnpm store, Go/NuGet caches, and ccache as ordinary subdirs. The dir-mounted `agent-nm-*` / `agent-wt-*` shadow volumes are omitted (no host FS underneath to shadow), the workspace bind mount is replaced via `compose.selfhosted.yml` (merged by target path, mirroring the fuse/netdev overlays), and `shadow-mounts.sh` is skipped entirely in `entrypoint-core.sh`. Because everything shares one mount, pnpm hardlinks everywhere — including the root `node_modules`, which falls back to copying in dir-mounted mode. The `agent-ws-*` and per-container `agent-podman-*` volumes are keyed by the full container name (part of the container identity); prune tooling (`commands/prune-volumes.*`) GCs orphaned `agent-ws-*` volumes alongside the others.

Deep dive (measured rationale, the copy→hardlink decision, validation): [worktree-node-modules-hardlinks.md](worktree-node-modules-hardlinks.md).

## Bundled PostgreSQL

- The base image installs the PostgreSQL 16 server + client + contrib from the official PGDG apt repo (`docker/base/Dockerfile`), version-matched to the `postgres:16.x` images projects pin so integration suites don't hit behavior drift from Debian's stock 15.
- No daemon is started at build or runtime. `docker/shared/pg-dev-up` (baked to `/usr/local/bin/pg-dev-up`) stands up a throwaway loopback cluster on demand under `$PGDATA` (default `/tmp/pgdata`), as the unprivileged `node` user with trust auth — so it needs **no** sudoers entry. Credentials/port/db are env-overridable; see the script header.
- The server binaries live off `PATH` at `/usr/lib/postgresql/<major>/bin`; `pg-dev-up` resolves the newest installed major itself, so a future PG bump needs no path edit.
- The emitted `DATABASE_URL` always carries `?sslmode=disable` (appended at the single construction site in `print_url`, so `up`, `url`, and `url --export` agree). The cluster is initdb'ed without SSL, and Go's `lib/pq` does not fall back to plaintext when the DSN omits the parameter — it fails with `SSL is not enabled on the server` — so a Go integration suite pointed at the bare URL broke until someone appended it by hand (v1.12.0 briefly defaulted to libpq's `prefer`, which would have connected, but v1.12.1 reverted that; it is the sole exception across the v1.0.0–v1.12.3 release span, every other treating an omitted `sslmode` as `require`). Loopback-only + trust auth inside the container security boundary makes `disable` the honest description, not a weakening — and it is the one spelling every common client accepts, which is what makes the explicit form portable: `pgx` and libpq/psql default to `prefer` (attempt TLS, fall back to plaintext) and so connect either way, while node-postgres (`pg` 8.x) attempts no TLS by default and treats `prefer`/`require` as `verify-full` aliases (so those spellings fail against this cluster), but all three honor an explicit `disable`. Because the URL now carries a query string, a caller appending its own parameter must use `&`, not `?`. `%q` backslash-escapes the `?` in the `--export` form and `eval` strips it back, so the export round-trip is unaffected — `scripts/test-pg-dev-up-scoped.sh` asserts both the parameter and that round-trip on the scoped and default paths.
- An opt-in scoped mode (`pg-dev-up --worktree <cmd>`, or `--profile <id>` outside Git) lets parallel worktrees run database tests concurrently: it derives a per-worktree data dir under a private temp root (`POWBOX_PG_SCOPED_ROOT`, default `${TMPDIR:-/tmp}/pg-dev-up-scoped`) keyed by a truncated SHA-256 of `CONTAINER_NAME` + the repo common Git dir + worktree toplevel, and allocates a free loopback port under a `flock` on the scoped root — recorded next to the data dir so `status`/`url`/`down` resolve the exact server `up` started, and `down` never touches another instance (teardown needs only the recorded data dir, so `down` still works when a failed `up`'s rollback had to drop the port reservation). Explicit `PGDATA`/`PGPORT` stay authoritative — and, being authoritative, a scoped `up` refuses rather than silently adapting when the scope already runs a cluster that a new explicit `PGPORT` conflicts with or that a new `PGDATA` would orphan (stop it with the scoped `down` first); a plain scoped `up` (no explicit `PGDATA`) resumes the data dir the scope recorded — including a prior explicit one — so the restart recipe `down` advertises always brings back the same instance. `PGPORT` must be a bare 1-65535 integer and `POWBOX_PG_SCOPED_ROOT` is constrained to `A-Za-z0-9._/-`, since both are interpolated into the (shell-executed) `pg_ctl -o` postmaster options; read commands also verify the scoped root/markers are caller-owned and owner-only before trusting them. Plain `pg-dev-up up` (no flag) keeps the unscoped defaults — `/tmp/pgdata` on port `5432` — rather than deriving either.

## Bundled Go toolchain

- The base image installs Go at `/usr/local/go` from the official go.dev tarball (`docker/base/Dockerfile`), pinned with per-arch sha256s — Debian trixie's `golang` package trails upstream by several releases, and Go repos pin exact toolchains (`go.mod` `toolchain` lines, `.tool-versions`), so the apt version is never the one a project wants.
- `GOTOOLCHAIN` stays at its `auto` default: a repo pinning a newer toolchain than the baked one transparently downloads and runs it on first `go` invocation (toolchain pins are minimums), so projects keep working between image bumps instead of failing fast on a version mismatch.
- `golangci-lint` (v2, release tarball sha256-pinned per arch exactly like Go — no `curl | sh` installer) is baked beside it as the one lint binary Go projects pin — a v1 binary cannot parse v2 config schemas, and it bundles staticcheck/errcheck/ineffassign/unused internally, so no standalone Go linters are installed. Bump it together with the Go version when projects move.
- **Go caches persist across container recreation.** The in-container defaults (`GOMODCACHE` → `~/go/pkg/mod`, `GOCACHE` → `~/.cache/go-build`) sit outside every volume, so recreation used to cold-download all modules and rebuild everything. The launcher exports `GOMODCACHE=<workspace>/.worktrees/.gomodcache` and `GOCACHE=<workspace>/.worktrees/.gocache` — inside the per-container `agent-wt-*` volume (dir-mounted) or the one workspace volume (self-hosted) — and `entrypoint-core.sh` pre-creates the dirs guarded (warn + unset on failure so `go` falls back to its defaults). Plain env is all `go` needs; no `go env -w`. These two caches are deliberately **shared across a project's worktrees**: the module cache is content-addressed with its own locking and the build cache is designed for concurrent builds, so sharing is safe and is the point (warm caches everywhere). The **ccache** compiler cache (`ccache` baked in the base native-build apt layer) rides the exact same wiring — the launcher exports `CCACHE_DIR=<workspace>/.worktrees/.ccache` behind the same worktrees-volume gate and `entrypoint-core.sh` pre-creates it in the same guarded loop — because a content-addressed, lock-safe-under-concurrency compiler cache is the same shape of asset. It stays **opt-in per build**: only the binary and the persistent dir are baked, with **no** global `CC`/`CXX` export or masquerade-dir `PATH` prepend, so plain `gcc`/`cmake` builds are byte-for-byte unaffected — projects activate it explicitly with `CC="ccache gcc"` or `cmake -DCMAKE_C_COMPILER_LAUNCHER=ccache`. Silently interposing a cache into every build would surprise reproducibility-sensitive pinned builds and differs from how every other baked cache behaves (the tool consults it, nothing is injected). A C/CMake-only folder with none of the JS/powbox, root `go.mod`, or bounded .NET markers mounts no worktrees volume, so it gets no `CCACHE_DIR` and ccache falls back to its container-lifetime default — acceptable.
- **The volume gate is split for pure-Go and pure-.NET repos.** `go.mod` and the bounded .NET predicate are worktrees-volume-only launch triggers: a matching dir-mounted repo with no `package.json`/`pnpm-workspace.yaml`/committed `.powbox.yml`/`.powbox.local.yml` with a top-level `shadow:` key mounts `agent-wt-*` (language caches + worktrees) but **not** `agent-nm-*`, so no empty `node_modules/` mountpoint litters the host folder; a local config with only `ctx:` stays non-dev for this gate. The .NET predicate checks solution and project files (`*.sln`, `*.slnx`, `*.csproj`, `*.fsproj`, `*.vbproj`) at the root or exactly one directory below it with fixed-depth, non-symlink-following matching rather than a repository-wide scan. The launcher evaluates that predicate only when the cheaper JS/powbox and root `go.mod` checks did not already enable the worktrees volume. `PNPM_STORE_DIR` stays keyed to the JS/powbox gate (`MOUNT_WORKSPACE_VOLUMES`) — the pnpm wrapper's host-litter warning still fires for a stray root `pnpm install` there — while Go, NuGet, and ccache env key on the wider gate (`MOUNT_WORKTREES_VOLUME`). Both flags and the resolved NuGet path appear in `POWBOX_PRINT_IDENTITY` output and are pinned across JS-only, Go-only, .NET-only, deeper-than-bounded, non-dev, and self-hosted fixture shapes.
- **The golangci-lint analysis cache is scoped per worktree by a wrapper shim.** Unlike the Go caches, golangci-lint's per-HOME analysis cache (`~/.cache/golangci-lint`) bleeds results across parallel worktrees (phantom findings from a sibling's tree state). The pnpm-wrapper precedent applies: the real binary is extracted off `PATH` to `/usr/local/libexec/golangci-lint`, and `/usr/local/bin/golangci-lint` is a symlink to `golangci-lint-wrapper.sh`, which derives `GOLANGCI_LINT_CACHE` from `git rev-parse --show-toplevel` at invocation time — a worktree under `.worktrees/<container>/<slug>` gets `.worktrees/.golangci-cache/<container>/<slug>`, the main checkout gets the reserved `.worktrees/.golangci-cache/.root` (dot-prefixed so it can never collide with a worktree slug — `wt-enter` forbids leading dots) when `.worktrees` is a mountpoint or a self-hosted subdir, and anything else keeps the default. An explicit `GOLANGCI_LINT_CACHE` wins, and the wrapper always execs the real binary — a derivation failure can never block the lint. `wt-remove` (and `wt-bootstrap`'s orphan prune) delete a removed worktree's cache dir so nothing accumulates.
- `gopls` and `dlv` are deliberately not baked: the agent harnesses speak no LSP and debug via tests/prints. `/home/node/go/bin` (Go's default `GOBIN`) is on `PATH`, so a session that wants either — or any project codegen tool (protoc plugins, sqlc, mockery) — is one `go install` away. That holds in login shells too, which reset `PATH` from `/etc/profile`: a baked `/etc/profile.d/golang-gobin.sh` re-adds `$HOME/go/bin` there, and `go`/`gofmt` themselves are symlinked into `/usr/local/bin` (the smoke test's GOBIN probe guards this).
- Having the toolchain baked also makes `go mod tidy` the authoritative resolver for `go.sum` merge/rebase conflicts (it regenerates and validates checksums) rather than hand-merged unions of both sides.
- **Upgrading an existing install:** the toolchain lives in the **base** layer, so an agent-layer rebuild (`cc --build`, or `agent-update` when just a binary is stale) would otherwise land a new agent on an old base with no `go`/`golangci-lint`. This is now caught automatically: the base image stamps a digest over its own build inputs (`powbox.base.recipe.digest`; see `scripts/base-source-files.txt`), and `agent-check-updates` flags the base **stale** whenever a base-layer source file changed — e.g. a Go/`golangci-lint` bump in the base Dockerfile — so `agent-update` offers the full base + agent rebuild with no manual step, while editing only an agent-layer file does not trigger it. A first-time build is unaffected. See the README [Upgrading an existing install needs a base-image rebuild](../README.md#upgrading-an-existing-install-needs-a-base-image-rebuild) for the full mechanism.

## Bundled .NET SDK

- The base image installs `dotnet-sdk-8.0` from the Microsoft apt repo (`docker/base/Dockerfile`), so a session touching a C#/F# project can run the same `dotnet build` / `dotnet test` its CI does instead of discovering a compile error only after pushing. No new apt source was needed: the `packages-microsoft-prod` repo and its rotated trixie keyring are already configured much earlier in the file for `pwsh` and `mssql-tools18`, and they carry the SDK packages too.
- **Pinned to the major.minor band only**, following the `postgresql-16` / `mssql-tools18` precedent rather than the sha256-pinned tarball treatment Go and OPA get — this is a signed distro repo, not a GitHub release asset. 8.0 is the LTS band projects pin in CI (`actions/setup-dotnet` with `8.0.4xx`) and the apt candidate resolves inside that band, so a local run and a CI run agree on the SDK feature band.
- **One SDK is baked, deliberately.** Each is roughly 575 MB, the single largest tool addition in the image (Go is ~250 MB). Because the Microsoft repo is already wired, a project needing a different band is one `sudo apt-get update && sudo apt-get install -y dotnet-sdk-N.0` away in-session — the same escape hatch `GOTOOLCHAIN=auto` gives Go projects, minus the automation. The `update` is required, not decorative: the SDK layer ends by clearing `/var/lib/apt/lists` and no later layer repopulates it, so a bare `apt-get install` in a fresh container reports "Unable to locate package" despite the source being configured.
- **No companion packages.** `dotnet build`, `dotnet test`, `dotnet format`, `dotnet nuget`, and `dotnet new` all ship inside the SDK, so there is no `golangci-lint`-shaped second install; `dotnet-sdk-8.0` also pulls its own runtime, the ASP.NET runtime, and the targeting/apphost packs, so `dotnet test -f net8.0` works with nothing else present. Targeting .NET Framework (`net48`) from Linux needs nothing extra either — a project references the `Microsoft.NETFramework.ReferenceAssemblies` NuGet package and compiles against reference assemblies, with no targeting pack and no Mono. (Executing `net48` **test binaries** still needs Windows or Mono; the usual pattern is to multi-target and run the modern TFM on Linux.)
- **Four env opt-outs keep build output parseable**, each set for an effect observed on a real first build in a fresh container: `DOTNET_CLI_TELEMETRY_OPTOUT=1`, `DOTNET_NOLOGO=1` (drops the multi-line first-run banner), `DOTNET_GENERATE_ASPNET_CERTIFICATE=false` (the CLI otherwise *silently* generates and installs an ASP.NET Core HTTPS dev certificate on first run — pure surprise state in a headless container), and `DOTNET_CLI_WORKLOAD_UPDATE_NOTIFY_DISABLE=1`. `DOTNET_SKIP_FIRST_TIME_EXPERIENCE` is deliberately **not** set: it has been a no-op since .NET 5. Stage 1 of the smoke test asserts all four values, so silently dropping one from the image is caught. That probe — like the sentinel one below — is a multi-clause `&&` chain, and every one of its clauses is binding because `scripts/smoke-test-image.{sh,ps1}` never put probe text into a script at all: the probes are handed to the container as **positional arguments**, and a fixed one-line runner — `i=0; for p in "$@"; do i=$((i + 1)); sh -ec "$p" || { printf "%s\n" "SMOKE PROBE $i FAILED" >&2; exit 1; }; done` — executes each probe in its own `sh -ec` and reports failures by index. Two properties follow structurally rather than by careful escaping. Probe text is data, so no probe's *text* can reach the runner's syntax, a neighbouring probe's syntax, or the failure message — no quote, comment, backtick or backslash has anything to reach. That is about probe *text*, not probe *output*: a probe can still *print* a line that mimics the diagnostic (`printf "%s\n" "SMOKE PROBE 99 FAILED" >&2; true` puts exactly that in the run output while the run exits 0), but it cannot make the runner emit one or change the verdict, which follows from the exit status alone (runtime effects are separate too: filesystem state still carries between probes, by design). And a probe fails the run exactly when its own shell exits non-zero, which nothing discards any more. The precise mechanism matters, because it is the rule probe authors write against, so it is worth stating as a general rule rather than a list of shapes. POSIX (XCU 2.14) *exempts* a failing command in several positions — a non-final member of an `&&`/`||` list, a `!`-negated pipeline, and the condition of an `if`/`elif`/`while`/`until` — and the probe being the shell's whole input does not change that (`sh -ec 'false && echo x; true'` and `sh -ec '! true; true'` both exit 0). What the exemption turns on is *position*: an exempt construct is **binding** when it is the probe's *last* command, because its own status then becomes the probe shell's exit status and the runner's `||` guard observes it, and **unenforced** when anything follows it, which overwrites that status. ("Its own status" stays POSIX: `! X` inverts, and an `if` whose condition is false with no `else` is 0 by definition, as is a `while`/`until` whose body never runs, so an `if`/`while`/`until` condition never fails a probe in either position.) Nothing outside that exempt set is suspended at all — a failing member of a *bare* `;` sequence or of a `{ …; }` group aborts the probe shell at that member; "bare" is load-bearing there, because a `{ …; }` group in a non-final `&&`/`||` position inherits the exemption throughout (`{ false; echo X; } && true` exits 0 and still prints `X`). So the `&&`-chain and pipeline shapes the probes actually use are binding; a pipeline reports its *last* command's status, and producer-side masking inside one is a separate matter (see the pipefail note below). This replaced two earlier forms, and the intermediate one is why the argv form exists. Joined the original way — every probe a bare line of one `set -e` script — the same exemption applied, but nothing caught the status it left behind, so the non-final `&&`/`||` members of any probe — and the overall status of every probe but the last, which nothing followed to discard — were masked (a failing *final* clause did trip `set -e` even then). Bare `;` sequences and `{ …; }` groups were already enforced under that join, so `;` enforcement is not something this change restored. Wrapping each probe as the condition of its own `if`, with an index-only failure guard on the following line, made a probe's overall status binding but kept the probe inside the aggregate script's syntax, which cost two things: an `if` condition *also* suspends `set -e`, so the non-final members of a `;` sequence went from enforced to unenforced — a genuine narrowing, not an inherited hole — and two probes with unbalanced quotes still re-balanced each other across the join, swallowing the first probe's guard *and* its assertion and turning a failure into a pass (measured on the triple `[ -n "" ] "` / `" ; true` / `true`: the bare-line join aborted at rc=2, the `if` join exited 0, the argv form fails and names probe 1). Both are closed. The two .NET probes originally carried a hand-rolled `|| { …; exit 1; }` tail (PR #120); the central driver fix (`tasks/002d-smoke-probe-set-e-masking-central-fix.md`) generalized it to the whole list and the hand-rolled tails were dropped as redundant — at the cost of the runtime values those tails used to print, since the central diagnostic carries only an index. The driver prints an index → probe manifest when a run fails, so a red Stage 1 no longer has to be bisected by hand. Consequences for probe authors: no per-probe `|| { …; exit 1; }` tail; every probe must be **self-contained**, because each runs in its own shell and `cd`, `export` and plain variables do not carry to the next probe (only filesystem effects do — that is how the golangci fixture probe hands the three probes after it a worktree); probes must stay single-line and must not end in a line continuation, which the driver still rejects — now for diagnosability rather than safety, since the manifest prints one line per probe, the `.ps1` mirror would otherwise hand `docker` a multi-line native-command argument, and `sh -ec` silently runs a dangling-continuation probe *truncated* and passes; and some shapes remain unenforceable, all shared with the original join rather than introduced here — stated as one rule rather than a count, so it cannot go stale the next time another instance turns up: any `set -e`-exempt construct that is not the probe's *last* command is unenforced, because the command after it overwrites the status (`A && B; C` and `! X; Y` are the instances), plus one that is not about `set -e` at all — a probe ending in `&`, whose async status POSIX fixes at 0. No shipped probe uses any of them, and section L of `scripts/test-smoke-probe-wrapper.sh` pins each with a characterization check rather than leaving it to an audit. Quote balance is no longer a cross-probe hazard: an unbalanced quote fails that probe's own shell with a syntax error, named by its index. The container shell remains a login shell (`sh -lc`), so `/etc/profile.d` runs once and every probe's shell inherits the resulting `PATH` — which is what the `$HOME/go/bin` GOBIN probe proves. `set -o pipefail` is deliberately **not** enabled — it is not POSIX, and it would make every `X | grep -q Y` probe sensitive to its producer's status including the SIGPIPE `grep -q` provokes, an exposure that scales with how much the producer emits and could therefore flip a probe from green to 141 with no code change — so producer-side masking inside such a probe is unchanged; `scripts/test-smoke-probe-wrapper.sh` unit-tests the runner, its injection-proofness against adversarial probe text (including the comment-consumption case), the per-probe shell isolation, the closed holes with pre-fix controls, and `.sh`/`.ps1` parity — argv, rejection, the *rendering* of each rejection message (a newline or CR echoed back escaped so the diagnostic stays one line, a trailing backslash run left byte-exact so it does not contradict the message about it), and what the two drivers call an *empty* probe: the `.ps1`'s `[string]::IsNullOrWhiteSpace()` is Unicode-aware while `[[:space:]]` in the `.sh` matches only the ASCII whitespace bytes under the C locale, so a probe of nothing but U+00A0 was once refused by one driver and run by the other, and the `.sh` now strips the non-ASCII Unicode `White_Space` code points from an explicit list to close that.
- **The first-use sentinels are pre-created at build time** so the very first `dotnet build` in a container is silent. Without them it prints `An issue was encountered verifying workloads`, which is unactionable here — workload manifests live under the root-owned `/usr/share/dotnet`, `node` cannot write them (`dotnet workload update` answers "Inadequate permissions"), and that is the permanent intended state of the image. The warning is emitted once per HOME per SDK version and then self-silences, so an agent's first build was exactly the one that got the noise. Two empty marker files under `/home/node/.dotnet` suppress it; the version is derived from `dotnet --version` at build time, so an SDK bump needs no edit. Warming it by running a throwaway `dotnet new` + build was rejected — that pulls NuGet packages into the image for no benefit. The step runs after `USER node` because the sentinels are per-HOME, and `/home/node` is image content (only `.claude` / `.config/gh` are volumes), so they persist into every container. Because `$(...)` strips only trailing newlines, the `RUN` validates that the derived value is one well-formed version token before it `touch`es anything — a `dotnet --version` that ever grew a second stdout line would otherwise create a newline-bearing garbage filename that suppresses nothing while the build still succeeds, so it now fails the build loudly instead. Stage 1 of the smoke test re-derives the version the same way and applies the same guard before asserting that both marker files exist, that they are owned by the runtime user, and that `$HOME/.dotnet` is writable by it — which pins that the warm-up ran, that it ran **as `node`** into the HOME the container actually uses, and that the build-time and runtime versions agree, so a stale cached sentinel layer against a bumped SDK fails there. The ownership and writability clauses are not padding: the `RUN` `touch`es the absolute `/home/node/.dotnet` path, so moving it above `USER node` would still leave both files exactly where a bare existence check looks — just root-owned, in a dir `node` cannot write. Re-deriving alone would be a tautology (both sides build the same string from the same command), which is why the well-formedness guard, not the filename comparison, is what catches the garbage case.
- **NuGet packages persist across container recreation.** The launcher exports `NUGET_PACKAGES=<workspace>/.worktrees/.nuget` behind the wider worktrees-volume gate, and `entrypoint-core.sh` pre-creates it in the same guarded warn-and-unset-on-failure loop as the Go and ccache dirs. This overrides the default `~/.nuget/packages`, which sits outside every volume, while deliberately leaving the separate NuGet HTTP and plugin caches at their defaults. The global packages folder is shared across a project's worktrees on purpose: NuGet keys extracted packages by ID and version, writes `.nupkg.metadata` only after successful extraction, and coordinates concurrent client access with filesystem locks through the shared NuGet scratch directory; Microsoft's [global packages and cache documentation](https://learn.microsoft.com/en-us/nuget/consume-packages/managing-the-global-packages-and-cache-folders) explicitly describes cross-project reuse and concurrent-process coordination. Sharing avoids duplicate restores, while the per-container `agent-wt-*` boundary still prevents two outer agent containers from writing the same cache. `NUGET_PACKAGES` takes precedence over repo `globalPackagesFolder` configuration, intentionally giving every launched project the persistent location. Because container environment is frozen at creation, normal reuse compares the existing value case-sensitively after trimming redundant trailing slashes before attaching or starting: a stopped stale container is recreated and a running one is left intact with a stop-and-relaunch warning, including self-hosted containers and dir-mounted containers whose volume mounts already match. Explicit `--resume`/`-Resume` intentionally bypasses all frozen mount/environment migrations and now warns that the persistent NuGet wiring is left unchanged. Stage 1 pins that the SDK honors this plain environment override with an offline `dotnet nuget locals global-packages --list` probe; the launcher smoke separately pins the resolved path and migration behavior.
- **Upgrading an existing install:** the SDK lives in the **base** layer, so the same rule as the Go toolchain applies — an agent-layer rebuild alone would land a new agent on a base with no `dotnet`. The `powbox.base.recipe.digest` staleness check covers this automatically, since `docker/base/Dockerfile` is a base-layer source file.
