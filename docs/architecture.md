# Architecture and runtime internals

Agent-facing reference for how the powbox image, identity, volumes, and bundled services fit together.
This is the detail that does not need to sit in every task's context — [AGENTS.md](../AGENTS.md) keeps only the always-on directives and routes here.
Container startup (the entrypoint chain, hooks, ordering, permission healing, shadow mounts) lives in a sibling chapter: [entrypoint-and-runtime.md](entrypoint-and-runtime.md).
For the deeper design specs, follow the cross-links at each section.

## Rules the file map does not state

See the README [Layout](../README.md#layout) for the repo file map. Rules that map does not state:

- There is one unified agent image `powbox-agent:latest` (`docker/agent/Dockerfile`) built on `powbox-agent-base:latest`. It installs both agent binaries — Codex below Claude so a Claude version bump (the common case) busts only the Claude layer plus the cheap asset/entrypoint layers above it; a Codex bump rebuilds the Claude layer on top too (accepted). The old per-agent images (`powbox-claude`, `powbox-codex`) and Dockerfiles are gone. See [unified-agent-image.md](unified-agent-image.md) for the full spec and migration order.
- Each agent's image-baked seed assets live under a per-agent directory `/home/node/.agent-container/<agent>` (e.g. `docker/claude/agent-container/` → `/home/node/.agent-container/claude/`), read by that agent's hook via the `AGENT_SEED_DIR` variable so the two agents' templates, skills, statusline, and build epoch never collide.
- Image-baked skills are seeded into each agent's user-level skills directory at startup (`$CLAUDE_CONFIG_DIR/skills/` for Claude, `~/.agents/skills/` for Codex), no-clobber at the skill-directory level; a per-repo `.claude/skills/` (or `.agents/skills/`) still takes precedence at invoke time. The copy logic and the `.powbox-seeded` ownership marker live in one baked helper `docker/shared/seed-skills.sh` (`/usr/local/bin/seed-skills.sh`), sourced by both entrypoint hooks (`seed_skills … noclobber`) and the updater, so the sites cannot drift. The marker means "powbox owns this copy": a marked skill may be refreshed/pruned, an unmarked folder is treated as user-authored and never touched.
- Skill custody is split (task 015). The bake+seed path above carries the **full Codex palette** (the 8 shared dev-workflow skills, fetched from `Roubtec/agent-skills` at build time, plus the powbox-specific Codex skills) and the **powbox-specific Claude skills** (`enable-worktrees`, `session-learnings`) only. The 8 shared Claude skills are **not** baked/seeded for Claude — they arrive through the `dev-skills@roubtec` marketplace plugin instead (namespaced `/dev-skills:<name>`; see the Claude plugin-channel bullet in [entrypoint-and-runtime.md](entrypoint-and-runtime.md) and README "Agent Skills"). So `update-skills.*` manages the bake+seed channel, and on a `claude-config` volume seeded before 015b it classifies those 8 as prunable orphans (marked, no longer baked for Claude).
- Because of the no-clobber, a rebuilt image's updated skill text does not replace the stale volume copies; `commands/update-skills.*` (function `agent-update-skills`) force-refreshes the baked skills onto both config volumes via a throwaway container, running the shared in-container worker `docker/shared/update-skills-incontainer.sh` (a classify/apply engine over the same `seed-skills.sh`). It seeds absent skills, refreshes marked ones, reports unmarked name-collisions as conflicts (overwritten only with `--adopt-all`), and reports marked skills no longer baked as obsolete (deleted only with `--prune`); `--dry-run` previews. On a TTY it prompts before adopting/pruning, and `agent-update` offers to run it after a successful rebuild. The `.powbox-seeded` marker records the image build epoch and the powbox commit baked via the `POWBOX_COMMIT` build-arg (`scripts/build-image.{sh,ps1}` → `docker-bake.hcl` → Dockerfile, next to `build-epoch`). User-authored skills (no marker) are left untouched.
- Claude-only dynamic workflows live under `docker/claude/agent-container/workflows/*.js` (no Codex sibling — Codex has no workflow runtime) and are seeded by `entrypoint-claude-hook.sh` into `$CLAUDE_CONFIG_DIR/workflows/` via `seed_workflows` in the shared `seed-skills.sh` (no-clobber at startup). A workflow is a single `.js` file with no "inside", so its `.powbox-seeded` ownership marker is a hidden sibling sidecar `.<name>.js.powbox-seeded` rather than an in-folder file; otherwise it mirrors skills exactly, so `update-skills-incontainer.sh` classifies / refreshes / adopts / prunes workflows as `workflow` items just like skills. They ship automatically because the Dockerfile copies the whole `docker/claude/agent-container/` tree. This is a testing batch (see that dir's README) reimagining the orchestration-heavy skills as workflows; they deliberately avoid the runtime's built-in `isolation: "worktree"` (it cannot honor the `.worktrees/$CONTAINER_NAME/<slug>` convention) — `wf-address-tasks` manages explicit convention worktrees, `wf-address-review` shares the one checkout — and the skills remain in place alongside them.
- The mechanical worktree lifecycle is encoded once, as three scripts (`docker/shared/wt-bootstrap`, `wt-enter`, `wt-remove` → `/usr/local/bin/`) shared by both agents' worktree-running skills and the Claude workflows: the workflows own control flow (waves, round caps, gating) as real code, agents own judgment, and the scripts own the git/worktree plumbing (root-safety checks, container-scoped orphan pruning, rerun-safe worktree resolve, guarded removal). Skill prose and workflow prompts must call these helpers rather than restate the plumbing — that split is what keeps the three layers from drifting. Like the entrypoint and per-agent hooks, these helpers are baked by the **agent** image, not the base, because they evolve in lockstep with the agent-layer assets that consume them — so editing one is picked up by the ordinary `agent-update` / `build.sh agent` rebuild (which reuses an existing base unless `--pull`) without forcing a base rebuild. The same agent layer bakes the other single-purpose helpers the skills and workflows call, for the same lockstep reason: `docker/shared/gitcat` (a cross-branch file reader with stable line numbers, for reading across a stacked-PR chain from one checkout) and `docker/shared/gh-review-threads` (a safe PR review-thread fetcher — manual pagination, never `gh api graphql --paginate`, with a repo-qualified, boundary-safe PR-scope assertion that fails closed on a contaminated response — used by both agents' `address-review` skills and the `wf-address-review` workflow). Add a new such helper here, not in the base, whenever it is consumed by an agent-layer skill or workflow.
- Image provenance: each image records the powbox commit that built it. A piecemeal build can carry up to three distinct commits — base (its own parent), codex, and claude/top — so they are tracked separately. Host-side: labels `powbox.commit.{base,codex,claude}` (+ `powbox.{codex,claude}.version` and `powbox.base.image.id`), surfaced by the `agent-image-info` shell function and in `agent-update` output. In-container: files `/home/node/.powbox/{base,codex,claude}.commit` (base inherited from the base image), printed by the baked `powbox-provenance` command. The codex commit is computed in `scripts/build-image.{sh,ps1}` (HEAD when the Codex layer rebuilds, else the prior image's value carried forward) and stamped only in the top metadata layer — never inside the Codex install layer, which would bust its cache. Reuse is judged against that layer's cache key — its parent base image (`powbox.base.image.id`) and `CODEX_VERSION` (`powbox.codex.version`) — so a separate base rebuild correctly re-stamps codex at HEAD; see [skills-refresh-and-provenance.md](skills-refresh-and-provenance.md) for the residual pre-build-prediction limitation. `-dirty` marks an uncommitted worktree. Introspection only; no logic depends on these values.
- Entrypoint scripts all live in `docker/shared/`, but only `entrypoint-core.sh` is baked by the base image. The unified entrypoint `entrypoint-agent.sh` and both per-agent hooks (`entrypoint-{claude,codex}-hook.sh`) are baked by the agent image, so editing the entrypoint or a hook only requires rebuilding the agent image — not the base. The old per-agent entrypoint shims (`entrypoint-{claude,codex}.sh`) are gone, replaced by `entrypoint-agent.sh` plus its in-script agent registry.
- After cutover the obsolete `powbox-claude` / `powbox-codex` images can be removed with `docker image rm powbox-claude powbox-codex` — non-destructive to the `claude-config` / `codex-config` volumes.

## Project Identity

There are two launch modes; the launchers (`scripts/launch-agent.{sh,ps1}`) branch the identity block on `--isolated` and dir-mounted is the default.

- **Dir-mounted (default, unchanged):** per-project identity uses `basename + SHA256(full path)` (truncated to 12 chars) so container names and `node_modules` volumes do not collide across similarly named projects. The host working dir is bind-mounted; this path-based identity is the contract and must not be altered.
- **Self-hosted (`--isolated`):** the container clones the repo into a private per-instance volume instead of bind-mounting the host (see README "Self-Hosted Mode"). Identity is `<repo-slug>[-<name-slug>] + SHA256(label-or-timestamp)[:12]` — the same 12-char hash shape — where the discriminator is `--name <label>` (deterministic → reusable: same clone + session history across launches) or, unnamed, a high-resolution timestamp (fresh every launch). The optional `<name-slug>` is a sanitised, capped rendering of `--name` woven into the name for human/`cc-list` legibility only; the **raw** `--name` (folded into the hash, and stored verbatim in the `powbox.instance-name` label) owns identity, so two names that slugify alike stay distinct. `--ref` is excluded from the hash (volatile). The repo is a required input (positional or `--repo`); when omitted inside a git repo it is inferred from `git remote get-url origin`. Self-hosted containers also carry `powbox.repo` / `powbox.ref` labels for the lists. All self-hosted logic is gated behind `--isolated` so the dir-mounted path is byte-for-byte unchanged.

## Volumes and Stores

See README "Workspace Shadow Mounts" and "Runtime" for volume behavior. The non-obvious constraint: pnpm can only **hardlink** from its store when the store and the target `node_modules` share **one mount** (not merely one device — `link(2)` returns `EXDEV` across mount points even on the same filesystem). So the per-container pnpm store lives *inside* the `.worktrees` volume (`agent-wt-<agent>-<project>`) alongside every `.worktrees/<task>/node_modules`, and `package-import-method=auto` lets pnpm hardlink there and transparently fall back to copying for the root `node_modules` (a separate mount). The launcher passes `PNPM_STORE_DIR` and `entrypoint-core.sh` points pnpm at it per project.

Context mounts are host-side launch concerns, not container startup behavior. The launchers derive a context mount set from CLI `--ctx` / `-Ctx` or effective `ctx:` config in `.powbox.yml` / `.powbox.local.yml`, mount each source under `/ctx/<name>` through a generated compose overlay attached only to the final agent run, and record the canonical derived set as the `powbox.ctx-hash` container label so stopped containers recreate when the set changes. With no CLI ctx and no effective `ctx:` key, the launcher deliberately skips that comparison and preserves any existing context mounts.

The same `.worktrees` volume also persists the Go caches (`.gomodcache`, `.gocache`, and the per-worktree `.golangci-cache/…`) via launcher-exported `GOMODCACHE`/`GOCACHE` env and the golangci-lint wrapper, plus the opt-in ccache compiler cache (`.ccache`, launcher-exported `CCACHE_DIR`) — see "Bundled Go toolchain" below for locations, the split volume gate that also triggers on `go.mod`, and the sharing-vs-isolation split.

In **self-hosted (`--isolated`)** mode this three-mount layout collapses to **one**: a single per-instance `agent-ws-<container>` volume mounted at `/workspace/<slug>` holds the clone plus `node_modules`, `.worktrees`, and the pnpm store, Go caches, and ccache as ordinary subdirs. The dir-mounted `agent-nm-*` / `agent-wt-*` shadow volumes are omitted (no host FS underneath to shadow), the workspace bind mount is replaced via `compose.selfhosted.yml` (merged by target path, mirroring the fuse/netdev overlays), and `shadow-mounts.sh` is skipped entirely in `entrypoint-core.sh`. Because everything shares one mount, pnpm hardlinks everywhere — including the root `node_modules`, which falls back to copying in dir-mounted mode. The `agent-ws-*` and per-container `agent-podman-*` volumes are keyed by the full container name (part of the container identity); prune tooling (`commands/prune-volumes.*`) GCs orphaned `agent-ws-*` volumes alongside the others.

Deep dive (measured rationale, the copy→hardlink decision, validation): [worktree-node-modules-hardlinks.md](worktree-node-modules-hardlinks.md).

## Bundled PostgreSQL

- The base image installs the PostgreSQL 16 server + client + contrib from the official PGDG apt repo (`docker/base/Dockerfile`), version-matched to the `postgres:16.x` images projects pin so integration suites don't hit behavior drift from Debian's stock 15.
- No daemon is started at build or runtime. `docker/shared/pg-dev-up` (baked to `/usr/local/bin/pg-dev-up`) stands up a throwaway loopback cluster on demand under `$PGDATA` (default `/tmp/pgdata`), as the unprivileged `node` user with trust auth — so it needs **no** sudoers entry. Credentials/port/db are env-overridable; see the script header.
- The server binaries live off `PATH` at `/usr/lib/postgresql/<major>/bin`; `pg-dev-up` resolves the newest installed major itself, so a future PG bump needs no path edit.

## Bundled Go toolchain

- The base image installs Go at `/usr/local/go` from the official go.dev tarball (`docker/base/Dockerfile`), pinned with per-arch sha256s — Debian trixie's `golang` package trails upstream by several releases, and Go repos pin exact toolchains (`go.mod` `toolchain` lines, `.tool-versions`), so the apt version is never the one a project wants.
- `GOTOOLCHAIN` stays at its `auto` default: a repo pinning a newer toolchain than the baked one transparently downloads and runs it on first `go` invocation (toolchain pins are minimums), so projects keep working between image bumps instead of failing fast on a version mismatch.
- `golangci-lint` (v2, release tarball sha256-pinned per arch exactly like Go — no `curl | sh` installer) is baked beside it as the one lint binary Go projects pin — a v1 binary cannot parse v2 config schemas, and it bundles staticcheck/errcheck/ineffassign/unused internally, so no standalone Go linters are installed. Bump it together with the Go version when projects move.
- **Go caches persist across container recreation.** The in-container defaults (`GOMODCACHE` → `~/go/pkg/mod`, `GOCACHE` → `~/.cache/go-build`) sit outside every volume, so recreation used to cold-download all modules and rebuild everything. The launcher exports `GOMODCACHE=<workspace>/.worktrees/.gomodcache` and `GOCACHE=<workspace>/.worktrees/.gocache` — inside the per-container `agent-wt-*` volume (dir-mounted) or the one workspace volume (self-hosted) — and `entrypoint-core.sh` pre-creates the dirs guarded (warn + unset on failure so `go` falls back to its defaults). Plain env is all `go` needs; no `go env -w`. These two caches are deliberately **shared across a project's worktrees**: the module cache is content-addressed with its own locking and the build cache is designed for concurrent builds, so sharing is safe and is the point (warm caches everywhere). The **ccache** compiler cache (`ccache` baked in the base native-build apt layer) rides the exact same wiring — the launcher exports `CCACHE_DIR=<workspace>/.worktrees/.ccache` behind the same worktrees-volume gate and `entrypoint-core.sh` pre-creates it in the same guarded loop — because a content-addressed, lock-safe-under-concurrency compiler cache is the same shape of asset. It stays **opt-in per build**: only the binary and the persistent dir are baked, with **no** global `CC`/`CXX` export or masquerade-dir `PATH` prepend, so plain `gcc`/`cmake` builds are byte-for-byte unaffected — projects activate it explicitly with `CC="ccache gcc"` or `cmake -DCMAKE_C_COMPILER_LAUNCHER=ccache`. Silently interposing a cache into every build would surprise reproducibility-sensitive pinned builds and differs from how every other baked cache behaves (the tool consults it, nothing is injected). A C/CMake-only folder with no `package.json`/`go.mod` mounts no worktrees volume, so it gets no `CCACHE_DIR` and ccache falls back to its container-lifetime default — acceptable.
- **The volume gate is split for pure-Go repos.** `go.mod` is a second, worktrees-volume-only launch trigger: a dir-mounted repo with `go.mod` but no `package.json`/`pnpm-workspace.yaml`/committed `.powbox.yml`/`.powbox.local.yml` with a top-level `shadow:` key mounts `agent-wt-*` (Go caches + worktrees) but **not** `agent-nm-*`, so no empty `node_modules/` mountpoint litters the host folder; a local config with only `ctx:` stays non-dev for this gate. `PNPM_STORE_DIR` stays keyed to the JS/powbox gate (`MOUNT_WORKSPACE_VOLUMES`) — the pnpm wrapper's host-litter warning still fires for a stray root `pnpm install` there — while the Go cache env keys on the wider gate (`MOUNT_WORKTREES_VOLUME`). Both flags appear in the `POWBOX_PRINT_IDENTITY` output and are pinned by the self-hosted smoke's four-shape fixture matrix.
- **The golangci-lint analysis cache is scoped per worktree by a wrapper shim.** Unlike the Go caches, golangci-lint's per-HOME analysis cache (`~/.cache/golangci-lint`) bleeds results across parallel worktrees (phantom findings from a sibling's tree state). The pnpm-wrapper precedent applies: the real binary is extracted off `PATH` to `/usr/local/libexec/golangci-lint`, and `/usr/local/bin/golangci-lint` is a symlink to `golangci-lint-wrapper.sh`, which derives `GOLANGCI_LINT_CACHE` from `git rev-parse --show-toplevel` at invocation time — a worktree under `.worktrees/<container>/<slug>` gets `.worktrees/.golangci-cache/<container>/<slug>`, the main checkout gets the reserved `.worktrees/.golangci-cache/.root` (dot-prefixed so it can never collide with a worktree slug — `wt-enter` forbids leading dots) when `.worktrees` is a mountpoint or a self-hosted subdir, and anything else keeps the default. An explicit `GOLANGCI_LINT_CACHE` wins, and the wrapper always execs the real binary — a derivation failure can never block the lint. `wt-remove` (and `wt-bootstrap`'s orphan prune) delete a removed worktree's cache dir so nothing accumulates.
- `gopls` and `dlv` are deliberately not baked: the agent harnesses speak no LSP and debug via tests/prints. `/home/node/go/bin` (Go's default `GOBIN`) is on `PATH`, so a session that wants either — or any project codegen tool (protoc plugins, sqlc, mockery) — is one `go install` away. That holds in login shells too, which reset `PATH` from `/etc/profile`: a baked `/etc/profile.d/golang-gobin.sh` re-adds `$HOME/go/bin` there, and `go`/`gofmt` themselves are symlinked into `/usr/local/bin` (the smoke test's GOBIN probe guards this).
- Having the toolchain baked also makes `go mod tidy` the authoritative resolver for `go.sum` merge/rebase conflicts (it regenerates and validates checksums) rather than hand-merged unions of both sides.
- **Upgrading an existing install:** the toolchain lives in the **base** layer, so an agent-layer rebuild (`cc --build`, or `agent-update` when just a binary is stale) would otherwise land a new agent on an old base with no `go`/`golangci-lint`. This is now caught automatically: the base image stamps a digest over its own build inputs (`powbox.base.recipe.digest`; see `scripts/base-source-files.txt`), and `agent-check-updates` flags the base **stale** whenever a base-layer source file changed — e.g. a Go/`golangci-lint` bump in the base Dockerfile — so `agent-update` offers the full base + agent rebuild with no manual step, while editing only an agent-layer file does not trigger it. A first-time build is unaffected. See the README [Upgrading an existing install needs a base-image rebuild](../README.md#upgrading-an-existing-install-needs-a-base-image-rebuild) for the full mechanism.
