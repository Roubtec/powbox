# Entrypoint and runtime internals

Agent-facing reference for container startup: the entrypoint chain, the per-agent seeding hooks, the ordering constraints between them, host-workspace permission healing, the mid-session pnpm/shadow wrapper, and the deliberate bash/zsh split.
Routed from [AGENTS.md](../AGENTS.md); see [architecture.md](architecture.md) for the image/identity/volume picture this startup sequence sits inside.

## Entrypoint and Runtime

- `entrypoint-agent.sh` is the image ENTRYPOINT. It reads `PRIMARY_AGENT` (`claude` | `codex`, defaulting to `claude` for an unknown value), holds the agent registry (`agent_env` maps each agent to its `AGENT_CONFIG_DIR`, `AGENT_SETUP_HOOK`, `AGENT_SEED_DIR`, name, binary, autonomy flag, instruction file, label, and one-shot invocation fragment `AGENT_ONESHOT` — the non-interactive form rendered under the peer's bullet in the instruction file), then seeds every agent and execs `entrypoint-core.sh` for the primary. Adding a harness = extend `agent_env` and `ALL_AGENTS`.
- It seeds in two passes: each non-primary agent is seeded directly (export its `AGENT_*` vars, run its hook); the primary agent's env is exported and handed to `entrypoint-core.sh`, which runs the primary's hook (so it is not run twice) alongside firewall/git/shadow setup before execing the CMD.
- Each per-agent hook (`entrypoint-claude-hook.sh`, `entrypoint-codex-hook.sh`) is run in full for every agent. Each writes only into its own config dir (`~/.claude` vs `~/.codex`/`~/.agents`), so there is no conflict; hooks are idempotent, build-epoch-gated, and read their baked assets from `AGENT_SEED_DIR`.
Seeding is no-clobber by default — an asset already on the volume is left alone — with the two documented exceptions below: the instruction file and the `statusLine` settings key are re-asserted on every epoch bump, and the Claude statusline script is refreshed on an epoch bump only while it is provably still powbox's own copy.
- `entrypoint-core.sh` is a wrapper-style entrypoint that must end with `exec "$@"` and is unchanged by the unification (still runs the single `AGENT_SETUP_HOOK`).
- The shared instruction template is rendered via `envsubst` with agent-specific variables (including `${AGENT_PEERS}`, the registry-derived peer list for the "Delegating to another agent" section).
- **Claude statusline seeding (`entrypoint-claude-hook.sh`, task 002e).** The statusline script used to be seeded pure no-clobber, which left it frozen at whatever the volume was first created with while the `statusLine` key in `settings.json` that points at it refreshed on every rebuild — so every later fix to the script was silently unreachable. It is now refreshed on a newer `build-epoch`, but only when powbox can *prove* the on-disk copy is still its own: `seed_statusline` writes a sidecar marker `~/.claude/.statusline-command.sh.powbox-seeded` holding `epoch=`, `commit=`, `sha256=` (of exactly the bytes written) and `source=`, and a refresh requires the file's current digest to equal the recorded one. A running container has no copy of the previous image's file, so the digest is the only proof available. Three outcomes: no file → seed and mark; marked and unchanged on a newer epoch → replace and re-mark; marked-but-edited, or **unmarked** (every `claude-config` volume predating the marker — powbox cannot prove it was not customized) → keep the file. An edited file gets one stderr note per *new image*, tracked by a separate `notified_epoch=` key so `epoch=` keeps meaning "the build that placed this file"; deleting the statusline re-seeds it and adopts the marker, so the next rebuild refreshes it automatically. The marker follows the `.powbox-seeded` convention `seed-skills.sh` established for skills/workflows (sidecar name shape, `key=value` body, parse-by-key) but is written inline rather than by sourcing that library — see [skills-refresh-and-provenance.md](skills-refresh-and-provenance.md) → D9. The image epoch is read once above both epoch-gated steps; the statusline compares it against its own marker while the instruction file compares against `.instruction-epoch` and stamps only that, so neither decision can gate the other in either direction. Every failure inside this block resolves the same way — keep what is on disk and carry on — because `entrypoint-core.sh` invokes the hook UNGUARDED and the hook runs under `set -euo pipefail`, so a status escaping here would end container startup and take the instruction file, `settings.json` and the CMD down over a cosmetic asset; an unreadable marker, an unreadable or read-only statusline, a missing `sha256sum` and a directory at the destination are all non-fatal, and only the unwritable-destination case says anything (one stderr note, because silence there is indistinguishable from a successful refresh). `scripts/test-claude-hook-skew.sh` pins all three transitions, both independence directions, and each of those error paths — asserting for every one that the hook exits 0 *and* that the instruction file and `settings.json` still refreshed, since independence has to hold on the error path too.
- `gh auth setup-git` runs from `$HOME` (not the workspace) and failure is non-fatal. On success it also adds a container-global `url."https://github.com/".insteadOf "git@github.com:"` rewrite (written to the ephemeral `GIT_CONFIG_GLOBAL`, never the host) so SSH-form `origin` remotes push/fetch over HTTPS+gh without rewriting the host repo.
- Alongside the `safe.directory` registration (and only when `GIT_CONFIG_GLOBAL` is writable), the entrypoint sets `push.useForceIfIncludes=true` so `--force-with-lease` additionally requires the overwritten remote tip to be in the local branch's reflog — closing the "a background fetch advanced the remote-tracking ref and defeated a bare lease" hole that shared-clone concurrency (parallel agents/worktrees) makes more likely. It is a no-op for fast-forward pushes and for raw `--force`, so the no-raw-force convention in [AGENTS.md](../AGENTS.md) "Git History Rewrites" is what actually carries the protection. Container-local (ephemeral `GIT_CONFIG_GLOBAL`), never the host `.gitconfig-host`.
- **Claude plugin channel — skills and `wf-*` workflows (`dev-skills@roubtec`).** No skills or workflows are image-baked for Claude (task 015b removed the 8 shared skills; the forfeit then moved `enable-worktrees`, `session-learnings`, and the `wf-*` dynamic workflows to `Roubtec/agent-skills` too, so the Claude hook seeds nothing); the container instead installs and keeps current the `dev-skills@roubtec` plugin (from the `Roubtec/agent-skills` marketplace) so it consumes the whole palette — skills namespaced `/dev-skills:<name>`, workflows `/dev-skills:wf-<name>` — through the same channel colleagues use. The work lives in `seed-claude-plugins.sh`, launched by `entrypoint-core.sh` immediately **after** `init-firewall.sh` (network ops ordered behind the firewall) and fully **detached** (`setsid`, stdin `</dev/null`, stdout/stderr → `$CLAUDE_CONFIG_DIR/.powbox-plugin-bootstrap.log`) on **every** launch, whether Claude is the primary agent or not — except the short-lived image-store **writer** container (`POWBOX_IMAGE_STORE_ROLE=writer`), which Docker reaps the moment its seeding command exits and so must never spawn a detached mutation of the shared claude-config volume. The Claude hook normally never touches the plugin; its one exception is a **build-skew shim** covering **two independent** detached convergence duties — the plugin bootstrap and the Codex shared-skill sync (see the next bullet) — each with its **own** "I own it" handshake exported by core (base-baked) before it runs the setup hook: `POWBOX_PLUGIN_BOOTSTRAP=core` and `POWBOX_CODEX_SYNC_BOOTSTRAP=core`. The hook gates each duty **separately** on its marker being absent, and separate markers are essential: the **current-main** base core already sets the *plugin* marker (it runs `seed-claude-plugins.sh`) but does **not** chain the Codex sync (that landed with task 021), so a single reused marker would make an agent-only `cc --build` over that base read "core owns it" and skip the sync entirely — silently stopping Codex convergence for the common agent-version-bump case. With split markers a **new** core sets both (the hook runs neither — no double-run), the **current** base sets only the plugin marker (the hook still runs the sync), and an **ancient** base sets neither (the hook runs both, plugin first so the sync then reads the just-refreshed clone). The hook's fallback fires only for **primary Claude**; a documented **residual gap** remains for a Codex-**primary** agent-only rebuild over the current base — the hook there runs pre-firewall as non-primary Claude's seeding (`PRIMARY_AGENT != claude`), so its sync-fallback is skipped and the old base core does not chain the sync either, leaving the Codex sync to run nowhere until a full base rebuild picks up the new core (which chains it for every launch, primary-agnostic); it self-heals on that rebuild or any Claude-primary start on the current base. No bounded wait on either fallback path; the refresh lands next session. `scripts/test-claude-hook-skew.sh` pins this gating (fallback fires when a marker is absent, is skipped when present, and honors the Codex-primary gap). As defense in depth the seeder also swaps a TTY stdin for `/dev/null` itself, so an ad-hoc run or a forgetful future call site cannot reintroduce the hang. Detachment is a **correctness requirement**, not just latency hygiene: the claude CLI **hangs** (SIGTERM-immune; only `timeout --kill-after`'s SIGKILL ends it) when invoked with the container TTY as stdin, so under the previous synchronous model (task 015g) even the read-only `claude plugin list --json` routing query burned its full 30s+5s bound on **every** warm primary-Claude start, and the synchronous cold install it was routing to never survived a TTY launch either — it hung the same way, timed out, and deferred to the background self-heal, so the promised first-session skill availability was paid for (~35s per start) but never delivered. The detached run converges patiently: `absent` (cold volume) → `marketplace add` + `plugin install`; `enabled` (warm) → keep-current — `marketplace update roubtec` refreshes the catalog **and** `plugin update dev-skills@roubtec` pulls the new commit-SHA version into the installed plugin cache (the CLI splits these: a marketplace update alone only refreshes listings); `disabled` → **respected**, never auto-re-enabled. Detached does not mean the session always misses the refresh: because Claude enumerates plugins once at session start, `entrypoint-core.sh` pairs the spawn with a **bounded, marker-based wait** at the very end of startup (primary-Claude launches only — a Codex prompt never uses the plugin), polling for a container-local done-marker that the run's EXIT trap touches on every exit path, for up to `POWBOX_PLUGIN_WAIT` seconds (default 4; `0` disables). The refresh overlaps the rest of the entrypoint, so a typical warm keep-current (~2–3s) finishes inside the window and its updates apply **this** session; the entrypoint never waits *on* the CLI process itself, so a hung CLI costs the cap, not the old 35s. Past the cap the session starts on the volume's current plugin state: a **cold** (fresh) claude-config volume's install usually outlives the window, so its first session lacks the `/dev-skills:*` skills until a `/reload-plugins` or restart, and a slow warm update lands one session late. The `Roubtec/agent-skills` repo is **public**, so `claude plugin marketplace add` clones it **anonymously** over HTTPS — no git credential helper, no dependency on the `gh auth setup-git` step (above), no auth-ordering race. Skills arrive namespaced as `/dev-skills:<name>` (e.g. `/dev-skills:address-review`); model-side Skill-tool matching by description is unaffected. Per-marketplace auto-update is left OFF (its on-disk schema is undocumented); opt in once per volume via `/plugin`. An offline start logs a skip and **self-heals** on a later online start; `CLAUDE_CODE_PLUGIN_KEEP_MARKETPLACE_ON_FAILURE=1` keeps the existing marketplace clone when a refresh fails offline. Because the claude-config volume is a *single global* volume shared by every powbox container, the bootstrap serializes its check-then-mutate with an flock on that volume (waiting the full `POWBOX_PLUGIN_LOCK_WAIT` — patient is fine, nothing is on the prompt's critical path), and every bounded op carries a `--kill-after` SIGKILL grace so a hung CLI can never hold that cross-container lock past its bound.
- **Codex piggybacks the plugin channel (`sync-codex-skills.sh`).** The plugin bootstrap above keeps a full clone of the `Roubtec/agent-skills` marketplace on the shared claude-config volume (`~/.claude/plugins/marketplaces/roubtec/`) and refreshes it (its `marketplace update` = git pull) every start; that clone carries `codex/dev-skills/skills/`, Codex's copies of the same shared palette (including the forfeited `enable-worktrees` and `session-learnings`). Rather than a second network fetch on the Codex bake cadence, `entrypoint-core.sh` chains `sync-codex-skills.sh` **directly after** the detached `seed-claude-plugins.sh` run — same post-firewall `setsid` detach, stdin `</dev/null`, stdio on the bootstrap log — as a **separate process** ordered after the clone refresh, so it reads the freshest clone and is a **local** sync (no network op of its own). (The Claude hook's build-skew shim runs this sync on its own `POWBOX_CODEX_SYNC_BOOTSTRAP=core` handshake, independent of the plugin marker, so an agent-only rebuild over the current base — which sets only the plugin marker — still converges Codex; see the plugin bullet above.) It is deliberately kept off the entrypoint's bounded plugin wait: that wait polls the *plugin* run's own done-marker, which the plugin step's EXIT trap fires **before** the Codex sync starts (the two run sequentially in one `bash -c`), so Claude's wait never gates on the Codex sync. Codex needs no wait anyway — unlike Claude (plugins enumerate once at session start) it observes skill-file changes **live**, so a refresh landing mid-session is picked up; the `POWBOX_PLUGIN_WAIT` wait is therefore *not* extended to Codex. The sync reuses `seed-skills.sh`'s marker/copy primitives: it iterates the clone's skill names (so it only ever touches skills the clone carries — since the forfeit that includes `enable-worktrees` and `session-learnings`, which are refreshed like any other; the former bake-owned denylist for those two is gone), overwrites only a copy powbox owns (`.powbox-seeded` present) via an atomic stage+rename, and never touches a marker-less user-adopted copy. It is **SHA-gated** so an unchanged palette is a byte-for-byte no-op (Codex warns loudly when skill files mutate under a running session): each refreshed marker records the synced `agent-skills` commit as `agent_skills_commit=<sha>` plus `channel=plugin-clone` (provenance = the SHA actually synced, `git -C <clone> rev-parse HEAD`, not the image build epoch) alongside the `source=Roubtec/agent-skills#codex/dev-skills/skills/<name>` upstream path every seeded item carries, and a start where the clone HEAD already matches the recorded SHA writes nothing. It serializes its check-then-mutate with its own flock on the shared **codex-config** volume (mirroring the plugin bootstrap's `run_locked`), and — because the clone it reads is Claude's plugin state, which a **concurrent** container's `marketplace update` (git pull) can be rewriting *and* advancing HEAD on at the same moment — it additionally holds the **same** claude-plugin flock `seed-claude-plugins.sh` uses (an INNER lock, nested under the codex-config lock) across the HEAD read + copy, so a peer's pull cannot interleave and hand it mixed content stamped with a since-moved SHA; a contended inner lock (a peer pull is in flight) is a clean skip that the next start re-syncs. It is best-effort: a cold claude-config volume with no clone yet (plugin disabled, or bootstrap not run) logs a skip and leaves the image-baked Codex copies in place, never exiting non-zero into the entrypoint. Precedence with the bake+seed refresher (`agent-update-skills`) is **last-writer-wins**: the updater may roll a synced Codex copy back to the image bake, and the next container start re-syncs it forward again as a cheap no-op-when-unchanged — see [skills-refresh-and-provenance.md](skills-refresh-and-provenance.md).
- Before the git/`safe.directory` steps, `entrypoint-core.sh` write-probes each dir-mounted `/workspace/<slug>` as `node` and, for any it cannot write, `sudo`s `fix-workspace-perms.sh`, which `chown`s it to `node` when the workspace root is owned by `root` (uid 0) — the common native-Linux case (a repo under `/root`, or a host running powbox as root), where the agent otherwise gets EACCES on every `git`/edit. The write probe alone misses a **mixed-ownership** workspace — a *node-owned* root that nonetheless hides nested `root`-owned files, which arises when a host operation runs as root against a live bind mount (most often `sudo git pull`, which re-owns to uid 0 only the paths it writes — new `.git/objects/*`, refs, changed working-tree files — leaving the top dir node-owned), so the agent can write the root yet `git commit`/`add` still fail with `insufficient permission for adding an object to repository database`. So besides the probe, the entrypoint runs a short-circuiting `find … -uid 0 -print -quit` (with the same mountpoint prune as below) over each node-writable workspace and hands any that contains a uid-0 entry to the same helper; the helper now acts on a root owned by **root or node** and re-owns only the `find -uid 0` entries (for a root-owned root that is the whole tree; for a node-owned root just the nested uid-0 entries — the root, already node, is untouched). A workspace whose root is owned by some *other* non-root, non-node host uid is refused with remedies (chown the repo to uid 1000 on the host, or relaunch in `--isolated` mode), never silently chowned, so a real host user is never locked out of their own repo. The probe creates its temp file with `mktemp` (O_EXCL, random name) rather than a predictable path, so a planted symlink in an untrusted workspace can't make it truncate an outside target as node. It is probe-/scan-gated, so it no-ops on Windows/WSL (FUSE bind mounts already honour node's writes) and on uid-matched hosts with no nested uid-0 entries; self-hosted mode and the detached image-store writer are exempt. The helper canonicalizes each argument and only acts on a direct `/workspace/<slug>` child; the chown (and the entrypoint's detection scan) prunes the real mountpoints nested under the workspace (from `/proc/self/mountinfo`), with `find -xdev` only as a backstop, so it never descends into the nested `node_modules`/`.worktrees` volume mounts — `-xdev` alone is insufficient when a volume shares the bind-mount source's filesystem (same st_dev). The recursive chown matches only root-owned entries (`find -uid 0`), so a file or directory nested inside a claimed tree but owned by another host uid keeps its owner rather than being re-owned to node — the same protection the root-level refusal gives, applied per-entry.
- **Sensitive-source refusal.** Before any of the above, both the heal decision (`heal-workspace-perms.sh`) and the privileged helper (`fix-workspace-perms.sh`) refuse outright to chown a workspace whose **host bind-mount source** is a system or home directory — `/`, `/root`, `/home/<user>`, `/Users/<user>`, the launching user's `$HOME`, or a bare FHS root like `/etc`/`/usr`/`/var`/`/opt`, plus any SSH config directory (a path ending in `/.ssh`, e.g. `/home/alice/.ssh` or `/root/.ssh`) — chowning just `~/.ssh` and its `authorized_keys` to node is itself enough to trip StrictModes even when the home dir stays root-owned (a project *nested* under a system/home root — `/opt/app`, `/var/www/html`, `/home/alice/code/app` — still heals normally). This guards a real incident: a `cc`/`cx` accidentally launched from `~` (e.g. `/root` on a VPS) bind-mounts the whole home tree as the "project", and the heal would then recursively chown it to node — re-owning `~/.ssh` **and its parent**, which breaks OpenSSH's StrictModes ownership chain so `sshd` refuses `~/.ssh/authorized_keys` and locks you out of the host (recoverable only via an out-of-band console). When the source is sensitive the workspace is **mounted but not chowned**, with a loud warning, so an accidental launch is a recoverable inconvenience (node may be unable to write that tree) instead of a host lockout. The shared predicate lives in `sensitive-host-path.sh` (sourced by both). Both classify on the launcher's **true absolute host source** rather than the layout-dependent mountinfo value: at trusted startup the entrypoint records each dir-mounted workspace's `POWBOX_WORKSPACE_HOST_PATH` (`pwd -P`-resolved) against its container mountpoint in a small per-boot marker map (`/run/powbox/workspace-sources`, node-writable), and `powbox_resolve_host_src` resolves a mount's source most-authoritative-first: (1) that marker map, (2) the launcher env for the one mount it names via `POWBOX_WORKSPACE_DIR` (a fallback if the marker could not be written; inert under `sudo`'s `env_reset`), (3) `/proc/self/mountinfo` field 4 as the env-independent last resort. This is what closes the two mountinfo-only gaps (task 009): a **direct** `sudo fix-workspace-perms.sh` refuses a `/home/<user>` bind on a separate-mount layout — where mountinfo field 4 reads back as the shallow `/alice` — because the marker (a *file*, surviving `env_reset`) records the true `/home/alice` (Gap A); and the heal **heals** a root-owned checkout whose bind source is a whole-filesystem mount — where mountinfo field 4 is a degenerate `/` — because the recorded true source (`/projects`) is authoritative over that degenerate value rather than OR-ed with it (Gap B). Mountinfo remains a working fallback when no launcher signal was recorded. The predicate and the mountinfo lookup are unit-tested by `scripts/test-sensitive-host-path.sh`; the live heal-skip/heal and fix-refusal (including both true-source cases) are smoke-tested by the dir-mount stage.
- Self-hosted (`--isolated`) clone seeding runs **after** the `gh auth` step (so a private clone has credentials) and **before** the shadow/pnpm steps, via the base-baked `seed-workspace.sh` (gated on `POWBOX_SELF_HOSTED=1`; a no-op otherwise, including the image-store writer role). It clones `POWBOX_CLONE_REPO`'s default branch into `POWBOX_WORKSPACE_DIR`, then applies the optional `POWBOX_CLONE_REF` as a **post-clone `git checkout`** (so it accepts a branch, tag, or raw commit SHA, and an unresolvable ref degrades to a warning + stay-on-default rather than aborting the clone), and skips the whole thing when a `.git` already exists (reuse — the agent owns its branches/worktrees; the ref is not re-applied on reuse). `--reclone` is **not** a frozen env flag (that would re-wipe the agent's work on every restart): it is a one-shot launcher action that empties the kept `agent-ws-*` volume and recreates the container, so the entrypoint then sees an empty dir and clones fresh. There is deliberately **no clone/auth failsafe and no retry**: on any failure it prints a loud announcement of the three remedies (use dir-mounted mode / `gh auth login` here / seed the shared gh volume) and `entrypoint-core.sh` `exec`s a plain `zsh` rather than execing the agent into an empty workspace.
- `safe.directory`/`core.filemode` handling is left as-is (harmless on a node-owned clone).
- Workspace shadow mounts run after git setup, so any shadow logic must not assume an earlier ordering. `shadow-mounts.sh` is **skipped** in self-hosted mode (no host FS to shadow, and a tmpfs would break the single-mount hardlinking); `wt-bootstrap` likewise branches its root-safety check on `POWBOX_SELF_HOSTED=1` (the worktree roots are plain subdirs of the one workspace volume, not per-dir mounts).
- `shadow-refresh.sh` — the hand-runnable re-scan — carries the **same two skips as the entrypoint** (`POWBOX_SELF_HOSTED=1` and `POWBOX_IMAGE_STORE_ROLE=writer`), because nothing downstream re-checks them: `shadow-mounts.sh` validates only "under `/workspace/` and not depth-1", never emptiness, and `CAP_SYS_ADMIN` is held in both modes, so an unguarded hand-run would successfully tmpfs-mask real content (live worktrees under `--isolated`; the host checkout's own `node_modules` in the writer role) rather than fail safe. Covered by `scripts/test-shadow-refresh-guard.sh`.
- One declared shadow is special: `.git/worktrees` gets **durable** per-worktree git metadata rather than tmpfs. When its sibling `.worktrees` is the persistent per-container volume (a non-tmpfs mountpoint), `shadow-mounts.sh` **bind-mounts** that volume's node-owned `.gitworktrees` subdir over `.git/worktrees`, so a linked worktree survives a container recycle with `git status` intact — instead of the working dir persisting on the volume while its metadata (formerly tmpfs) was discarded. Both the bind source and destination are still validated under `/workspace/`, and the destination bind hides the host's own `.git/worktrees` so container registrations never leak onto the host. Without a persistent `.worktrees` volume (the fallback launch) it falls back to tmpfs — still container-local. The decision lives entirely in the one privileged `shadow-mounts.sh`, so the entrypoint and `shadow-refresh.sh` loops are unchanged. Recovery is safe: `wt-bootstrap`/`wt-enter`/`wt-remove` (via `wt-common.sh`) reap a dir that is no longer a live worktree only when it is empty, and otherwise **preserve** it (move it to `.worktrees/.orphaned/`), so a pre-durable-metadata dir whose tmpfs metadata was lost is never deleted as the sole copy of dirty work.
- **.NET projects are shadowed by derivation, not declaration.** Alongside the pnpm/npm/yarn workspace globs (each → that package's `node_modules`), `detect-shadows.sh` walks the workspace for `*.csproj`/`*.fsproj`/`*.vbproj` and emits each project directory's sibling `bin` and `obj`. The reason is the same host-vs-container mixing `node_modules` shadowing exists for, but the mechanism differs: MSBuild bakes **absolute** paths into `obj/`, so a container restore writes `/workspace/<slug>/.worktrees/.nuget/` into `obj/project.assets.json` and `obj/*.nuget.g.props` while the same project built on a Windows host writes `C:\Users\<user>\.nuget\packages\` — shared over the bind mount the two silently clobber each other's restore graph. Doing it in the detector rather than per-repo `.powbox.yml` entries means adding a project needs no config change. Six properties matter: (1) `bin`/`obj` are emitted as **literals**, not a `*/bin` glob — the glob branch is existence-gated and build output is absent on a fresh clone or after a clean, exactly when the shadow has to be established, so a glob would shadow nothing in the case that motivates the feature; `shadow-mounts.sh` `mkdir -p`s a literal, at the accepted cost of an empty `bin`/`obj` mountpoint dir for a never-built project (or one redirecting output via `ArtifactsPath`), the same trade-off as the empty `node_modules`/`.worktrees` mountpoint dirs and gitignored by every standard .NET template. (2) The walk **prunes** `node_modules`, `.git`, `.worktrees`, `.claude`, and `bin`/`obj` themselves — keeping it at ~0.16s on a 1700-directory monorepo (hence no depth bound), skipping **both** worktree roots (`.worktrees`, the persistent volume, and `.claude/worktrees`, the harness-native tmpfs shadow: container-local, no host counterpart to collide with, and shadowing them would only cost RAM, discard build state, and nest a tmpfs inside a tmpfs), and stopping a project file copied under `bin/` from seeding a nested scan. The `bin`/`obj` prune matches at any depth, so the converse also holds: a project genuinely located at `<ws>/tools/bin/Tool.csproj` is invisible to the scan and gets no shadow — an accepted trade-off, since a directory named `bin` beside a project file is overwhelmingly output rather than source. The three project extensions and the `bin`/`obj` prune are matched **case-insensitively** (`-iname`), because a checkout authored on Windows keeps its casing once bind-mounted onto a case-sensitive Linux filesystem: `Legacy.CSPROJ` is a project MSBuild will happily build (its own extension matching is case-insensitive), so a case-sensitive scan would miss it and let the container's `bin`/`obj` land straight on the host — the exact collision the feature prevents — and by the same argument an output directory spelled `Bin`/`Obj` must be pruned or a project file copied under it seeds a nested scan. The four tool-created prune names (`node_modules`, `.git`, `.worktrees`, `.claude`) stay case-**sensitive**, since the tools that create them only ever write them in lower case and loosening them would merely widen what is skipped; emitted paths likewise stay lower-case `bin`/`obj` literals whatever the project file was called, because that is what a container-side `dotnet build` writes. The prune is bounded by `-mindepth 1` so it applies to the tree's interior only: `find` evaluates its expression against the scan root as well, so a workspace whose own basename is a pruned name (`bin`, and with the case-insensitive match `Bin` too) pruned itself at depth 0 and silenced the entire .NET scan — a container slug is `<name>-<hash>` so startup never reached it, but a hand-run `shadow-refresh.sh <path>` did. (3) An existing `bin`/`obj` that is a **symlink** is skipped, not resolved: this scan is inferred from repo content rather than declared by an operator, so resolving `app/bin -> ../src` would let the tree itself choose to tmpfs-mask real source for the whole session; the `.powbox.yml` branches still resolve symlinks, because those paths *are* an explicit declaration. Checking that final component is sufficient because the walk runs `find -H`, which dereferences **only its command-line argument** — no symlink encountered inside the tree is ever followed, so repo content cannot aim the walk, and the one dereferenced component is the operator-supplied `$WORKSPACE_DIR`. That argument has to be dereferenced: plain `-P` does not descend into a command-line symlink at all, so a hand-run `shadow-refresh.sh /path/to/symlink-to-workspace` would scan nothing and silently emit no .NET shadows (in practice the `/workspace` entries are bind mounts, so container startup never hit it; `entrypoint-core.sh`'s `/workspace/*/` glob would pass a symlinked entry straight through, which `-H` now handles correctly instead of skipping in silence). `-H` also keeps `find` printing paths with the argument's own spelling, which is what the workspace-relative arithmetic and `git -C "$WORKSPACE_DIR"` both assume. (4) Every derived path goes through the same `add_shadow_path` under-workspace-root validation as `.powbox.yml` entries, so nothing outside the workspace (and not the workspace root itself) can be shadowed — the pnpm/npm workspace globs included, since a manifest is repo content too and `packages: ["../other/src"]` must not be able to aim the shadow at a sibling project's tree. (5) An existing `bin`/`obj` holding **Git-tracked** content is skipped, on the same "an inferred shadow must not mask real files" principle as (3): a project redirecting its output (`ArtifactsPath`/`OutputPath`) can legitimately keep tracked scripts or fixtures in a sibling `bin`, and a tmpfs over one would make them read as deleted for the session while any edit landed in an overlay that dies with the container — real build output is gitignored by every standard .NET template, so "tracked" is a sound disposability signal. Three checks decide it, ordered cheapest-first. A `.git` **inside** the candidate (`app/bin/.git`), or the `HEAD`+`objects`+`refs` triple of a **bare** repository (which has no `.git` of its own and no entry in the outer index, so nothing else would stop its object store being masked), vetoes outright — neither is MSBuild output — and costs a few stats. A `.git` on any ancestor *strictly below* the workspace root (a submodule at `libs/sub`, a nested clone at `vendor/lib`) means the candidate belongs to a repository the workspace's own index cannot see into, so that repository is asked about it directly, one call for those few directories; the ancestor search is stats only, and the answer is only accepted once `rev-parse --show-toplevel` confirms that it really was the *found* repository that answered — a `.git` entry is not always one git will use (a dangling symlink, or a gitlink whose target is gone, makes the discovery walk step straight past it), and the outer repository reporting "untracked" for a directory it cannot see into is precisely the fail-open this branch exists to prevent. That nested probe is three-way like the batched one below, because "could not determine" is not the same answer as "holds tracked content": conflating them would report a skip as *contains Git-tracked files* when nothing was established, and would withhold a merely **absent** `bin`/`obj` — the fresh-clone case the feature exists for — whenever the owning repository's index was unreadable, disagreeing with the outer path, which still shadows an absent candidate in exactly that situation. Everything else — the overwhelming majority — is settled by one batched `git ls-files -z --cached` for the whole scan, over **every** candidate including those not on disk (a gitlink whose submodule was never initialized, or a path a sparse checkout left out, is tracked with nothing on disk, and shadowing it would send the eventual checkout into a tmpfs that dies with the container; batching them costs nothing, since the call count does not depend on the pathspec count); attribution compares workspace-**relative** paths, the same form `git -C` prints, so no absolute-path arithmetic can disagree with git's spelling (`WORKSPACE_DIR` is normalized of a trailing slash up front, since `shadow-refresh.sh /workspace/<slug>/` — what tab completion produces — passes its argument through verbatim). `--literal-pathspecs` keeps a project directory named `app[1]` from being read as a character class, and `git_scrubbed` clears the ambient git variables that would otherwise redirect or break the reads: `GIT_DIR`/`GIT_WORK_TREE`/`GIT_INDEX_FILE`/`GIT_COMMON_DIR`/`GIT_OBJECT_DIRECTORY`, because `git -C` does **not** override them and `shadow-refresh.sh` runs from whatever environment invoked it — inside a Git hook an inherited `GIT_DIR` would have another repository answer for this tree, in either direction — plus the `GIT_*_PATHSPECS` family, any of which makes the explicit `--literal-pathspecs` a fatal "incompatible with all other global pathspec settings". The failure split is deliberate: only *positive* evidence that there is **no repository** (neither `rev-parse` nor a `.git` entry at the workspace root) fails *open* and shadows as usual — an unreadable `.git`, which `rev-parse` also reports as "not a git repository", must not read as a plain folder. Every `.git` test here — inside the candidate, on a nested ancestor, and at the workspace root — is therefore **lexical**: an entry that exists, *or* a symlink even when its target does not, since `-e` follows symlinks and would answer false for a dangling `.git` (a linked worktree whose gitdir moved, a `.git` symlinked onto a volume that is not mounted yet) at the very moment the tracked-content question has become unanswerable; a bare repository's `HEAD` is counted the same way, since the deprecated-but-supported `core.prefersymlinkrefs` makes `git init --bare` write HEAD as a symlink to a default branch that does not exist until the first commit — leaving `objects` and `refs` on `-d`, because a repository cannot function without those as real directories and loosening them would start matching things that are not repositories at all. Any other failure fails **closed**, leaving every **existing** `bin`/`obj` un-shadowed while an **absent** one is still shadowed (there is nothing there for a tmpfs to mask, and that is the fresh-clone case): not shadowing costs a host/container `obj` collision, whereas shadowing tracked files loses edits. (6) No emitted path may contain a **newline**, enforced at the single emit point. The output protocol is newline-delimited — `mapfile -t` here, `read -r` in `shadow-refresh.sh` — so such a path would reach the privileged `shadow-mounts.sh` as two arguments whose first is a truncated *ancestor* of the target: a project beside a directory literally named `$'\nfoo'` emits `<ws>/`, which still passes the under-`/workspace` check, and the whole checkout would be tmpfs-masked for the session. The scan is what makes that reachable from repo content alone with no declaration, and guarding the one funnel also covers the `.powbox.yml` glob branch, whose expansion can match the same directory (the literal branch cannot carry a newline — `yq`'s output is itself read line by line).
- **A mountpoint `shadow-mounts.sh` creates inherits the host ownership of the tree it lands in.** A literal shadow whose target is absent (a `.powbox.yml` declaration, or any `bin`/`obj` on a never-built project) needs a directory under the tmpfs, and the helper only ever runs via `sudo` — so that directory is created by root. Only the tmpfs above it is node-owned, and it exists only while the container runs: once the container stops, a native-Linux bind mount is left with an empty root-owned mode-755 directory that the host user can neither populate nor remove, breaking the next host-side `dotnet build`. So immediately after `mkdir -p` (and necessarily **before** the mount, or it would chown the tmpfs root instead) each component it just created is chowned to the uid/gid of the deepest ancestor that already existed — the checkout's host owner on a bind mount, node on a container-local volume. `heal-workspace-perms.sh` has already run by this point in `entrypoint-core.sh`, so a root-owned checkout reads back as node-owned here rather than re-inheriting root. Each created directory is re-validated between the `mkdir` and its `chown` — a path that is now a symlink is skipped, and the resolved path must still land under `/workspace`. That **narrows** the window rather than closing it: `chown -h` declines to dereference only the **final** component, so a swap of an intermediate one between the check and the chown would still be followed. The residue is not a privilege boundary here — the `node` user already reaches root through the sudoers-allowed `apt-get`, and the `mkdir` and `mount` traverse the very same attacker-mutable path — so the cheap check earns its place while the race does not justify create-as-the-target-user machinery. A failed chown is never fatal (it warns **once per run** — on a Windows/FUSE bind mount the failure is expected and per-directory warnings would be dozens of lines every start — and the mount still proceeds). This was latent for `.powbox.yml` literals; the .NET scan is what makes it automatic and per-project. The decision logic is unit-tested hermetically by `scripts/test-shadow-mounts-chown.sh` (the `/workspace` literal relocated into a tmpdir, `id`/`stat`/`chown`/`mount`/`mountpoint` PATH-shimmed, so the emitted chown/mount sequence, the deepest-existing-ancestor lookup, and the warn-once behaviour are asserted without root or a real mount — on **both** routes to a mount, the ordinary tmpfs one and the `.git/worktrees` durable bind); the privileged end of it — that a real root-created mountpoint really lands host-owned on a real bind mount — is smoke-tested by `scripts/smoke-test-worktree-metadata.sh`, for a single created component on the ordinary tmpfs path (`proj/bin`, the .NET artifact shape above), a multi-component creation (`.claude/worktrees`), and the single-component case on the special durable-bind path (`.git/worktrees`).
- **`shadow-mounts.sh` refuses a target that is a workspace itself, not merely one outside `/workspace`.** Every legitimate shadow lives *below* `/workspace/<slug>`, so a depth-1 target can only be a mistake — and a tmpfs over it masks an entire checkout for the session. The producers already refuse to emit one (`detect-shadows.sh` rejects the workspace root, and rejects any path whose embedded newline would split into a truncated ancestor — property (6) above), but the privileged end enforces it too: a caller passes arbitrary argv, and the blast radius is a whole checkout.
- Unlike the pnpm path below, there is **no `dotnet` wrapper**: a project scaffolded mid-session is picked up only by re-running `shadow-refresh.sh` (which re-runs `detect-shadows.sh` wholesale, so the .NET scan is included and already-mounted paths are skipped) — build it before that and its `bin`/`obj` land on the host bind mount. This is the documented manual step in the container instruction file rather than an automated one because `dotnet` has no single node_modules-writing subcommand set to gate on the way `pnpm install`/`add`/`update` does.
- Startup shadow detection only sees the subpackages that exist at container start, so a package scaffolded mid-session would have its `node_modules` populated straight onto the host bind mount before any re-shadow. To close that race, `pnpm`/`pn` are replaced (base image, after `npm install -g pnpm`) with `docker/shared/pnpm-shadow-wrapper.sh`: for node_modules-writing subcommands (`install`/`add`/`update`/… — detected by scanning all args, since global flags can precede the subcommand) it runs `shadow-refresh.sh` scoped to the `/workspace/<slug>` enclosing pnpm's *effective* directory — honoring `-C, --dir <dir>`, so a `pnpm -C /workspace/<repo> install` invoked from outside `/workspace` still re-shadows the right project — *before* exec'ing the real `/usr/local/lib/node_modules/pnpm/bin/pnpm.mjs`. It is a no-op when that effective directory is outside `/workspace` or in self-hosted mode (`POWBOX_SELF_HOSTED=1`), mirroring the entrypoint's own self-hosted skip of the shadow step — that guard lives in `entrypoint-core.sh` around the `shadow-mounts.sh` call, not inside `shadow-mounts.sh`, which still carries no guard of its own (`shadow-refresh.sh` does carry the same two skips, per the bullet above — it is the hand-runnable entry point, so it has to) — and always execs pnpm so a shadow failure never blocks the command. `pnpx`/`pnx` (dlx) are left unwrapped — they don't write workspace `node_modules`. The same wrapper also closes the launch-time gate's residual hole (task 002b): a folder launched as **non-dev** (no `package.json`/`pnpm-workspace.yaml`/committed `.powbox.yml`/`.powbox.local.yml` with a top-level `shadow:` key, so the launcher mounts no `agent-nm-*` root volume and sets no `PNPM_STORE_DIR`; a ctx-only local config does not enter this gate) that gains a `package.json` mid-session would, on a **root** install, write `node_modules` straight onto the host bind mount — the very host litter the gate exists to prevent, and which the wrapper cannot retrofit a mount for. So before such an install it prints exactly one loud stderr warning (then still proceeds) telling the user to relaunch the agent (the folder now has a `package.json`, so the next launch mounts an isolated volume). The regression is detected via `<workspace>/node_modules` not being a mountpoint **plus** an empty `PNPM_STORE_DIR` (the launcher sets it only when it mounted the volume) and the effective dir being the workspace root, so a self-hosted run, an already-mounted dir-mounted dev project, and a subpackage install never trip it; it is unit-tested by `scripts/test-pnpm-shadow-wrapper.sh`.
- Right after the pnpm store-dir step, `entrypoint-core.sh` pre-creates the launcher-pointed Go caches, ccache compiler cache, and NuGet global packages folder (`GOMODCACHE`/`GOCACHE`/`CCACHE_DIR`/`NUGET_PACKAGES` env → `.worktrees/.gomodcache`/`.gocache`/`.ccache`/`.nuget`; set for dir-mounted JS/powbox/Go/.NET projects and in self-hosted mode, omitted for non-dev folders so nothing is mkdir-ed onto a host bind mount). Plain env is all four tools need — no `go env -w`, ccache config, or NuGet config — so the guarded `mkdir` exists only to surface a bad value loudly at startup; on failure it warns and **unsets** the var, so the tool falls back to its image-default (container-ephemeral) cache path instead of failing every build. (ccache stays opt-in per build: the binary and this persistent dir are baked, but nothing interposes it into a plain `gcc`/`cmake` invocation.) `golangci-lint` is likewise a wrapper on `PATH` (`docker/shared/golangci-lint-wrapper.sh`, real binary at `/usr/local/libexec/golangci-lint`) that derives a per-worktree `GOLANGCI_LINT_CACHE` at invocation time — see [architecture.md](architecture.md) "Bundled Go toolchain" for the cache layout and rationale, and "Bundled .NET SDK" for NuGet's shared-across-worktrees design.
- The container's two shells are split on purpose, so the `usermod --shell /bin/zsh` and `ENV SHELL=/bin/bash` in `docker/base/Dockerfile` are not a contradiction: zsh is the human login shell (and `launch-agent --shell` execs `zsh` directly), while bash is the `$SHELL` the agent harnesses' Bash tools spawn — the models write bash/POSIX (word-splitting, 0-indexed arrays) and a non-interactive one-shot call gains nothing from zsh, so defaulting agents to zsh only wasted turns. Both rc files (`docker/shared/.bashrc`, `.zshrc`) are baked but only shape interactive sessions; `EDITOR` and `PATH` live in image `ENV` so neither shell owns them.
