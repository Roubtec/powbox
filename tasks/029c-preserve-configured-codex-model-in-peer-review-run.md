# Task 029c: Preserve the configured Codex model and expose peer review prose

## Why this task exists

`peer-review-run` correctly isolates a Codex peer with `--ignore-user-config`, but that isolation also discards the top-level `model` selected in `$CODEX_HOME/config.toml` by the container's rolling `/model` workflow; it also discards any root `profile` or `model_provider` needed to interpret that model safely.

The helper explicitly re-injects `model_reasoning_effort` through a `-c` override, so effort passthrough works today, while an omitted Codex `--model` leaves `MODEL` empty, adds no `-m` argument, and reports `model:null`; the peer therefore uses the bare CLI default instead of the configured high-capability rolling model.

The stable `powbox.peer-review-run/v1` result also returns only `artifactDir`, not a provider-neutral location or field containing the full human-readable review prose; Claude's prose is nested in provider-native JSON in `provider.stdout`, while Codex uses a different final-message artifact, so a caller must currently know undocumented filenames and formats to relay findings verbatim.

Roubtec/agent-skills task 015 is adopting this helper in the canonical review skills, but its Claude-led renderings must retain a raw isolated `codex exec` launch until the helper preserves the configured Codex model without embedding a dated model ID, and all renderings need a stable way to retrieve the peer's full review prose before they can replace their provider-specific extraction.

## Scope

- Preserve a configured top-level Codex model across `peer-review-run`'s user-config isolation when the caller does not provide an explicit model and the root configuration makes that model safe to apply without forwarding provider or profile configuration.
- Add a stable provider-neutral result pointer to the full review prose for successful `passed` and `issues` outcomes from both providers, while retaining `artifactDir` and provider-native artifacts for debugging and audit.
- Keep the public command provider-neutral: `--model <ID>` remains the explicit per-invocation override for either provider, while an omitted model resolves through the selected provider's documented default policy.
- Keep explicit effort selection independent from model selection and continue passing Codex effort through `-c model_reasoning_effort=<LEVEL>`.
- Continue reporting the model and effort that the helper actually applied in the existing result contract.
- Document both helper-boundary changes as powbox-owned prerequisites for Roubtec/agent-skills task 015.

Out of scope: loading the rest of Codex user configuration into the peer, weakening project-config/rules/hooks/MCP isolation, selecting or hard-coding a dated Codex model ID, changing Claude's current `opus` default, changing review policy in Roubtec/agent-skills, or changing provider-native artifact retention.

## Desired interface and model semantics

- Do not add a Codex-only caller flag: keep `--model <ID>` as the single provider-neutral explicit override.
- When `--provider codex` is selected and `--model` is omitted, inspect only the root top-level `model`, `profile`, and `model_provider` keys in `${CODEX_HOME:-$HOME/.codex}/config.toml`, the location managed by the container's `/model` workflow, before launching the isolated peer.
- A root configured model is safe to pass as one `-m` argv element only when there is no root `profile` and no explicit root `model_provider`; any explicit provider selection is conservatively provider-dependent even if its value resembles a built-in or default provider, so do not hard-code a safe provider identity.
- Put configured-model resolution, TOML parsing, validation, and warnings in the existing strength-knob block alongside the `-*` model check, before artifact-root creation, `SESSION_DIR`, help-probe files, or any other filesystem side effect.
- Parse TOML as TOML with Python 3's standard-library `tomllib`, which is already baked into the runtime; do not source the file, use `eval`, or approximate TOML with a regex that can misread comments, quoted values, tables, or escapes. If Python 3 or `tomllib` is unavailable, degrade exactly like an unparseable existing config with a warning, no `-m`, and `model:null` rather than making the parser a new hard dependency.
- Start that parser in isolated mode — `python3 -I`, or an equivalent that keeps the invocation's working directory off `sys.path` and ignores `PYTHONPATH`, `PYTHONSTARTUP`, and the user site directory. Two distinct vectors make this load-bearing, and they are worth keeping separate because only one of them comes from the reviewed tree:
  - The reviewed checkout. A plain `python3 -c` or stdin script puts the working directory at `sys.path[0]`, and `peer-review-run` is routinely invoked from the very checkout under review, so a reviewed branch that adds `tomllib.py` shadows the standard-library module and executes arbitrary Python inside the unsandboxed helper before the peer is ever launched — ahead of the isolation the review is supposed to run under.
  - The ambient environment. `sitecustomize.py` is not reachable through the working directory (`site` runs during interpreter startup, before the `-c` path entry is inserted), but it does execute when its directory is on `PYTHONPATH` or in the user site directory, so a poisoned environment reaches the parser by that route instead.
Isolated mode closes both, which is why it is one flag rather than two mitigations.
Naming the standard library is not the same as importing it: the requirement is that the import provably resolves there, so the parser invocation is part of this task's security surface rather than an implementation detail.
- Bound the config *input* as well as the parser, and open it in a way that can classify it before reading. `${CODEX_HOME}/config.toml` is ordinary user state read at the pre-filesystem point required above, so no artifact root, session directory, or supervised deadline exists yet and nothing downstream can interrupt the read. A path that is a FIFO, or a symlink to an unbounded character device such as `/dev/zero`, therefore turns the documented warn-and-degrade path into a hang or an unbounded allocation — a regression against today's isolated launch, which never reads that file at all. Isolated startup closes the code-execution vector on the parser; this closes the resource vector on its input, and neither substitutes for the other. Three requirements, in this order:
  - Open non-blockingly, then classify by `fstat` on that descriptor. A plain `open(path, 'rb')` on a FIFO blocks inside `open()` before any check can run, and a `stat`-then-open sequence is check-then-act on a path a same-UID process may control — so open with `O_RDONLY|O_NONBLOCK`, `fstat` the descriptor, require a regular file, and read only then. Symlinks are followed as normal: a `config.toml` that is a symlink to a regular file is ordinary user state, and it is the final target's type that decides.
  - Cap the read. Regular does not mean small — a multi-gigabyte `config.toml` exhausts memory as surely as `/dev/zero` does — so read at most a stated cap, generous for this file at a few hundred KiB, and treat an over-cap file as unparseable rather than reading it to find out.
  - Take the existing degraded path on every rejection: no `-m`, `model:null`, and a clear stderr warning naming what was rejected. None of this adds a failure mode; it routes a new class of bad input into the one this task already defines.
- An explicit `--model` always wins, is validated by the existing flag-shaped-value rule, and bypasses configured-model lookup entirely, so an unreadable or invalid config cannot affect an explicit invocation.
- A missing config file or a valid config with no root top-level `model`, `profile`, or `model_provider` remains the backward-compatible unconfigured case: pass no `-m` and report `model:null` so Codex uses its CLI default.
- Profiles and provider definitions are deliberately outside the passthrough contract: never read values from `[profiles.*]` or `[model_providers.*]`. If a root `profile` or root `model_provider` is present, do not forward even a root `model`; pass no `-m`, report `model:null`, and warn that the profile- or provider-dependent selection cannot be preserved through isolated execution.
- If an existing config cannot be read or parsed, or its root `model` is empty, non-string, or flag-shaped, preserve today's otherwise-valid isolated review by passing no `-m`, reporting `model:null`, and emitting a clear stderr warning that configured-model passthrough degraded; this follows the helper's existing honest-degradation precedent rather than turning unrelated user-config damage into an exit-64 failure.
- Continue adding `--ignore-user-config`, `--ignore-rules`, `--disable hooks`, the MCP/approval/project-document overrides, and all existing read-only/session-isolation flags exactly as capability probing permits; only a successfully resolved root model crosses the isolation boundary.
- Keep Claude behavior unchanged: omitted `--model` resolves to `opus`, and an explicit model still overrides it.

## Provider-neutral review payload

- Add an additive `reviewFile` field to `powbox.peer-review-run/v1`; for `passed` and `issues`, it is an absolute path inside `artifactDir` to a UTF-8 plain-text file containing the full provider final review message used for verdict parsing, with provider JSON envelopes decoded and no helper-authored summary substituted for the provider's prose.
- For `passed` and `issues`, `reviewFile` must be non-null, the file must exist when the result is emitted, and the same semantics must hold for Claude and Codex; other outcomes report `reviewFile:null` unless a future contract explicitly defines usable review prose for them.
- Set the file's mode to 0600 and report honestly if that does not take, but do **not** fail the run over it: attempt the `chmod`, and on a failure — or a mode that reads back as something else — emit a clear stderr warning and continue to the normal `passed` or `issues` result. The file's privacy rests on the enclosing directory, which `ensure_private_dir` has already proved enforces 0700 before any provider ran, and the mode is defence in depth on top of that rather than the guarantee itself.
This is deliberately weaker than `ensure_private_dir`'s discipline, for three reasons that all point the same way. `ensure_private_dir` is the *only* mode enforcement in the helper today: `prompt.txt`, `provider.stdout`, `provider.stderr`, `codex-last-message.txt`, and `meta.json` are all created at the umask default inside that same directory, so a fail-closed 0600 here would make `reviewFile` the one mode-enforced file in the helper — guarding a normalized copy of `codex-last-message.txt`, which sits beside it unprotected. It also buys nothing against either documented threat: 0700 already excludes other UIDs, and the helper's stated residual is that a same-UID reader is unstoppable regardless. And the state it would guard on is a filesystem that enforces directory modes but not file modes, on a directory whose 0700 was just verified — against a certain cost, since fail-closed here means discarding a completed, already-paid-for peer review.
Content is the opposite case and stays fail-closed: the full-prose contract is what callers actually consume, nothing else in the helper covers it, and a truncated `reviewFile` is relayed as the peer's review.
- Reconcile the new exit with the documented outcome contract, which it contradicts as it stands, in **both** places the contract is written down. `docs/architecture.md` promises the helper "exits 0 for any produced outcome (non-zero only for its own usage errors)", and the helper's own header carries the same promise: "It exits 0 for ANY produced outcome … and non-zero ONLY for its own usage/operational errors."
The header's second clause already accommodates an operational exit; the architecture doc's narrower "usage errors" does not. What conflicts in both is the *first* clause — a `passed` review is a produced outcome, and a failed write now exits non-zero instead of reporting it. Amend that clause in both, and state plainly for callers that a completed review can now be discarded by a post-review write failure, since a consumer that reads non-zero as "the invocation was malformed" would misread it. Leaving either as-is is not an option: the doc is the downstream adoption boundary Roubtec/agent-skills reads, and a header that contradicts it is the next reader's confusion.
- Name the exit status rather than inheriting it by analogy. A failed write is not a usage problem — the invocation was valid and the filesystem gave out afterwards — so it exits 70, the helper's existing operational-failure status, and not `EX_USAGE` (64) by analogy with `ensure_private_dir`, whose 64 is right for its own case because an artifact root that does not enforce modes is a bad `--artifact-root` the caller chose. This path introduces no new exit-64 case, so it must not route through `die_usage`, whose "Try: peer-review-run --provider …" synopsis would reprint the required flags for an invocation that was well-formed. Say what actually failed instead.
- Verify the write, do not merely status-check it. `peer-review-run` deliberately runs without `set -e`, so a write that fails part-way — a full or read-only artifact filesystem, a quota hit mid-write — leaves an empty or truncated file that the subsequent `chmod 0600` then succeeds on regardless, and a silently truncating filesystem returns success by definition, so an exit-status test alone cannot see it. Read the write back: check the write's status, then read the file back through the same descriptor it was written on (per the creation rule below) and require it to be byte-for-byte identical to the parsed provider message that was written. Compare bytes — a `[ "$(cat f)" = "$text" ]` form strips trailing newlines on both sides and so cannot see a truncation confined to trailing bytes, which is precisely the case this exists to catch. Fail closed on either. A mode-only or status-only check emits `passed` or `issues` with a `reviewFile` that silently violates the full-prose contract, which is worse than an outright failure because the caller relays the truncation as the peer's review.
- Create the review file with a single atomic exclusive create that cannot follow a symlink, and let that same open be the write. The helper writes it unsandboxed into the attempt directory, which is the one directory the peer is handed a writable target inside, at the same UID; a peer that pre-creates the review path as a symlink would redirect that write to a path of its choosing, and a symlink to `/dev/null` would yield "write succeeded, non-null path" (the content read-back above catches the emptiness, but only after the out-of-tree write happened).
A `test ! -e` guard followed by a redirection does not deliver that, and the difference is the whole requirement: it is check-then-act, and the window between the two is exactly when a live same-UID descendant swaps the path. That descendant is reachable here rather than hypothetical — tasks 029d and 029e suppress further *attempts* when reaping cannot confirm the tree is gone, but neither kills the survivor, so an attempt that reaps with only a warning and still parses a verdict arrives at this normalization step with a process from its own provider tree live.
So creation must be a real `O_CREAT|O_EXCL` open, which fails with `EEXIST` when anything already occupies the path — a symlink included, whatever it points at, since POSIX requires the flag pair to fail on the link itself rather than resolve it.
**The shell's `noclobber` is not that open, and reaching for it is the trap this bullet exists to close.** `set -C` does not pass `O_EXCL`: it `stat()`s the path first — following symlinks — and adds `O_EXCL` only when that `stat` *fails*, so an existing **non-regular** target is opened and written straight through. Measured on bash 5.2: a review path pre-created as a symlink to `/dev/null`, or as a FIFO, is written through under `set -C`, while an `O_CREAT|O_EXCL` open refuses all of them with `EEXIST`. Noclobber refuses only the two cases an existence test already refuses — an existing regular file, and a dangling symlink — so it is check-then-act wearing a flag, and it leaves open precisely the `/dev/null` symlink this bullet's own first paragraph names. The blast radius is wider than a discarded review: a symlink to a FIFO reintroduces the unbounded block the config-input rule above exists to eliminate, on a path with no supervised deadline left in force, and a symlink to `/proc/self/fd/1` writes the review prose into the helper's own stdout ahead of the result object, corrupting the `powbox.peer-review-run/v1` JSON every caller parses.
Do the create, the write, and the content read-back in **one** isolated `python3 -I` invocation holding **one** descriptor — `os.open(path, O_RDWR|O_CREAT|O_EXCL, 0o600)`, write the prose, `lseek` back, read it back, compare bytes, exit non-zero on any mismatch — with the path in `argv` and the prose on stdin. One descriptor is what makes the guarantee whole: nothing is ever re-resolved by path, so the read-back cannot be pointed at a replica, and — the reason it is not merely tidy — it cannot be pointed at a FIFO or `/dev/zero` either, which a re-open by path would let a live descendant do to a read that has no deadline over it. The create's mode is umask-subject, so the separate warn-and-continue `chmod 0600` above still stands.
That leaves one residual, stated rather than papered over: the `reviewFile` path in the emitted result can be swapped after the helper exits, which is the same-UID reader the helper already documents as unstoppable. What must not be the weak link is anything the helper itself does with that path.
This is the one place the task takes a hard dependency on Python 3, and the asymmetry with the config parser above is deliberate: that parser degrades when Python is absent because configured-model passthrough is an optimization over a working default, whereas this path's whole contract is fail-closed, so an unavailable interpreter exits 70 rather than emitting a `reviewFile` it cannot stand behind. Python 3 is baked into the image this helper ships in, so that is a stated precondition rather than a live degradation path — but say so in the header, since it is a new way for a completed review to be discarded.
- Callers read the path from the result and must not construct provider-specific paths, inspect `provider.stdout`, know Codex's final-message filename, or parse provider-native JSON.
- Preserve `artifactDir` unchanged as the returned final-attempt directory containing that attempt's provider-native artifacts; earlier retry-attempt directories remain siblings under the existing parent session tree, and the normalized review file inside the returned `artifactDir` is an additional stable consumption surface rather than a replacement for diagnostic evidence.

## Implementation notes

- Grow the header's `--model` paragraph to describe root configured-model resolution and degraded fallback, then extend the line range in `usage()` so `--help` prints the complete header rather than truncating mid-sentence.
- Resolve the configured model in the strength-knob block before any artifact/session path is created; do not defer it to `build_cmd_codex()` or temporarily run Codex without isolation to discover it.
- Use Python 3 standard-library `tomllib` only to classify the root `model`, `profile`, and `model_provider` keys; leave `[profiles.*]` and `[model_providers.*]` unread, and do not forward profiles, provider definitions, project trust, hooks, MCP servers, approval policy, sandbox settings, instructions, or any other user-config value. Parser absence or failure takes the documented degraded path rather than failing the review helper.
- Do the opening inside that same interpreter rather than shelling the file in. `os.open(path, os.O_RDONLY | os.O_NONBLOCK)`, `os.fstat` on the returned descriptor, `stat.S_ISREG` or degrade, then read from that descriptor up to one byte past the cap — looping to EOF, since a regular-file `read()` may legitimately return short — and reject an over-cap file before parsing. One descriptor from classification to parse, so nothing is re-resolved by path in between. `tomllib.load()` on a file object opened the ordinary way is what reintroduces the blocking open, and a shell-side `[ -f ]` precheck is the check-then-act shape the requirement rejects; the helper's existing `[ -f "$PROMPT_FILE" ]` guard is a caller-supplied path outside the peer's reach and is not a precedent for this one.
- Feed the parser correctly: `tomllib.loads()` takes `str`, not `bytes`, and handing it the buffer raises `TypeError` — which the degraded path would then swallow, turning **every** valid configured model into a silent `model:null` while the whole feature reports as working. Decode the bounded buffer as strict UTF-8 and call `tomllib.loads()` on the result, or hand `tomllib.load()` an `io.BytesIO` over it. TOML is UTF-8 by definition, so route a `UnicodeDecodeError` to the same degraded path as a parse failure.
- Pass the isolation flag on the interpreter invocation itself (`python3 -I -c …`), and treat it as load-bearing when reviewing the diff: dropping it is a silent reintroduction of arbitrary code execution from the reviewed tree, not a style regression. Isolated mode also suppresses `PYTHONPATH` and user site-packages, so no ambient interpreter configuration can substitute a parser either.
- Treat the parsed model as data and append it through the existing Bash argv array so whitespace, quotes, or shell metacharacters cannot become shell syntax.
- Preserve precedence: explicit CLI model, then a usable root configured Codex model only when neither a root profile nor a root model provider is selected, then the bare Codex CLI default with honest warning/null reporting for unsupported or degraded configured selection.
- Preserve the existing effort floor and validation independently of model resolution; a configured `model_reasoning_effort` must not override the helper's default or caller-selected `--effort`.
- Keep config lookup outside the reviewed worktree and do not copy the config or its unrelated contents into retained attempt artifacts or diagnostics.
- Normalize the already-parsed final provider message into a new file inside the final attempt's returned `artifactDir`, created, written, and read back through one `O_RDWR|O_CREAT|O_EXCL` descriptor in a single isolated `python3 -I` invocation, before constructing a `passed` or `issues` terminal result; fail closed at exit 70 if the content cannot be proved. Do **not** use a shell redirection under `set -C` for this: noclobber is not `O_EXCL` and writes through an existing non-regular target, which is the hole the creation rule above documents in full. A refused creation is the same operational failure and exits 70 too: the invocation was well-formed and the path was taken from under the helper. Set the mode to 0600 separately and warn rather than fail if that does not take. Without `set -e` the helper's status test on that invocation has to be explicit, and the in-descriptor read-back is what covers the truncating case that reports success — a later successful `chmod` says nothing about whether the bytes landed. Retain earlier attempts as sibling directories under the existing session parent, and do not make the stable payload path an alias for undocumented provider-native files.
- Give every Codex-provider test case a harness-owned empty `CODEX_HOME` by default, with case-specific `config.toml` fixtures only where configuration behavior is under test, so neither the developer's rolling `/model` selection nor any other ambient `~/.codex/config.toml` value can change existing or new assertions.
- Use fixture-only model names in tests so neither implementation nor documentation acquires a dated production model pin.

## Acceptance criteria

- A Codex-provider invocation without `--model` reads a valid configured root model only when neither root `profile` nor root `model_provider` is present, passes that exact value as one `-m` argument despite `--ignore-user-config`, and reports it in `.model`.
- The same invocation reports the independently requested or defaulted reasoning level in `.effort` and passes the matching `model_reasoning_effort` override.
- An explicit `--model` wins over configuration, bypasses config parsing, and is the only model sent to the provider.
- Missing config and a valid config without a root model, root profile, or root model provider preserve the current no-`-m`, `model:null` fallback.
- An active root `profile`, any explicit root `model_provider`, an unavailable Python 3/`tomllib` parser, and existing but unreadable, malformed, empty, non-string, or flag-shaped root model values launch without `-m`, report `model:null`, and emit a clear stderr warning before any artifact/session filesystem side effect; resolving configuration never invokes the provider as a discovery mechanism.
- Provider-degradation tests include root `model_provider` fixtures backed by `[model_providers.*]` definitions and prove that the helper neither reads nor tries to forward those definitions, never assumes an explicit provider is safe, and instead warns, omits `-m`, and reports `model:null`.
- A `${CODEX_HOME}/config.toml` that is a FIFO, one that is a symlink to an unbounded character device such as `/dev/zero`, and one regular file larger than the stated cap each take the degraded path — no `-m`, `model:null`, stderr warning — and the invocation still terminates. Bound the assertion rather than trusting it: run these cases under an outer `timeout`, so a blocking `open()` or an unbounded read fails the case instead of hanging the suite. The FIFO and `/dev/zero` fixtures fail loudly against a naive implementation, because the outer `timeout` is a real discriminator there. The over-cap case has no such property for free and must be built to have one: any over-cap fixture small enough for a hermetic suite is also read to EOF in milliseconds, so an uncapped implementation stays well inside the `timeout`, and if the padding also breaks the parse it degrades to `model:null` with a warning and passes the case for the wrong reason.
Build it so the two implementations disagree on the *result*: make the fixture valid TOML that defines a usable root `model` and pad it past the cap with comment lines, keeping it a few hundred KiB against a cap in that range rather than manufacturing a huge file. A capped implementation rejects it unread and reports `model:null` with a warning naming a size or cap rejection; an uncapped one parses it happily and reports the fixture's model, failing the criterion on the assertion that matters.
- A test worktree carrying a shadow `tomllib.py`, with the helper invoked from that worktree as its working directory, resolves the real standard-library parser and does not execute the shadow; configured-model resolution behaves exactly as it does from a clean directory. This is the regression detector for the isolation flag: without it the case fails loudly. Give the shadow an observable side effect — have it write a marker file — and assert that marker's absence, so non-execution is proved directly rather than inferred from the resolved model value.
- A companion case puts a `sitecustomize.py` on `PYTHONPATH` (or the user site directory) and asserts it does not execute either. Note that it proves the ambient half only — a `sitecustomize.py` sitting in the working directory is inert with or without the isolation flag, so it detects nothing on its own and must not stand in for the `tomllib` shadow above.
- Tests prove `--ignore-user-config`, rules/hooks isolation, MCP disabling, approvals-off behavior, project-document disabling, read-only sandboxing, and ephemeral execution remain present alongside configured-model passthrough.
- Every Codex-provider test, including pre-existing default, explicit-model, unavailable, capability-probe, retry, and verdict cases, runs with a harness-controlled `CODEX_HOME`; new configuration cases replace that empty default with their own fixture, so ambient `/model` state cannot affect native-Linux results.
- Claude defaults and explicit model behavior remain unchanged.
- Every `passed` or `issues` result from either provider has a non-null absolute `.reviewFile` inside `.artifactDir`, whose plain-text contents are the complete provider review message used for the verdict; callers can relay it without inspecting native artifacts or parsing provider formats.
- A fixture whose `chmod 0600` on the review file fails or is silently ignored still produces the normal `passed` or `issues` result, with a clear stderr warning and a usable `reviewFile`; no mode failure aborts a completed review. Scope such a fixture to the review file's own path — an unscoped shim trips `ensure_private_dir` on the session or attempt directory first and exits 64 there, which is that function's existing behavior and not this path's.
- A fixture that fails the normalized-file write while leaving `chmod` and the mode read succeeding, and a separate fixture whose write reports success but silently truncates, both prove the same fail-closed behavior, exiting 70, so an empty or partial `reviewFile` can never ship inside a successful result. The truncating case is what proves the content read-back exists; a status-only implementation passes the first fixture and fails this one.
Both need a named mechanism, and the task is not complete until one is implemented and used. A full or read-only filesystem is not constructible from the existing unprivileged hermetic harness, so name an env-gated test-only injection point on the write — the same discipline task 029d applies to its survivor case. Do not reach for a fake provider that pre-creates the review path as a directory or as a symlink to `/dev/null`: under the exclusive-create rule above those fixtures are refused at the open, which is a different requirement, and using them here would leave the write path itself untested.
- A fixture in which the peer pre-creates the review path proves the helper refuses rather than writing through it, and that nothing is written at the planted target. Cover five shapes, and the last two are the ones that carry the requirement: a regular file, a directory, a symlink to a regular file outside the attempt directory, **a symlink to `/dev/null`**, and **a symlink to a harness-made FIFO**. The first three are refused by an existence test, by noclobber, and by an `O_EXCL` open alike, so they discriminate between none of them; only a non-regular target separates the mechanism this task requires from the one it rejects. Run the FIFO shape under an outer `timeout` and assert termination as well as refusal — a naive implementation blocks there rather than failing an assertion.
- A further case proves the creation is *exclusive* rather than merely checked, which the pre-created fixtures above cannot: they are all planted before the helper looks, so a `test ! -e` implementation is refused by every one of them. Name a mechanism and implement it — an env-gated test-only injection point at the last instruction before the creating open, mirroring the one the write path already requires, whose hook plants the review path as a symlink to a non-regular target (`/dev/null` and a FIFO both serve). That is the attacker winning the race, made deterministic: an `O_EXCL` create fails on the now-existing path and the helper exits 70 with nothing written at the target, while a check-then-act implementation has already passed its existence test — and a noclobber one has already `stat`ed a non-regular target and dropped `O_EXCL` — and both write straight through. Assert the fail-closed exit, the untouched target, and, for the FIFO variant under an outer `timeout`, that the helper terminated at all.

- The result contract keeps `.model` and `.effort` describing values actually applied rather than merely requested or discovered.
