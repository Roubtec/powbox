# Task 029c: Preserve the configured Codex model and expose peer review prose

## Why this task exists

`peer-review-run` correctly isolates a Codex peer with `--ignore-user-config`, but that isolation also discards the top-level `model` selected in `$CODEX_HOME/config.toml` by the container's rolling `/model` workflow; it also discards any root `profile` or `model_provider` needed to interpret that model safely.

The helper explicitly re-injects `model_reasoning_effort` through a `-c` override, so effort passthrough works today, while an omitted Codex `--model` leaves `MODEL` empty, adds no `-m` argument, and reports `model:null`; the peer therefore uses the bare CLI default instead of the configured high-capability rolling model.

The stable `powbox.peer-review-run/v1` result also returns only `artifactDir`, not a provider-neutral location or field containing the full human-readable review prose; Claude's prose is nested in provider-native JSON in `provider.stdout`, while Codex uses a different final-message artifact, so a caller must currently know undocumented filenames and formats to relay findings verbatim.

Roubtec/agent-skills task 015 is adopting this helper in the canonical review skills, but its Claude-led renderings must retain a raw isolated `codex exec` launch until the helper preserves the configured Codex model without embedding a dated model ID, and all renderings need a stable way to retrieve the peer's full review prose before they can replace their provider-specific extraction.

## Scope

- Preserve a configured top-level Codex model across `peer-review-run`'s user-config isolation when the caller does not provide an explicit model and the root configuration makes that model safe to apply without forwarding provider or profile configuration.
- Add a stable provider-neutral result pointer to the full review prose for successful `passed` and `issues` outcomes from both providers, while retaining `artifactDir` and provider-native artifacts for debugging and audit.
- Keep the public command provider-neutral: `--model <ID>` remains the explicit per-invocation override for either provider, while an omitted model resolves through the selected provider's documented default policy.
- Keep explicit effort selection independent from model selection and continue passing Codex effort through `-c model_reasoning_effort=<LEVEL>`.
- Continue reporting the model and effort that the helper actually applied in the existing result contract.
- Document both helper-boundary changes as powbox-owned prerequisites for Roubtec/agent-skills task 015.

Out of scope: loading the rest of Codex user configuration into the peer, weakening project-config/rules/hooks/MCP isolation, selecting or hard-coding a dated Codex model ID, changing Claude's current `opus` default, changing review policy in Roubtec/agent-skills, or changing provider-native artifact retention.

## Desired interface and model semantics

- Do not add a Codex-only caller flag: keep `--model <ID>` as the single provider-neutral explicit override.
- When `--provider codex` is selected and `--model` is omitted, inspect only the root top-level `model`, `profile`, and `model_provider` keys in `${CODEX_HOME:-$HOME/.codex}/config.toml`, the location managed by the container's `/model` workflow, before launching the isolated peer.
- A root configured model is safe to pass as one `-m` argv element only when there is no root `profile` and no explicit root `model_provider`; any explicit provider selection is conservatively provider-dependent even if its value resembles a built-in or default provider, so do not hard-code a safe provider identity.
- Put configured-model resolution, TOML parsing, validation, and warnings in the existing strength-knob block alongside the `-*` model check, before artifact-root creation, `SESSION_DIR`, help-probe files, or any other filesystem side effect.
- Parse TOML as TOML with Python 3's standard-library `tomllib`, which is already baked into the runtime; do not source the file, use `eval`, or approximate TOML with a regex that can misread comments, quoted values, tables, or escapes. If `tomllib` is unavailable — it arrived in 3.11, so an older interpreter is the reachable case — degrade exactly like an unparseable existing config with a warning, no `-m`, and `model:null` rather than making the *parser* a new hard dependency. The **interpreter** is a separate question and is answered the other way: the review-file rule below preflights `python3` as a precondition of the helper, so its outright absence is not a degradation case here at all.
- Start that parser in isolated mode — `python3 -I`, or an equivalent that keeps the invocation's working directory off `sys.path` and ignores `PYTHONPATH`, `PYTHONSTARTUP`, and the user site directory. It is load-bearing rather than hygiene, and closes two separate vectors with one flag: a plain `python3 -c` puts the working directory at `sys.path[0]`, and `peer-review-run` is routinely invoked from the very checkout under review, so a reviewed branch that adds `tomllib.py` shadows the stdlib module and executes arbitrary Python inside the unsandboxed helper before the peer is ever launched; and a poisoned `PYTHONPATH` or user site directory reaches the same parser through `sitecustomize.py`. The acceptance criteria below state which fixture proves which vector, and which one proves nothing on its own.
- Bound the config *input* as well as the parser, and open it in a way that can classify it before reading. `${CODEX_HOME}/config.toml` is ordinary user state read at the pre-filesystem point required above, so no artifact root, session directory, or supervised deadline exists yet and nothing downstream can interrupt the read. A path that is a FIFO, or a symlink to an unbounded character device such as `/dev/zero`, therefore turns the documented warn-and-degrade path into a hang or an unbounded allocation — a regression against today's isolated launch, which never reads that file at all. Isolated startup closes the code-execution vector on the parser; this closes the resource vector on its input, and neither substitutes for the other. Three requirements, in this order:
  - Open non-blockingly, then classify by `fstat` on that descriptor. A plain `open(path, 'rb')` on a FIFO blocks inside `open()` before any check can run, and a `stat`-then-open sequence is check-then-act on a path a same-UID process may control — so open with `O_RDONLY|O_NONBLOCK`, `fstat` the descriptor, require a regular file, and read only then. Symlinks are followed as normal: a `config.toml` that is a symlink to a regular file is ordinary user state, and it is the final target's type that decides.
  - Cap the read. Regular does not mean small — a multi-gigabyte `config.toml` exhausts memory as surely as `/dev/zero` does — so state a cap as the largest payload that will be *accepted*, generous for this file at a few hundred KiB, read up to one sentinel byte past it, and treat anything that reaches that byte as unparseable rather than reading on to find out. The `+1` is how over-cap is detected, not a larger cap.
  - Take the existing degraded path on every rejection: no `-m`, `model:null`, and a clear stderr warning naming what was rejected. None of this adds a failure mode; it routes a new class of bad input into the one this task already defines.
- An explicit `--model` always wins, is validated by the existing flag-shaped-value rule, and bypasses configured-model lookup entirely, so an unreadable or invalid config cannot affect an explicit invocation.
- A missing config file or a valid config with no root top-level `model`, `profile`, or `model_provider` remains the backward-compatible unconfigured case: pass no `-m` and report `model:null` so Codex uses its CLI default.
- Profiles and provider definitions are deliberately outside the passthrough contract: never read values from `[profiles.*]` or `[model_providers.*]`. If a root `profile` or root `model_provider` is present, do not forward even a root `model`; pass no `-m`, report `model:null`, and warn that the profile- or provider-dependent selection cannot be preserved through isolated execution.
- If an existing config cannot be read or parsed, or its root `model` is empty, non-string, or flag-shaped, preserve today's otherwise-valid isolated review by passing no `-m`, reporting `model:null`, and emitting a clear stderr warning that configured-model passthrough degraded; this follows the helper's existing honest-degradation precedent rather than turning unrelated user-config damage into an exit-64 failure.
- Continue adding `--ignore-user-config`, `--ignore-rules`, `--disable hooks`, the MCP/approval/project-document overrides, and all existing read-only/session-isolation flags exactly as capability probing permits; only a successfully resolved root model crosses the isolation boundary.
- Keep Claude behavior unchanged: omitted `--model` resolves to `opus`, and an explicit model still overrides it.

## Provider-neutral review payload

- Add an additive `reviewFile` field to `powbox.peer-review-run/v1`; for `passed` and `issues`, it is an absolute path inside `artifactDir`, at the fixed basename `review.txt`, to a plain-text file containing the full provider final review message used for verdict parsing, with provider JSON envelopes decoded and no helper-authored summary substituted for the provider's prose. That basename is pinned here rather than left to the implementation, and it is provider-neutral by construction — it collides with none of the existing `prompt.txt`, `provider.stdout`, `provider.stderr`, `codex-last-message.txt`, `meta.json` artifacts — so the helper, the header, the architecture doc, and the tests all name the same file: the pre-created-path fixtures below have to plant an obstacle at exactly `<artifactDir>/review.txt` before the helper runs.
State the guarantee as "plain text, byte-identical to the parsed message" and no more. Not fidelity to the provider's raw stream, which is already unavailable — the message reaches the writer through a Bash command substitution, which drops NUL bytes **and strips trailing newlines** — and not *UTF-8*, which nothing here validates and which a gate would only enforce by discarding completed reviews.
That stripping is a trap for the tests as much as for the contract: the expected bytes are the *post-substitution* value, so a fixture that compares the review file against the fake provider's own last-message artifact — which still carries its trailing newline — fails against a correct implementation. Build the expected value accordingly and compare it byte-exactly with `cmp`, never `[ "$(cat a)" = "$(cat b)" ]`, which strips both sides and would hide exactly the trailing-byte truncation the read-back exists to catch.
- For `passed` and `issues`, `reviewFile` must be non-null, the file must exist when the result is emitted, and the same semantics must hold for Claude and Codex; other outcomes report `reviewFile:null` unless a future contract explicitly defines usable review prose for them.
- **Create, write, verify, and set the mode in one isolated `python3 -I` invocation holding one descriptor.** This is the whole mechanism; the paragraphs under it say why each part is not substitutable. `os.open(path, O_RDWR|O_CREAT|O_EXCL, 0o600)` with the process umask temporarily cleared so the create mode is really 0600; write the prose, looping until it is all out, since a partial `os.write` is legal; `fchmod` to 0600 and `fstat` to confirm, warning and continuing rather than failing on either (the mode rule below); `lseek` back to zero; read back and compare bytes; exit non-zero on any content mismatch. The path arrives in `argv`, the prose on stdin. Make this invocation and the config parser's distinguishable on argv — tests shim one without the other, and a shim that cannot tell them apart breaks the case it is not aiming at.
One descriptor is what makes the guarantee whole: after the exclusive create, nothing is re-resolved by path, so neither the read-back nor the `chmod` can be steered onto a replica, a FIFO, or `/dev/zero` by a live descendant.
**Bound the read-back to `len(expected) + 1` bytes**, looping until that many are in hand or EOF is reached, whichever comes first — the same rule the config read follows above, and for the same reason: a regular-file `os.read()` may legally return short, so a single call would fail closed on a complete file and discard a paid-for review. The bound is what keeps that loop's memory finite while the survivor postulated below appends to the file it failed to pre-empt; a read-to-EOF would still *detect* the extra bytes, but only after consuming them all. The bound doubles as the assertion: exactly the expected bytes passes, anything shorter or a byte more fails, so truncation and overrun are caught by one read. Treat a zero-progress `os.write` as an error rather than looping on it.
The writer's exit convention carries the fail-closed/warn split and should be stated outright, since consolidating the mode into this invocation made it the only thing that does: exit non-zero for **any** failure — refused creation, failed write, failed seek or read, content mismatch — except the mode set, which warns on stderr and exits 0. Enumerating only some non-zero causes would leave an implementer free to read a write error as non-fatal. Make the refused-creation diagnostic distinguishable from the content-mismatch one; the creation fixtures below assert which of the two fired.
Deliver the prose with `printf '%s'` through a pipe and read `sys.stdin.buffer` — never a here-string or a `$( )` capture, which respectively append and strip trailing newlines and would make the byte-equality check fail, or pass, for reasons unrelated to the code. Test the writer's exit status explicitly at the call site and exit **70** on any non-zero — the helper runs without `set -e`, so nothing detects it otherwise, and the contract's status is 70 rather than whatever the interpreter returned.
Two placement notes an implementer will otherwise learn the hard way. The parsed message is a `local` inside `run_attempt`, so "before constructing a `passed` or `issues` result" means writing at the point that outcome is set inside that function, not after it returns, where the value is gone. And the `python3` preflight runs before the config read, so a missing interpreter exits 70 without first emitting a spurious configured-model degradation warning.
- The mode is warn-and-continue, not fail-closed: on an `fchmod` or `fstat` failure, or a mode that reads back as something else, emit a clear stderr warning and continue to the normal `passed` or `issues` result. Its privacy rests on the enclosing directory, which `ensure_private_dir` has already proved enforces 0700 before any provider ran; the mode is defence in depth on top of that rather than the guarantee.
That is deliberately weaker than `ensure_private_dir`'s discipline, on the same parity argument the directory residual below makes about the sibling files: it buys nothing against either documented threat, and its cost is certain — discarding a completed, already-paid-for peer review.
Clearing the umask at creation is what keeps that decision honest. Without it the create can land at 0400, 0200, or 0000 under a restrictive umask, and a warn-and-continue mode failure would then emit a `passed` result pointing at a file the caller cannot read or cannot write — a worse outcome than the one this rule declines to fail over.
Content is the opposite case and stays fail-closed: the full-prose contract is what callers actually consume, nothing else in the helper covers it, and a truncated `reviewFile` is relayed as the peer's review.
- Reconcile the new exit with the documented outcome contract, which it contradicts as it stands, in **both** places the contract is written down. `docs/architecture.md` promises the helper "exits 0 for any produced outcome (non-zero only for its own usage errors)", and the helper's own header carries the same promise: "It exits 0 for ANY produced outcome … and non-zero ONLY for its own usage/operational errors."
The header's second clause already accommodates an operational exit; the architecture doc's narrower "usage errors" does not. What conflicts in both is the *first* clause — a `passed` review is a produced outcome, and a failed write now exits non-zero instead of reporting it. Amend that clause in both, and state plainly for callers that a completed review can now be discarded by a post-review write failure. Leaving either as-is is not an option: the doc is the downstream adoption boundary Roubtec/agent-skills reads, and a header that contradicts it is the next reader's confusion.
- Name the exit status rather than inheriting it by analogy. A failed write is not a usage problem — the invocation was valid and the filesystem gave out afterwards — so it exits 70, the helper's existing operational-failure status, and not `EX_USAGE` (64) by analogy with `ensure_private_dir`, whose 64 is right for its own case because an artifact root that does not enforce modes is a bad `--artifact-root` the caller chose. This path introduces no new exit-64 case, so it must not route through `die_usage`, whose "Try: peer-review-run --provider …" synopsis would reprint the required flags for an invocation that was well-formed. Say what actually failed instead.
- The create must be `O_CREAT|O_EXCL`, and the two mechanisms that look equivalent are not. The helper writes this file unsandboxed into the attempt directory — the one directory the peer is handed a writable target inside, at the same UID — and the descendant that makes that live is not hypothetical: tasks 029d and 029e suppress further *attempts* when reaping cannot confirm the tree is gone, but neither kills the survivor, so an attempt that reaps with only a warning and still parses a verdict reaches this step with a process from its own provider tree running. `test ! -e` follows symlinks, so a dangling one reads as absent and the write creates the attacker's file out of tree. `set -C` (`noclobber`) is the trap worth naming, because it looks like the real thing: it `stat()`s first and adds `O_EXCL` only when that `stat` *fails*, so it writes through an existing non-regular target — silently through a `/dev/null` symlink, by blocking on a FIFO. Only `O_CREAT|O_EXCL` refuses every shape with `EEXIST`, symlinks included whatever they point at, because POSIX requires the pair to fail on the link itself rather than resolve it. Which fixture catches which mechanism is stated once, in the criteria, rather than argued twice.
- Two residuals, stated rather than papered over, because a fail-closed contract that overstates its reach is worse than one that names its edge. Together they mean the guarantee is against a *standing* obstacle at the path, not against an actively racing same-UID descendant; write it that way in the header rather than as an unqualified fail-closed promise.
  - **`O_EXCL` protects the final path component only.** A same-UID survivor that renames the attempt directory and puts a symlink in its place still redirects the create, because every parent component is resolved normally. Closing that means binding the create to a directory descriptor opened once and verified by `st_dev`/`st_ino` against the directory the helper made, then creating with `dir_fd`. This task does **not** require it, on the reasoning that settled the mode question: `prompt.txt`, `provider.stdout`, `provider.stderr`, `codex-last-message.txt`, and `meta.json` are all written by path into that same directory — `meta.json` after the verdict is parsed, so it shares this exact exposure window — and hardening `reviewFile` alone would make it the single fortified file among unprotected peers while an attacker holding the directory already owns all of them. Revisit only if the attempt directory is hardened as a whole.
  - **The emitted path can be swapped after the helper exits**, or the file appended to between the read-back and result emission — the same-UID writer the helper already documents as unstoppable. Composed with the first residual, the honest worst case is a `passed` result whose `reviewFile` no longer resolves to the bytes that were verified.
This makes the **interpreter** a hard precondition of the helper, and that has to be reconciled with the degradation rule above rather than left to collide with it. The two cannot both stand as first written: a run with no `python3` cannot both "degrade to `model:null` and carry on" and "fail closed at 70 for want of a review file", because the second discards the very result the first promises. Split them along the line that actually holds:
  - **The interpreter is required, and is checked up front.** Preflight `python3` in the same spirit as the existing `jq` check, before the provider is launched, and exit 70 if it is missing. Not `die_usage`/64 — a missing interpreter is operational rather than a malformed invocation, so the "no new exit-64 case" clause above stands and the `jq` precedent's 64 is not propagated. Preflighting is the whole point: discovering it after a completed review is what throws away work nobody can get back, and a run that cannot produce a `reviewFile` should never have paid a provider.
  - **`tomllib` alone may be absent, and only that degrades.** `tomllib` arrived in 3.11, so an interpreter that lacks it is the reachable case and the one the degradation rule is really about. Narrow that rule to it: an unimportable `tomllib` warns, omits `-m`, and reports `model:null`, exactly as before.
Python 3 is baked into the image this helper ships in, so the precondition is documented rather than a live degradation path — but say so in the header, since it is a new hard dependency and a new way for an invocation to fail.
- Callers read the path from the result and must not construct provider-specific paths, inspect `provider.stdout`, know Codex's final-message filename, or parse provider-native JSON.
- Preserve `artifactDir` unchanged as the returned final-attempt directory containing that attempt's provider-native artifacts; earlier retry-attempt directories remain siblings under the existing parent session tree, and the normalized review file inside the returned `artifactDir` is an additional stable consumption surface rather than a replacement for diagnostic evidence.

## Implementation notes

- Grow the header's `--model` paragraph to describe root configured-model resolution and degraded fallback, then extend the line range in `usage()` so `--help` prints the complete header rather than truncating mid-sentence.
- Resolve the configured model in the strength-knob block before any artifact/session path is created; do not defer it to `build_cmd_codex()` or temporarily run Codex without isolation to discover it.
- Use Python 3 standard-library `tomllib` only to classify the root `model`, `profile`, and `model_provider` keys. Do not inspect `[profiles.*]` or `[model_providers.*]`, derive any configuration from them, or forward them — "leave them unread" is not the requirement and is not achievable, since `tomllib` parses the whole document by construction. Also do not forward profiles, provider definitions, project trust, hooks, MCP servers, approval policy, sandbox settings, instructions, or any other user-config value. An unimportable `tomllib`, or a parse failure, takes the documented degraded path rather than failing the review helper; the interpreter's own absence is the preflight case above instead.
- Do the opening inside that same interpreter rather than shelling the file in. `os.open(path, os.O_RDONLY | os.O_NONBLOCK)`, `os.fstat` on the returned descriptor, `stat.S_ISREG` or degrade, then read from that descriptor, looping until `cap + 1` bytes are in hand or EOF is reached, whichever comes first — a regular-file `read()` may legitimately return short, so a single call is not enough — and reject the file unparsed if the cap was exceeded. One descriptor from classification to parse, so nothing is re-resolved by path in between. `tomllib.load()` on a file object opened the ordinary way is what reintroduces the blocking open, and a shell-side `[ -f ]` precheck is the check-then-act shape the requirement rejects; the helper's existing `[ -f "$PROMPT_FILE" ]` guard is a caller-supplied path outside the peer's reach and is not a precedent for this one.
- Feed the parser correctly: `tomllib.loads()` takes `str`, not `bytes`, and handing it the buffer raises `TypeError` — which the degraded path would then swallow, turning **every** valid configured model into a silent `model:null` while the whole feature reports as working. Decode the bounded buffer as strict UTF-8 and call `tomllib.loads()` on the result, or hand `tomllib.load()` an `io.BytesIO` over it. TOML is UTF-8 by definition, so route a `UnicodeDecodeError` to the same degraded path as a parse failure.
- Pass the isolation flag on the interpreter invocation itself (`python3 -I -c …`), and treat it as load-bearing when reviewing the diff: dropping it is a silent reintroduction of arbitrary code execution from the reviewed tree, not a style regression. Isolated mode also suppresses `PYTHONPATH` and user site-packages, so no ambient interpreter configuration can substitute a parser either.
- Treat the parsed model as data and append it through the existing Bash argv array so whitespace, quotes, or shell metacharacters cannot become shell syntax.
- Preserve precedence: explicit CLI model, then a usable root configured Codex model only when neither a root profile nor a root model provider is selected, then the bare Codex CLI default with honest warning/null reporting for unsupported or degraded configured selection.
- Preserve the existing effort floor and validation independently of model resolution; a configured `model_reasoning_effort` must not override the helper's default or caller-selected `--effort`.
- Keep config lookup outside the reviewed worktree and do not copy the config or its unrelated contents into retained attempt artifacts or diagnostics.
- Normalize the already-parsed final provider message into a new file inside the final attempt's returned `artifactDir`, by the single-invocation writer specified under "Provider-neutral review payload" — that bullet is the one statement of the flow and is not restated here — before constructing a `passed` or `issues` terminal result. A refused creation and an unprovable content both exit 70: the invocation was well-formed and either the path was taken from under the helper or the bytes did not land. Retain earlier attempts as sibling directories under the existing session parent, and do not make the stable payload path an alias for undocumented provider-native files.
- Give every Codex-provider test case a harness-owned empty `CODEX_HOME` by default, with case-specific `config.toml` fixtures only where configuration behavior is under test, so neither the developer's rolling `/model` selection nor any other ambient `~/.codex/config.toml` value can change existing or new assertions.
- Use fixture-only model names in tests so neither implementation nor documentation acquires a dated production model pin.

## Acceptance criteria

- A Codex-provider invocation without `--model` reads a valid configured root model only when neither root `profile` nor root `model_provider` is present, passes that exact value as one `-m` argument despite `--ignore-user-config`, and reports it in `.model`.
- The same invocation reports the independently requested or defaulted reasoning level in `.effort` and passes the matching `model_reasoning_effort` override.
- An explicit `--model` wins over configuration, bypasses config lookup entirely, and is the only model sent to the provider. "Bypasses" needs its own fixture or it asserts nothing: an implementation that parses the config and discards the result satisfies both other clauses. Run the explicit-model case against a config that would degrade *loudly* — malformed TOML, or a FIFO symlink under an outer `timeout` — and assert **no** degradation warning on stderr and no hang. That absence is the only black-box evidence the lookup was skipped.
- A config that is a symlink whose final target is an ordinary regular file is **accepted** and its model applied. This positive case is what stops the classification rule from being implemented as `O_NOFOLLOW` or an `lstat` test, which passes every negative fixture — the directly-created FIFO, the `/dev/zero` symlink, the over-cap file — while rejecting ordinary symlinked user state that the rule above explicitly requires be followed.
- Root `profile` and `model_provider` are rejected on **presence**, not truthiness: fixtures with `profile = ""`, `profile = false`, and a non-string `model_provider` each still degrade to `model:null` with the warning. A naive `if config.get("profile")` forwards the model for every one of them, and no fixture carrying only ordinary non-empty strings can catch it.
- Missing config and a valid config without a root model, root profile, or root model provider preserve the current no-`-m`, `model:null` fallback.
- An active root `profile`, any explicit root `model_provider`, an unimportable `tomllib`, and existing but unreadable, malformed, empty, non-string, or flag-shaped root model values launch without `-m`, report `model:null`, and emit a clear stderr warning; resolving configuration never invokes the provider as a discovery mechanism.

- Provider-degradation tests include root `model_provider` fixtures backed by `[model_providers.*]` definitions and assert that nothing from those definitions reaches provider argv, that no explicit provider is treated as safe, and that the helper warns, omits `-m`, and reports `model:null`. - The short-I/O rules are proved rather than assumed. A single `os.write` and a single `os.read` behave identically to looped ones on ordinary regular files, so every other fixture here passes without them and the truncation case proves only that the comparison exists, not that a legal short syscall is survived. Add injections that return short progress **once** — one on the writer's write, one on its read-back, one on the config read — and assert the run still completes normally with exact content and the expected `.model`. Without these three the looping requirements are decoration.
- The cap boundary is asserted from both sides, because `>=` and `>` are equally easy to write and only one matches the rule: a valid config of exactly the cap in bytes is accepted and its model applied, and one byte more degrades to `model:null` with the size warning.
- A `${CODEX_HOME}/config.toml` that is a FIFO, one that is a symlink to an unbounded character device such as `/dev/zero`, and one regular file larger than the stated cap each take the degraded path — no `-m`, `model:null`, stderr warning — and the invocation still terminates. Bound the assertion rather than trusting it: run these cases under an outer `timeout`, so a blocking `open()` or an unbounded read fails the case instead of hanging the suite. Pair the `/dev/zero` case with a `ulimit -v` in its own subshell as well — an uncapped read there allocates as fast as memory allows and could OOM the runner before the `timeout` fires, and the resulting `MemoryError` would otherwise degrade to `model:null` and satisfy the assertion for the wrong reason, so require the warning to name a *type* rejection rather than any failure. The FIFO and `/dev/zero` fixtures fail loudly against a naive implementation, because the outer `timeout` is a real discriminator there. The over-cap case has no such property for free and must be built to have one: any over-cap fixture small enough for a hermetic suite is also read to EOF in milliseconds, so an uncapped implementation stays well inside the `timeout`, and if the padding also breaks the parse it degrades to `model:null` with a warning and passes the case for the wrong reason.
Build it so the two implementations disagree on the *result*: make the fixture valid TOML that defines a usable root `model` and pad it with comment lines to strictly more than the implementation's stated cap — a few hundred KiB against a cap in that range, rather than manufacturing a huge file. A capped implementation rejects it unread and reports `model:null` with a warning naming a size or cap rejection; an uncapped one parses it happily and reports the fixture's model, failing the criterion on the assertion that matters.

This is the regression detector for the isolation flag: without it the case fails loudly. Give the shadow an observable side effect — have it write a marker file — and assert that marker's absence, so non-execution is proved directly rather than inferred from the resolved model value.

- Every `passed` or `issues` result from either provider has a non-null absolute `.reviewFile` equal to `<artifactDir>/review.txt`, whose plain-text contents are the complete provider review message used for the verdict; callers can relay it without inspecting native artifacts or parsing provider formats.
- A fixture whose mode set on the review file **fails**, and one where it **succeeds but applies the wrong mode**, each still produce the normal `passed` or `issues` result, with a clear stderr warning and a usable `reviewFile`; no mode failure aborts a completed review. Both variants must be defined concretely, because the obvious spellings have no observable once the umask is cleared: an injection that merely *skips* `fchmod` leaves the file at the create mode, which is already 0600, so `fstat` confirms it and nothing warns. So make the first variant raise or report an error, and the second apply a different mode (0644 serves) while reporting success, which is what puts the `fstat` mismatch branch under test. The mode is now `fchmod` on the writer's own descriptor rather than an external `chmod`, so a `PATH` shim cannot reach it: drive this from an env-gated injection inside the writer program, exactly as the truncation case does. That is also what keeps it scoped — an external `chmod` shim would trip `ensure_private_dir` on the session or attempt directory first and exit 64 there, which is that function's existing behavior and not this path's.
- A fixture proves the created mode does not depend on the ambient umask. Apply that umask as a further **env-gated injection inside the writer program** — `os.umask(0o200)` at the top of it, ahead of the production clear-and-create — composed with the *failing* variant of the mode injection above, then assert the review file is still 0600 and readable and the result is still `passed`/`issues` with a warning.
Both halves of that construction are load-bearing, and the obvious simpler spellings are each broken in a different direction:
  - **Not an ambient umask on the helper invocation.** Measured against the real helper: every owner-bit mask that would change the create mode also kills the run long before the review file exists — a write-masking umask dies at the `provider.stdout` redirect and at `meta.json`, and a read-masking one leaves artifacts the final-message extraction cannot read — while every mask under which the run reaches `passed` (`0077`, `0100`, `0000`) leaves the create at 0600 and discriminates nothing. There is no ambient mask that both discriminates and completes. Setting it inside the writer, which is its own process, leaves the helper's artifact writes untouched.
  - **Not a skipped mode set.** With the umask cleared the create already yields 0600, so a skipped mode set warns about nothing: a correct implementation would fail the warning assertion while only the buggy one satisfies it, making the criterion passable exclusively by the bug it exists to catch. It has to *fail*.
Composed this way the discrimination is exact: a correct writer clears the injected mask and the file lands 0600; a naive one lands 0400 and fails the assertion; and either way the outcome is `passed`/`issues` carrying the mode warning.
If the third injection is judged not worth its cost, the honest alternative is to say the created mode is not black-box constructible and demote it to a diff-review item, as the ordering and never-inspects clauses already are — but do not substitute an ambient umask, which is how this criterion has now been wrong twice. The composition is the whole criterion, because an unconditional `fchmod` to 0600 succeeds on a file you own whatever its current mode: on its own the umask case ends at 0600 under every mask, clear or no clear, and cannot fail. Compose the two and the masks separate properly — without the clear, `0777` leaves `0000`, `0200` leaves `0400`, `0400` leaves `0200`, each an unreadable or unwritable payload behind a successful result — while `0077` remains vacuous even composed, since it never touches the owner bits.
This is exactly the scenario the mode rule above describes conditionally: a mode step that warns and continues, over a file the create left unusable. Only the injection makes that condition real.
- A fixture whose writer invocation fails outright, and a separate fixture whose write reports success but silently truncates, both prove the same fail-closed behavior, exiting 70, so an empty or partial `reviewFile` can never ship inside a successful result. The truncating case is what proves the content read-back exists; a status-only implementation passes the first fixture and fails this one.
Both need a named mechanism, and the task is not complete until one is implemented and used, because a full or read-only filesystem is not constructible from the existing unprivileged hermetic harness. Moving the writer into an external `python3` invocation changes which mechanism each case needs, and the two cases genuinely differ now, so name them separately rather than reaching for one tool three times:
  - The **failed write** and the **race** cases can be driven by an argv-discriminating `python3` shim on the harness `PATH`, with no production hook at all — the same discipline task 029d applies to its survivor case, and the same argv discrimination the `tomllib` criterion above requires, since a blanket stub would also break the parser.
  - The **silent truncation** and **mode-failure** cases cannot. Each tests behavior that now lives *inside* the very invocation a shim would replace — the read-back that catches a short write, and the `fchmod`/`fstat` that warns and continues — so a shim proves nothing about the shipped code. Both need env-gated injection points inside the writer program itself: one truncating between the write and the read-back, and one for the mode set in each of its two viable forms — failing outright, or succeeding while applying a different mode. Not a skipped mode set, which the criteria above explain has no observable once the umask is cleared.
Every injection point this task adds to the writer — truncation, mode, umask, and the short-write and short-read gates — ships inside a production helper, so each must be **inert in normal operation**, gated on an environment variable that is unset in every non-test path. Task 029d states the same requirement for its own injection; this one carries more of them, in the one place whose whole contract is fail-closed.
An implementer who reaches for a shim for all three ships a truncation test that asserts nothing.
What is ruled out is a **pre-created** obstacle standing in for either: a fake provider that plants the review path as a directory or a `/dev/null` symlink *before* the helper looks is refused at the open, which is the separate refusal requirement below, and using it here would leave the write path itself untested. Planting the same shape *inside* the race window is a different fixture testing a different property, and the race case below does exactly that.
- A fixture in which the peer pre-creates the review path — `<artifactDir>/review.txt`, the basename the contract pins — proves the helper refuses rather than writing through it. Cover six shapes; what each is worth depends entirely on whether writing through it is *observable*, so name the observable per shape rather than asserting a bare exit 70 — which every shape produces anyway, since a writer that follows an obstacle then fails its own read-back and exits 70 too.
  - A regular file, a directory, and a symlink to a regular file outside the attempt directory: refused by all three mechanisms, so they discriminate between none of them and are coverage only. The symlink shape still gets a target assertion — that file's contents must be unchanged — which costs a line and catches a writer that follows the link and overwrites it.
  - **A dangling symlink pointing outside the attempt directory** — the discriminator against `test ! -e`, which reports it absent. Observable: the target file is created and carries the prose. Assert it does not exist.
  - **A symlink to a harness-made FIFO, with no reader attached** — the discriminator against `set -C`. Observable: the helper blocks in `open()`. Run it under an outer `timeout` and assert termination plus the refusal diagnostic. Leave the read end closed deliberately: attach a reader and the small prose fits the pipe buffer, the wrong writer no longer blocks, and the `timeout` stops discriminating anything.
  - **A symlink to `/dev/null`** — coverage, not a discriminator, and say so. Writing through it leaves nothing to inspect and still ends at exit 70 via the read-back, so it separates no mechanism the two shapes above do not already separate.
The refusal has to be distinguishable from a content failure for any of this to bite: require the diagnostic to name a refused creation rather than unprovable content, and assert that text, so a fixture cannot pass on an exit 70 that arrived by the wrong route.
- A further case adds the **race** dimension the pre-created shapes cannot reach: they are all planted before the helper looks, so they catch a mechanism weak against a *standing* obstacle. Build it with the `python3` shim named above and no production hook: on the writer invocation the shim plants the review path as a symlink to a non-regular target (`/dev/null` or a FIFO), then `exec`s the real interpreter with the same argv. That fires after any shell-side precheck and before the real open, so a shell-side `[ ! -e "$f" ] && python3 …` writes through while an `O_EXCL` create fails `EEXIST`. Assert the fail-closed exit **with the refused-creation diagnostic**, the untouched target, and — for the FIFO variant, under an outer `timeout` — that the helper terminated at all. The diagnostic is not optional here: plant a `/dev/null` symlink and a shell-side `[ ! -e "$f" ] && python3 …` writes through it, fails its own read-back, and exits 70 with the *content* diagnostic, satisfying every other assertion in this list. An implementation that never invokes `python3` fails the same assertion for want of the exit, so there is no vacuous pass.
Be precise about what this case does and does not prove, because it is easy to over-read. The shim plants *before* the writer program starts, so a check-then-act **inside** that program sees the obstacle at its own check and refuses — passing this case without ever using `O_EXCL`. That shape is caught instead by the pre-created **dangling symlink** above, which `os.path.exists()` reports as absent exactly as `[ -e ]` does, so a non-atomic in-program open follows it and creates the target out of tree. Between them the two fixtures cover check-then-act at either level; what no black-box fixture can catch is a genuine in-program window, and that is closed by requiring `O_CREAT|O_EXCL` and reviewing the diff for it, not by a test.
