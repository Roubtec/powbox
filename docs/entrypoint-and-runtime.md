# Entrypoint and runtime internals

Agent-facing reference for container startup: the entrypoint chain, the per-agent seeding hooks, the ordering constraints between them, host-workspace permission healing, the mid-session pnpm/shadow wrapper, and the deliberate bash/zsh split.
Routed from [AGENTS.md](../AGENTS.md); see [architecture.md](architecture.md) for the image/identity/volume picture this startup sequence sits inside.

## Entrypoint and Runtime

- `entrypoint-agent.sh` is the image ENTRYPOINT. It reads `PRIMARY_AGENT` (`claude` | `codex`, defaulting to `claude` for an unknown value), holds the agent registry (`agent_env` maps each agent to its `AGENT_CONFIG_DIR`, `AGENT_SETUP_HOOK`, `AGENT_SEED_DIR`, name, binary, autonomy flag, instruction file, label, and one-shot invocation fragment `AGENT_ONESHOT` — the non-interactive form rendered under the peer's bullet in the instruction file), then seeds every agent and execs `entrypoint-core.sh` for the primary. Adding a harness = extend `agent_env` and `ALL_AGENTS`.
- It seeds in two passes: each non-primary agent is seeded directly (export its `AGENT_*` vars, run its hook); the primary agent's env is exported and handed to `entrypoint-core.sh`, which runs the primary's hook (so it is not run twice) alongside firewall/git/shadow setup before execing the CMD.
- Each per-agent hook (`entrypoint-claude-hook.sh`, `entrypoint-codex-hook.sh`) is run in full for every agent. Each writes only into its own config dir (`~/.claude` vs `~/.codex`/`~/.agents`), so there is no conflict; hooks are idempotent, no-clobber, and build-epoch-gated, and read their baked assets from `AGENT_SEED_DIR`.
- `entrypoint-core.sh` is a wrapper-style entrypoint that must end with `exec "$@"` and is unchanged by the unification (still runs the single `AGENT_SETUP_HOOK`).
- The shared instruction template is rendered via `envsubst` with agent-specific variables (including `${AGENT_PEERS}`, the registry-derived peer list for the "Delegating to another agent" section).
- `gh auth setup-git` runs from `$HOME` (not the workspace) and failure is non-fatal. On success it also adds a container-global `url."https://github.com/".insteadOf "git@github.com:"` rewrite (written to the ephemeral `GIT_CONFIG_GLOBAL`, never the host) so SSH-form `origin` remotes push/fetch over HTTPS+gh without rewriting the host repo.
- **Claude skills plugin channel (`dev-skills@roubtec`).** The 8 shared skills are no longer image-baked for Claude (task 015b); the Claude hook instead installs and keeps current the `dev-skills@roubtec` plugin (from the `Roubtec/agent-skills` marketplace) so a container consumes them through the same channel colleagues use. The work lives in `seed-claude-plugins.sh`, invoked from `entrypoint-claude-hook.sh` when Claude is the **primary** agent (**synchronously**, and post-firewall — the primary's hook runs from `entrypoint-core.sh` after `init-firewall.sh`; stdout stays on the terminal for the cold path's few concise status lines — an "installing…" line then a terminal "ready…"/"still installing…" line; stderr and all debug go to `$AGENT_CONFIG_DIR/.powbox-plugin-bootstrap.log`), outside the build-epoch gate so keep-current runs every start. The `Roubtec/agent-skills` repo is **public**, so `claude plugin marketplace add` clones it **anonymously** over HTTPS — no git credential helper, so there is no dependency on the `gh auth setup-git` step (above) and no auth-ordering race; the historical "detach + wait for the helper" scaffolding is gone (task 015g). The script splits the three states so **only the cold case runs synchronously** (task 015g): on a **cold** (fresh) claude-config volume the plugin is `absent`, so it is installed in the **foreground before the entrypoint `exec`s claude** — bounded by `POWBOX_PLUGIN_COLD_INSTALL_BOUND` (~50s), a short `POWBOX_PLUGIN_COLD_LOCK_WAIT` (~15s) for a peer's lock, and up to two `POWBOX_PLUGIN_LIST_TIMEOUT`-bounded `claude plugin list` state queries (the routing query plus the authoritative one under the lock, ~2×30s), for a worst-case start delay of roughly `COLD_INSTALL_BOUND + COLD_LOCK_WAIT + 2×LIST_TIMEOUT` — so the `/dev-skills:*` skills are live in the **first session** with no `/reload-plugins` or restart (Claude enumerates plugins once at session start, so an install that lands after that is otherwise invisible until a reload). If that bounded install times out or can't grab the lock in time, the **remaining work is detached to a background self-heal** (`setsid`, re-exec with `POWBOX_PLUGIN_BACKGROUND=1`, patient bounds, log-only, never re-spawns) and the entrypoint proceeds — so a slow/offline cold start is **never wedged**; worst case the skills simply arrive a session late, exactly today's behavior. This synchronous foreground cold install runs **only when Claude is the primary agent** (its hook then runs from `entrypoint-core.sh`, *after* `init-firewall.sh`, so the network ops are correctly ordered behind the firewall). When Claude is the **non-primary** agent — e.g. `PRIMARY_AGENT=codex`, where the Claude hook runs during `entrypoint-agent.sh`'s non-primary seeding, *before* the firewall is initialized — that hook **skips the plugin entirely** (touching the network there would run ahead of the firewall). Instead `entrypoint-core.sh`, immediately **after** `init-firewall.sh`, re-invokes `seed-claude-plugins.sh` **detached** with `POWBOX_PLUGIN_BACKGROUND=1` (pointing the log at Claude's `CLAUDE_CONFIG_DIR`): this converges the non-primary Claude plugin from the patient background branch, so its network ops are both **ordered after the firewall** and kept **off the primary (Codex) prompt's critical path**; the skills self-heal onto the shared claude-config volume for the next Claude session. On a **warm** volume the plugin is `enabled`, so the script **self-backgrounds** the cheap keep-current and returns immediately, adding **no start latency**: `marketplace update roubtec` refreshes the catalog and `plugin update dev-skills@roubtec` pulls the new commit-SHA version into the installed plugin cache (the CLI splits these: a marketplace update alone only refreshes listings). A keep-current that pulls a newer commit only takes effect **next session** (plugins load once at startup); this one-session update staleness is **accepted**. A deliberately **disabled** plugin is **respected** (never auto-re-enabled). Skills arrive namespaced as `/dev-skills:<name>` (e.g. `/dev-skills:address-review`); model-side Skill-tool matching by description is unaffected. Per-marketplace auto-update is left OFF (its on-disk schema is undocumented); opt in once per volume via `/plugin`. An offline cold start logs a skip and **self-heals** on a later online start. Because that claude-config volume is a *single global* volume shared by every powbox container, the bootstrap serializes its check-then-mutate with an flock so concurrent container starts can't race the same `~/.claude/plugins` state (the synchronous cold path waits only the short `COLD_LOCK_WAIT` so a peer bootstrap can never block startup; the background self-heal waits the full `POWBOX_PLUGIN_LOCK_WAIT`), and it exports `CLAUDE_CODE_PLUGIN_KEEP_MARKETPLACE_ON_FAILURE=1` so an offline refresh keeps the existing marketplace clone instead of wiping it.
- Before the git/`safe.directory` steps, `entrypoint-core.sh` write-probes each dir-mounted `/workspace/<slug>` as `node` and, for any it cannot write, `sudo`s `fix-workspace-perms.sh`, which `chown`s it to `node` when the workspace root is owned by `root` (uid 0) — the common native-Linux case (a repo under `/root`, or a host running powbox as root), where the agent otherwise gets EACCES on every `git`/edit. The write probe alone misses a **mixed-ownership** workspace — a *node-owned* root that nonetheless hides nested `root`-owned files, which arises when a host operation runs as root against a live bind mount (most often `sudo git pull`, which re-owns to uid 0 only the paths it writes — new `.git/objects/*`, refs, changed working-tree files — leaving the top dir node-owned), so the agent can write the root yet `git commit`/`add` still fail with `insufficient permission for adding an object to repository database`. So besides the probe, the entrypoint runs a short-circuiting `find … -uid 0 -print -quit` (with the same mountpoint prune as below) over each node-writable workspace and hands any that contains a uid-0 entry to the same helper; the helper now acts on a root owned by **root or node** and re-owns only the `find -uid 0` entries (for a root-owned root that is the whole tree; for a node-owned root just the nested uid-0 entries — the root, already node, is untouched). A workspace whose root is owned by some *other* non-root, non-node host uid is refused with remedies (chown the repo to uid 1000 on the host, or relaunch in `--isolated` mode), never silently chowned, so a real host user is never locked out of their own repo. The probe creates its temp file with `mktemp` (O_EXCL, random name) rather than a predictable path, so a planted symlink in an untrusted workspace can't make it truncate an outside target as node. It is probe-/scan-gated, so it no-ops on Windows/WSL (FUSE bind mounts already honour node's writes) and on uid-matched hosts with no nested uid-0 entries; self-hosted mode and the detached image-store writer are exempt. The helper canonicalizes each argument and only acts on a direct `/workspace/<slug>` child; the chown (and the entrypoint's detection scan) prunes the real mountpoints nested under the workspace (from `/proc/self/mountinfo`), with `find -xdev` only as a backstop, so it never descends into the nested `node_modules`/`.worktrees` volume mounts — `-xdev` alone is insufficient when a volume shares the bind-mount source's filesystem (same st_dev). The recursive chown matches only root-owned entries (`find -uid 0`), so a file or directory nested inside a claimed tree but owned by another host uid keeps its owner rather than being re-owned to node — the same protection the root-level refusal gives, applied per-entry.
- **Sensitive-source refusal.** Before any of the above, both the heal decision (`heal-workspace-perms.sh`) and the privileged helper (`fix-workspace-perms.sh`) refuse outright to chown a workspace whose **host bind-mount source** is a system or home directory — `/`, `/root`, `/home/<user>`, `/Users/<user>`, the launching user's `$HOME`, or a bare FHS root like `/etc`/`/usr`/`/var`/`/opt`, plus any SSH config directory (a path ending in `/.ssh`, e.g. `/home/alice/.ssh` or `/root/.ssh`) — chowning just `~/.ssh` and its `authorized_keys` to node is itself enough to trip StrictModes even when the home dir stays root-owned (a project *nested* under a system/home root — `/opt/app`, `/var/www/html`, `/home/alice/code/app` — still heals normally). This guards a real incident: a `cc`/`cx` accidentally launched from `~` (e.g. `/root` on a VPS) bind-mounts the whole home tree as the "project", and the heal would then recursively chown it to node — re-owning `~/.ssh` **and its parent**, which breaks OpenSSH's StrictModes ownership chain so `sshd` refuses `~/.ssh/authorized_keys` and locks you out of the host (recoverable only via an out-of-band console). When the source is sensitive the workspace is **mounted but not chowned**, with a loud warning, so an accidental launch is a recoverable inconvenience (node may be unable to write that tree) instead of a host lockout. The shared predicate lives in `sensitive-host-path.sh` (sourced by both). Both classify on the launcher's **true absolute host source** rather than the layout-dependent mountinfo value: at trusted startup the entrypoint records each dir-mounted workspace's `POWBOX_WORKSPACE_HOST_PATH` (`pwd -P`-resolved) against its container mountpoint in a small per-boot marker map (`/run/powbox/workspace-sources`, node-writable), and `powbox_resolve_host_src` resolves a mount's source most-authoritative-first: (1) that marker map, (2) the launcher env for the one mount it names via `POWBOX_WORKSPACE_DIR` (a fallback if the marker could not be written; inert under `sudo`'s `env_reset`), (3) `/proc/self/mountinfo` field 4 as the env-independent last resort. This is what closes the two mountinfo-only gaps (task 009): a **direct** `sudo fix-workspace-perms.sh` refuses a `/home/<user>` bind on a separate-mount layout — where mountinfo field 4 reads back as the shallow `/alice` — because the marker (a *file*, surviving `env_reset`) records the true `/home/alice` (Gap A); and the heal **heals** a root-owned checkout whose bind source is a whole-filesystem mount — where mountinfo field 4 is a degenerate `/` — because the recorded true source (`/projects`) is authoritative over that degenerate value rather than OR-ed with it (Gap B). Mountinfo remains a working fallback when no launcher signal was recorded. The predicate and the mountinfo lookup are unit-tested by `scripts/test-sensitive-host-path.sh`; the live heal-skip/heal and fix-refusal (including both true-source cases) are smoke-tested by the dir-mount stage.
- Self-hosted (`--isolated`) clone seeding runs **after** the `gh auth` step (so a private clone has credentials) and **before** the shadow/pnpm steps, via the base-baked `seed-workspace.sh` (gated on `POWBOX_SELF_HOSTED=1`; a no-op otherwise, including the image-store writer role). It clones `POWBOX_CLONE_REPO`'s default branch into `POWBOX_WORKSPACE_DIR`, then applies the optional `POWBOX_CLONE_REF` as a **post-clone `git checkout`** (so it accepts a branch, tag, or raw commit SHA, and an unresolvable ref degrades to a warning + stay-on-default rather than aborting the clone), and skips the whole thing when a `.git` already exists (reuse — the agent owns its branches/worktrees; the ref is not re-applied on reuse). `--reclone` is **not** a frozen env flag (that would re-wipe the agent's work on every restart): it is a one-shot launcher action that empties the kept `agent-ws-*` volume and recreates the container, so the entrypoint then sees an empty dir and clones fresh. There is deliberately **no clone/auth failsafe and no retry**: on any failure it prints a loud announcement of the three remedies (use dir-mounted mode / `gh auth login` here / seed the shared gh volume) and `entrypoint-core.sh` `exec`s a plain `zsh` rather than execing the agent into an empty workspace.
- `safe.directory`/`core.filemode` handling is left as-is (harmless on a node-owned clone).
- Workspace shadow mounts run after git setup, so any shadow logic must not assume an earlier ordering. `shadow-mounts.sh` is **skipped** in self-hosted mode (no host FS to shadow, and a tmpfs would break the single-mount hardlinking); `wt-bootstrap` likewise branches its root-safety check on `POWBOX_SELF_HOSTED` (the worktree roots are plain subdirs of the one workspace volume, not per-dir mounts).
- Startup shadow detection only sees the subpackages that exist at container start, so a package scaffolded mid-session would have its `node_modules` populated straight onto the host bind mount before any re-shadow. To close that race, `pnpm`/`pn` are replaced (base image, after `npm install -g pnpm`) with `docker/shared/pnpm-shadow-wrapper.sh`: for node_modules-writing subcommands (`install`/`add`/`update`/… — detected by scanning all args, since global flags can precede the subcommand) it runs `shadow-refresh.sh` scoped to the `/workspace/<slug>` enclosing pnpm's *effective* directory — honoring `-C, --dir <dir>`, so a `pnpm -C /workspace/<repo> install` invoked from outside `/workspace` still re-shadows the right project — *before* exec'ing the real `/usr/local/lib/node_modules/pnpm/bin/pnpm.mjs`. It is a no-op when that effective directory is outside `/workspace` and in self-hosted mode (`POWBOX_SELF_HOSTED`), mirroring `shadow-mounts.sh`, and always exec's pnpm so a shadow failure never blocks the command. `pnpx`/`pnx` (dlx) are left unwrapped — they don't write workspace `node_modules`. The same wrapper also closes the launch-time gate's residual hole (task 002b): a folder launched as **non-dev** (no `package.json`/`pnpm-workspace.yaml`/committed `.powbox.yml`/`.powbox.local.yml` with a top-level `shadow:` key, so the launcher mounts no `agent-nm-*` root volume and sets no `PNPM_STORE_DIR`; a ctx-only local config does not enter this gate) that gains a `package.json` mid-session would, on a **root** install, write `node_modules` straight onto the host bind mount — the very host litter the gate exists to prevent, and which the wrapper cannot retrofit a mount for. So before such an install it prints exactly one loud stderr warning (then still proceeds) telling the user to relaunch the agent (the folder now has a `package.json`, so the next launch mounts an isolated volume). The regression is detected via `<workspace>/node_modules` not being a mountpoint **plus** an empty `PNPM_STORE_DIR` (the launcher sets it only when it mounted the volume) and the effective dir being the workspace root, so a self-hosted run, an already-mounted dir-mounted dev project, and a subpackage install never trip it; it is unit-tested by `scripts/test-pnpm-shadow-wrapper.sh`.
- Right after the pnpm store-dir step, `entrypoint-core.sh` pre-creates the launcher-pointed Go caches and the ccache compiler cache (`GOMODCACHE`/`GOCACHE`/`CCACHE_DIR` env → `.worktrees/.gomodcache`/`.gocache`/`.ccache`; set for dir-mounted JS/powbox/Go projects and in self-hosted mode, omitted for non-dev folders so nothing is mkdir-ed onto a host bind mount). Plain env is all `go`/`ccache` need — no `go env -w`, no ccache config — so the guarded `mkdir` exists only to surface a bad value loudly at startup; on failure it warns and **unsets** the var, so the tool falls back to its image-default (container-ephemeral) cache path instead of failing every build. (ccache stays opt-in per build: the binary and this persistent dir are baked, but nothing interposes it into a plain `gcc`/`cmake` invocation.) `golangci-lint` is likewise a wrapper on `PATH` (`docker/shared/golangci-lint-wrapper.sh`, real binary at `/usr/local/libexec/golangci-lint`) that derives a per-worktree `GOLANGCI_LINT_CACHE` at invocation time — see [architecture.md](architecture.md) "Bundled Go toolchain" for the cache layout and rationale.
- The container's two shells are split on purpose, so the `usermod --shell /bin/zsh` and `ENV SHELL=/bin/bash` in `docker/base/Dockerfile` are not a contradiction: zsh is the human login shell (and `launch-agent --shell` execs `zsh` directly), while bash is the `$SHELL` the agent harnesses' Bash tools spawn — the models write bash/POSIX (word-splitting, 0-indexed arrays) and a non-interactive one-shot call gains nothing from zsh, so defaulting agents to zsh only wasted turns. Both rc files (`docker/shared/.bashrc`, `.zshrc`) are baked but only shape interactive sessions; `EDITOR` and `PATH` live in image `ENV` so neither shell owns them.
