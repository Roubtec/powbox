# 063 — Build an optional layer-set image between the base and the agent image

## Why this task exists

The base image carries every tool its maintainer's projects need (Go, .NET, PowerShell, Chromium, Podman, …), which is about 2.7 GB of the 5.5 GB root filesystem and irrelevant to most other users. The agreed direction is a **lean base** plus an optional, user-selectable **layer set** built on top of it, so a new user gets a small useful image out of the box and anyone can add their own toolchains without editing tracked files.

This task delivers the mechanism only: the image chain, the selector, staleness detection and the update flow. It moves **no tool** out of the base. Its one change to the base is the removal of the commit-stamped file layer, which the chain would otherwise turn into a reinstall of the whole selected set on every `all` build at a new commit (see "No commit-dependent filesystem layer in the base"). The tool moves are tasks 071 and 073; CI coverage is 065; agent-facing notes are 067; smoke composition is 069.

## Scope

**In scope:**

1. A three-image chain: `powbox-agent-base:latest` → `powbox-agent-layers:latest` (only when a set is selected) → `powbox-agent:latest`.
2. The layer-set layout under `docker/layers/`, a gitignored selector file `.powbox-layers`, and a committed `.powbox-layers.example`.
3. A committed **skeleton** `docker/layers/full/` set whose Dockerfile adds nothing yet, so the chain is exercised before any tool moves.
4. A directory digest for the selected set, recorded on the layers image and compared by the update check.
5. `agent-check-updates` / `agent-update` awareness: a `layers` row, and a rebuild path that rebuilds only the layers and agent images, from cache.
6. The base image stops carrying a commit-dependent filesystem layer: `/home/node/.powbox/base.commit` is written by the agent image's top metadata layer instead of the base Dockerfile, so a base bake at a new commit changes the base's labels and nothing else.
7. Bash and PowerShell parity for every script touched.
8. Documentation of the mechanism.

**Out of scope:**

- Moving any tool, template row or smoke probe (tasks 071, 073).
- Agent instruction notes for a layer set (task 067) and layer smoke probes (task 069).
- Stacking several sets. Exactly one set is selected, or none.
- A layers line in the in-container `powbox-provenance` helper. It prints the baked `/home/node/.powbox/*.commit` files, and a user-owned layer Dockerfile cannot be made to write one. The agent image's top metadata layer could write it from the inherited `powbox.commit.layers` label, the way this task makes it write `base.commit`, but that is left out so `powbox-provenance` and its output stay unchanged here. The layers commit is exposed host-side only, through `agent-image-info`; record that limit in `docs/skills-refresh-and-provenance.md`.
- Backward compatibility with existing images. The maintainer rebuilds; do not add migration shims.

## Context and references

- `docker/agent/Dockerfile` already starts with `ARG BASE_IMAGE=powbox-agent-base:latest` and `FROM ${BASE_IMAGE}`, and `docker-bake.hcl` passes `BASE_IMAGE` to the `agent` target. Pointing the agent at another parent needs no instruction change in that Dockerfile. Its comments and one label do describe the parent as "the base", though: the "Shared linters" comment ("Keep these above Codex so its cache parent remains the base image") and the "Provenance labels" comment on `powbox.base.image.id`. Both need rewording (see "Codex-layer provenance" below).
- `docker/agent/Dockerfile`, the top metadata `RUN`: it begins `RUN date +%s%N | tee …/build-epoch`, sits below `ARG POWBOX_COMMIT`, `ARG POWBOX_COMMIT_CODEX` and `ARG AGENT_SKILLS_COMMIT`, and writes `/home/node/.powbox/{claude,codex,agent-skills}.commit`. The comment above it says "(base.commit is inherited from the base image)". `POWBOX_COMMIT_CODEX` is the precedent for a commit that the build scripts resolve from image labels and pass in as a build argument.
- `docker/base/Dockerfile`, the end of the file: `ARG BASE_SOURCE_IMAGE`, `ARG BASE_SOURCE_DIGEST`, `ARG POWBOX_COMMIT` (under the comment "Powbox commit that built this base image. Recorded both as an inheritable label … and as a baked file readable in-container"), `ARG POWBOX_BASE_RECIPE_DIGEST` (under the "Cache-key note" comment), then the final `RUN mkdir -p /home/node/.powbox && printf '%s\n' "${POWBOX_COMMIT}" > /home/node/.powbox/base.commit`, then the closing `LABEL` block that ends with `powbox.commit.base`. That `RUN` is the only one below those four `ARG` lines. A `RUN` is keyed on every `ARG` declared above it, so it runs again at every new commit and every `-dirty` flip and gives the base a new top layer each time. Today that costs a reinstall of Codex, the linters and Claude whenever the base is baked at a new commit, and `resolve_codex_commit` relies on it (see "Codex-layer provenance").
- `docker/shared/powbox-provenance` is the only reader of `base.commit` (through `read_commit base`). The smoke drivers only probe `command -v powbox-provenance`. `agent-image-info` reads the `powbox.commit.base` label, which this task leaves alone.
- `scripts/base-source-digest.sh` and its `.ps1` sibling define the existing recipe digest (manifest `scripts/base-source-files.txt`, label `powbox.base.recipe.digest`). The new digest follows the same algorithm and the same "build-time and check-time must call one script" rule stated in that file's header.
- `commands/check-updates.sh` documents the porcelain contract in its header and emits the literal `update available` marker that `agent-update` greps for.
- `shell/powbox.sh`: `agent-update`, `_powbox_build_from_table`, `agent-full-rebuild`, `agent-image-info`. `shell/powbox.ps1` mirrors them (`agent-update`, `_Powbox-BuildFromTable`, `agent-full-rebuild`, `agent-image-info`). `agent-update --refresh` (`-Refresh`) builds target `all`, and with nothing stale it pins both binaries to their baked versions (`_powbox_build_from_table "$table" "" all`), and README "Profile Shortcuts" describes it as cached, with unchanged layers reused, and "much faster" than `agent-full-rebuild`.
- `scripts/build-image.sh`: the `TARGET` dispatch at the end of the file, `run_bake`, `ensure_base_image`, `base_image_id`, `image_label`, `resolve_codex_commit`. `scripts/build-image.ps1` mirrors it (`Invoke-Bake`, `Assert-BaseImage`, `Get-BaseImageId`, `Get-ImageLabel`, `Get-CodexCommit`).
- `docs/skills-refresh-and-provenance.md` describes the per-layer commit provenance this task must keep truthful.

## Design decisions already made

These were settled with the maintainer; implement them rather than reopening them.

- **Layout.**

  ```text
  docker/layers/full/Dockerfile     committed; the maintainer's bundle (skeleton in this task)
  docker/layers/custom/.gitkeep     committed; everything else in this directory is gitignored
  .powbox-layers                    gitignored; one line naming the selected set
  .powbox-layers.example            committed; a commented template for the selector
  ```

- **Selector.** `.powbox-layers` at the repo root. The first line that is neither blank nor a `#` comment, trimmed of whitespace and a trailing CR, is the set name. It must match `^[a-z0-9][a-z0-9._-]*$` and `docker/layers/<name>/Dockerfile` must exist. A missing or effectively empty file means **no set: the lean image**. An invalid name or a missing Dockerfile is a hard error naming the path, never a silent fallback to lean.
- **Why a file and not an environment variable.** The build, the update check and the smoke test run from different shells (bash and PowerShell) and must agree, or the update check reports permanent false staleness.
- **Build context is the set's own directory**, not the repo root. A copied set then works unchanged, and the digest covers exactly the build inputs. A set that needs a repo file keeps its own copy.
- **Layer Dockerfile contract.** It starts with `ARG BASE_IMAGE=powbox-agent-base:latest` and `FROM ${BASE_IMAGE}`, switches to `USER root` for installs, and ends with `USER node`. The base's final user is `node`, and the agent Dockerfile assumes that. Every `COPY` and `ADD` instruction carries `--chmod=<mode>`, so the mode a copied file gets in the image comes from the Dockerfile, which the digest covers, and never from the checkout, which it does not: a Windows checkout has no Unix modes at all, and Git tracks only the executable bit, so a mode read from the context is neither portable nor fully digestable. The digest step rejects a layer Dockerfile holding a `COPY` or `ADD` without `--chmod=` as a hard error naming the line, like the invalid selector under "Selector"; `docker/base/Dockerfile` already writes its helper copies this way (`COPY --chmod=755`).
- **Image name.** `powbox-agent-layers:latest`, whichever set is selected. It is deliberately not named after the `custom` directory, so an image built from `full` is not called "custom".
- **Digest.** sha256 over every regular file under the selected set directory, recursively, `.gitkeep` included: paths relative to the set directory, forward slashes, byte-sorted, same `"<sha256>  <path>\n"` buffer format as `base-source-digest`. It is content-only on purpose: Docker's build context also carries file modes and symlink targets, and a content-only digest would miss a change to either, so the contract above removes them as build inputs instead of hashing them. Modes are set by `--chmod=` in the Dockerfile, which is hashed. A symlink or any other non-regular entry under the set directory is a hard error naming the path, in both digest implementations; a set that needs a link creates it in a `RUN`. Directories are not hashed: each is represented by its files, and a `.gitkeep` is one of them, so the committed `custom/.gitkeep` and a `.gitkeep`-only subdirectory are covered like any other build input. Git commits no empty directory, so a truly empty one is never part of a committed set; it appears only by hand in a working tree, most likely in a user's gitignored `custom` set, and the digest does not police that, since a user editing a custom Dockerfile knows what their `COPY` picks up. Stamp the digest and the set name on the layers image as labels `powbox.layers.digest` and `powbox.layers.set`, plus `powbox.commit.layers` for provenance and `powbox.layers.base.id` for the currency test below (the `.Id` of the base image the layers image was built FROM, as `base_image_id` reads it). Do not confuse that label with the existing `powbox.base.image.id`: the older one sits on the **agent** image and describes the agent's own parent for the Codex-layer resolver (see "Codex-layer provenance"). With a set selected that parent is the layers image, so the two labels describe different images and hold different kinds of value. Set these from the bake target (its `labels` attribute), not from the user's Dockerfile, so a custom Dockerfile cannot omit them. The agent image inherits them from its parent; an agent built directly on the base has none, which reads as "no set".
- **Targets.** `build.sh` / `build.ps1` accept `base | layers | agent | all`.
  - `base`: base only, as today.
  - `layers`: the layers image only, always baked; ensures the base exists first, as `agent` does; errors clearly when no set is selected.
  - `agent`: ensure the base exists (as `ensure_base_image` does), or refresh it under `--pull` as the `agent)` branch does today; then ensure the layers image is **current** and bake it when it is not; then build the agent on it. With no set selected, build the agent on the base.
  - `all`: base, then layers when a set is selected (always baked), then agent. What that costs at a new commit is spelled out under "What `all` costs with a set selected".
- **What "current" means.** The layers image is current only when all of these hold: it exists; its `powbox.layers.set` and `powbox.layers.digest` labels equal the working tree's selected set and digest; and its `powbox.layers.base.id` label equals the `.Id` of the present `powbox-agent-base:latest`, read **after** the base step of the same run. Anything else bakes it, from cache: the `agent` target's `--no-cache` does not reach this step, for the reason the comment in `ensure_base_image` gives for the base.
  - The parent half is what carries a rebuilt base through. Today the `agent)` branch refreshes the base under `--pull`, and its comment promises "cascading any digest change into the agent layers automatically"; README "Build Modes" lists `./build.sh base` followed by `./build.sh agent` among its examples. With a set selected, both must leave the agent on a layers image built from the new base, never on one whose lower layers are the old base.
  - Compare the base's image ID, not its layer chain. The ID covers the image config as well as the layers, so a base change that leaves every filesystem layer alone (an `ENV` line, a label) reaches the agent too, and nobody has to reason about which base edits alter a layer.
  - Do not replace the test with an unconditional bake. Tier 1 (task 065) restores the layers image from a `docker save` tarball on a runner whose BuildKit cache is empty, so an unconditional bake there would reinstall the whole set on every run. It would also restamp `powbox.commit.layers` on every agent build and make that label meaningless.
  - A base bake at a new commit is such a label-only change once this task has landed (see the next decision). So every run that bakes the base at a new commit (`base`, `all`, `agent --pull`) leaves the layers image not current, and the next `layers`, `agent` or `all` step rebakes it. That is intended; the rebake is expected to consist of cache hits only.
- **No commit-dependent filesystem layer in the base.** The base keeps its commit only as the `powbox.commit.base` label, which lives in the image config. Remove the final `RUN` that writes `/home/node/.powbox/base.commit` from `docker/base/Dockerfile`. No `RUN` then follows any of the four per-build `ARG` lines, so a base bake whose recipe and upstream digest are unchanged reuses every filesystem layer and changes only labels.
  - The agent image writes the file instead, in its existing top metadata `RUN`, from a new build argument (for example `POWBOX_COMMIT_BASE`, default `unknown`) declared beside `ARG POWBOX_COMMIT_CODEX`. Do not declare it any higher: an `ARG` above the Codex or Claude install `RUN` would put the base commit into those layers' cache keys.
  - The build scripts supply the value: the `powbox.commit.base` label of the agent's **actual parent**, read with `image_label` / `Get-ImageLabel` once that parent is in place. The parent is the base, or the layers image, which inherits the label because the `layers` bake target does not set it. Resolve it where `run_bake` / `Invoke-Bake` resolve `POWBOX_BASE_IMAGE_ID` today, so that a base rebuilt earlier in the same run is the one described. An absent or empty label becomes `unknown`.
  - Readers see no change. `powbox-provenance` still finds `/home/node/.powbox/base.commit`, and the file agrees with the `powbox.commit.base` label that `powbox-agent:latest` inherits, because both come from the same parent. The base image on its own no longer contains the file; nothing reads it there.
  - Removing the `RUN` changes the base recipe digest, so the first update check after this lands reports the base stale and rebuilds everything once. That is expected.
- **What `all` costs with a set selected.** `agent-update --refresh` builds target `all`, and README "Profile Shortcuts" presents it as the cheap way to pick up recipe changes. With the commit file gone from the base, a second `all` at a new commit with an unchanged recipe is expected to go as follows.
  - Base: every step is a cache hit. The labels are restamped, so the image ID changes and the layer chain does not.
  - Layers: baked, because `all` always bakes it, and the currency test would demand it anyway since `powbox.layers.base.id` no longer matches. Its parent has a new ID but the same layers and environment, so every `RUN` and `COPY` of the layer Dockerfile is expected to be a cache hit. Only the `powbox.commit.layers` and `powbox.layers.base.id` labels are restamped; they come from the bake target, not from an `ARG` in the layer Dockerfile, so they enter no step's cache key. Nothing in the set is reinstalled.
  - Agent: the Codex, linter and Claude install layers are expected to be cache hits as long as the version arguments are the same as in the previous build. `agent-update --refresh` passes each binary's baked version number, so that holds when the previous build was pinned to the same numbers, as an earlier `agent-update` leaves it. After a build that passed no version (a plain `./build.sh all`, where both arguments default to `latest`) the arguments change from `latest` to numbers, and the first `--refresh` reinstalls both agents once for that reason alone. The top metadata layer and the cheap layers above it rebuild, as they do at every new commit.
  - This is cheaper than today, where the base's commit layer forces the Codex, linter and Claude installs on every `all` at a new commit. One side effect goes with it: a plain `./build.sh all` at a new commit used to reinstall both agents at whatever `latest` resolved to, and now reuses the cached install layers, as `./build.sh agent` already does, until a version is passed or `--no-cache` is given.
  - **Expected, not measured.** All of this rests on BuildKit keying a child image's steps on its parent's layer chain and environment, not on the parent's image ID. No build of this repo has confirmed it; it is the same assumption "Cache behaviour to verify" names, and the acceptance criteria pin it. If a real build contradicts it, stop and report the measurement to the maintainer, as that note says.
- **Update flow.** A stale base keeps today's behaviour (`all --pull --no-cache`), which now includes the layers image. A stale layer set with a current base rebuilds through the `agent` target **from cache**, with both agent binaries pinned to their baked versions unless they are stale too. `agent-update --refresh` keeps target `all`, from cache, at the cost described under "What `all` costs with a set selected". No new flags.

## Implementation notes

- **Porcelain row.** Add `layers<TAB><ok|stale><TAB><baked|-><TAB><wanted|->` where each value is `<set>@<digest>` or `-` for none. Read "baked" from the labels on `powbox-agent:latest`, because that is what containers run. `stale` when they differ, including selected-but-built-lean and lean-but-built-on-a-set. Trust only a non-empty recomputed digest: when a set is selected but its digest cannot be computed (no sha256 tool), skip the digest comparison alone, following the rule the base recipe digest already has in `commands/check-updates.sh` ("an undeterminable digest never forces a rebuild"). The set-name half of the comparison needs no digest and still runs: a selected set with none baked, a baked set with none selected, and a selected name that differs from the baked one all mark the row `stale` whether or not a digest could be computed, since `agent-update` would otherwise print "Nothing to update" over an agent built from the wrong set. Only an equal name with no computable digest reports `ok`, and the wanted value then shows the name with `-` for its digest. An invalid selector is different: that is the hard error from "Selector", not a quiet `ok`. Keep the three existing rows and their meaning unchanged.
- **Human report.** One `Layers` row between `Base` and `Codex`, in the existing format. It must print the literal `update available` marker when stale, because `agent-update` greps the report for it. With no set selected and none baked, print a row that says so (for example `(none — lean image)`) rather than omitting it.
- **`agent-update`.** Today a run with no stale binary and no `--refresh` prints "Nothing to update" before building. A stale `layers` row must reach the build instead: the `agent` target with `_powbox_build_from_table` pinning both binaries.
- **Codex-layer provenance.** `resolve_codex_commit` decides whether the Codex install layer will be reused by comparing `base_image_id` with the previous agent's `powbox.base.image.id` label. The Codex layer's parent is now the layers image when a set is selected, so compare against the **actual parent**, resolved after the layers image has been ensured. The resolver's early returns change with it. `[ "$PULL" = true ] && return 0` and `case "$TARGET" in base | all) return 0` sit under the comment "Any of these rebuild the Codex layer, so it was built at HEAD" (`Get-CodexCommit` has the same two tests). That held only because the base's commit file gave the base a new top layer at every commit. With the file gone, `all` at a new commit, and `--pull` when the upstream digest has not moved, leave the parent's layers and environment unchanged and reuse the Codex layer, so stamping `HEAD` would misattribute it. Drop both early returns and let those runs fall through to the parent comparison, which therefore has to run after the base and layers steps of the same run, not at script load where `resolve_codex_commit` is called today. `--no-cache` keeps returning `HEAD`; the `base` and `layers` targets build no agent and need no answer. A label-only change to the parent (new digest or commit label, identical filesystem layers) changes its image ID without invalidating the Codex layer, so compare the parent's layer chain (`docker image inspect --format '{{json .RootFS.Layers}}'`) rather than its `.Id`, or provenance will misattribute a reused layer to `HEAD`. The layer chain alone errs the other way for an `ENV`-only change in the parent, such as an edited `ENV` line in a layer Dockerfile (task 071 adds several): BuildKit is understood to key a `RUN` on the environment it inherits, so the Codex `RUN` would run again while the resolver carried the old commit forward. That was not measured on a build. Include the parent's environment (`{{json .Config.Env}}`) in the compared value anyway: if the assumption is wrong the cost is `HEAD` stamped on a reused layer, which is the resolver's existing fallback. The environment is not the only inherited configuration a `RUN` executes under, and the others are keyed the same way: BuildKit compiles a `RUN` into an exec whose arguments are the inherited `SHELL` plus the command, whose working directory is the inherited `WORKDIR` and whose user is the inherited `USER`, so a layer Dockerfile that changes only one of those rebuilds the Codex layer while a signature over layers and `Env` alone stays equal to the previous parent's, and `resolve_codex_commit` would carry the old commit forward onto a freshly built binary. Compare `.Config.Env`, `.Config.Shell`, `.Config.WorkingDir` and `.Config.User` together with the layer chain; leave out `.Config.Labels`, which is exactly the label-only change this comparison must ignore. State in `docs/skills-refresh-and-provenance.md` that the resolver approximates BuildKit's cache key and that the label is informational. This is a different question from the currency test above, which deliberately compares `.Id`: that one asks "must the layers image be rebuilt", this one asks "will Docker reuse the Codex layer". The agent's `powbox.base.image.id` label and the `POWBOX_BASE_IMAGE_ID` bake variable must then record whatever the resolver compares, for the actual parent (a sha256 over the JSON of the layer chain and those four config fields, in a fixed order, is enough). Keeping the name or renaming it is the implementer's call, since no backward compatibility is required, but every reader and comment must follow: grep for `powbox.base.image.id` and `POWBOX_BASE_IMAGE_ID` (at the time of writing `docker-bake.hcl`, `docker/agent/Dockerfile`, both build scripts, `docs/architecture.md`, `docs/skills-refresh-and-provenance.md`).
- **Layers commit.** `powbox.commit.layers` is `HEAD` at the time the layers image was last baked, exactly as `powbox.commit.base` is for the base. Because the `agent` target skips the bake for a current image, the label does not move on an ordinary agent rebuild. It does move on every `all`, and on any run that bakes it after a base bake, even when every step was a cache hit. Both labels therefore mean "last baked at this commit", not "content last changed at this commit"; say so where `docs/skills-refresh-and-provenance.md` describes the anchors.
- **Cache behaviour to verify.** Two behaviours rest on one assumption: BuildKit keys a child image's steps on its parent's layer chain and environment, so a parent whose labels changed and whose layers did not keeps the child's cache. Neither was measured on a build of this repo.
  - Layers image to agent: editing a file in the set that the layer Dockerfile does not `COPY` changes the digest label but no filesystem layer. Confirm on a real build that this does not reinstall Codex and Claude in the agent image (host session steps 4 and 8).
  - Base to layers image: a base bake at a new commit with an unchanged recipe changes only the base's labels. ## Acceptance criteria

- With no `.powbox-layers`, `./build.sh all` produces the base and agent images as today apart from where `base.commit` is written, no `powbox-agent-layers` image is built, and `agent-check-updates` shows the layers row as none and up to date.
